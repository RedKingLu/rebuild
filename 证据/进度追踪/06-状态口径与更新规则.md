## 0. 状态枚举

### 0.1 功能表状态（详述源）

| 状态 | 含义 | 设置条件 | 谁可设置 |
|------|------|---------|---------|
| `not_started` | 未开始 | 默认初始状态 | Agent |
| `planned` | 已有计划或方案 | 方案文档已产出且可引用 | Agent |
| `in_progress` | 正在施工 | 代码/文档正在编写 | Agent |
| `partial` | 部分实现，有明确缺口 | 已实现部分，缺口已写明 | Agent/验收Agent |
| `implemented` | 已实现但未验收 | 代码完成、build通过、自验通过 | Agent（需证据） |
| `verified` | 已通过测试/自验 | 有可复现测试证据 | Agent/验收Agent |
| `accepted` | 用户/Copilot/独立验收按规则接受 | 验收报告+用户确认 | 用户/验收Agent |
| `blocked` | 被阻塞 | 阻塞项已登记（引用阻塞ID） | Agent |
| `future` | 经明确理由归入未来 | 决策/待确认项中说明了归入原因和归属阶段 | Agent（需引用） |
| `deprecated` | 已废弃 | 有废弃记录和替代说明 | Agent（需用户确认） |

### 0.2 阻塞项状态

| 状态 | 含义 |
|------|------|
| `open` | 未解决 |
| `investigating` | 调查中 |
| `waiting_user` | 等待用户裁决 |
| `mitigated` | 已缓解（有 workaround） |
| `resolved` | 已解决 |
| `deferred` | 已延期（说明了后续阶段和解除条件） |

### 0.3 待确认项状态

| 状态 | 含义 |
|------|------|
| `open` | 待处理 |
| `proposed` | 已给出建议方案 |
| `user_confirmed` | 用户已确认 |
| `rejected` | 用户拒绝 |
| `superseded` | 被后续信息替代 |
| `promoted_to_decision` | 已升级为决策记录 |
| `closed` | 已关闭 |

### 0.4 施工记录状态

| 状态 | 含义 |
|------|------|
| `draft` | 草稿（施工中） |
| `completed` | 完成（待审核） |
| `reviewed` | 已审核 |
| `accepted` | 已验收通过 |
| `superseded` | 被后续轮次替代 |

### 0.5 验收证据状态

| 状态 | 含义 |
|------|------|
| `candidate` | 候选证据 |
| `self_verified` | 自验通过 |
| `independently_verified` | 独立验收通过 |
| `user_accepted` | 用户验收通过 |
| `stale` | 已过期（代码变更后证据不再有效） |

## 1. 能力项粒度规则

### 1.1 一个能力项的粒度

- 每个能力项应是可独立追踪、可独立验收的"用户/平台可感知能力"
- 不要过细（如"一个 API 端点一个功能项"），也不要过粗（如"整个后端"一个功能项）
- 判断标准：该能力是否可在某个 R 阶段内独立完成、独立验收

### 1.2 能力项必须有来源

- 每个功能项必须引用至少一个正式文档路径作为来源
- 不接受"凭记忆/凭印象"登记的功能项
- 如果找不到正式文档来源，登记为待确认项

### 1.3 能力项拆分/合并规则

- 如果一个功能项跨越多个 R 阶段，应拆分（如"Agent 定义（R6）"vs"Agent 运行时（R8）"）
- 如果多个功能项总是同时完成、同时验收，可以合并
- 拆分/合并后在功能表中注明

## 2. 更新触发条件

### 2.1 功能表更新触发

| 触发事件 | 更新动作 |
|---------|---------|
| R 阶段方案产出 | 新增能力项或更新状态为 `planned`（引用方案路径） |
| 施工开始 | 状态更新为 `in_progress` |
| 施工完成（部分） | 状态更新为 `partial` + 写明缺口 |
| 施工完成（全部） | 状态更新为 `implemented` + 补证据路径 |
| 自验通过 | 状态更新为 `verified` + 补验收证据索引 |
| 验收通过 | 状态更新为 `accepted` |
| 发现新能力需求 | 新增功能项 |
| 能力废弃 | 状态更新为 `deprecated` + 写明替代 |
| 被阻塞 | 状态更新为 `blocked` + 引用阻塞ID |
| 归入未来 | 状态更新为 `future` + 引用决策/待确认项 |

### 2.2 阻塞项更新触发

| 触发事件 | 更新动作 |
|---------|---------|
| 发现阻塞 | 新增阻塞项 |
| 阻塞解除 | 状态更新为 `resolved` |
| 阻塞缓解 | 状态更新为 `mitigated` + 说明 workaround |
| 用户裁决完成 | 状态更新为 `resolved` 或 `deferred` |

### 2.3 待确认项更新触发

| 触发事件 | 更新动作 |
|---------|---------|
| 发现待确认 | 新增待确认项 |
| 给出建议方案 | 状态更新为 `proposed` |
| 用户确认 | 状态更新为 `user_confirmed` |
| 升级为决策记录 | 状态更新为 `promoted_to_decision` + 反链决策编号 |

### 2.4 施工记录更新触发

| 触发事件 | 更新动作 |
|---------|---------|
| 方案/施工/验收/修复/收口轮次完成 | 新增施工记录 |
| 发现遗漏记录 | 补录（标注补录时间和来源） |

### 2.5 验收证据更新触发

| 触发事件 | 更新动作 |
|---------|---------|
| 测试/验收产出证据 | 新增证据索引 |
| 代码变更导致证据失效 | 证据状态更新为 `stale` |

## 3. 阶段收口一致性检查清单

每个 R 阶段标记 `accepted` 前，必须逐项检查：

```text
□ 01-功能表：本阶段涉及的所有能力项状态是否已更新？
□ 01-功能表：是否有 partial 能力缺口未写明？
□ 01-功能表：是否有 implemented 但无证据路径的能力？
□ 02-阻塞项：本阶段发现的阻塞是否已登记？
□ 02-阻塞项：本阶段解决的阻塞是否已更新状态？
□ 03-待确认项：本阶段发现的待确认项是否已登记？
□ 03-待确认项：需要升级到决策记录的待确认项是否已标记？
□ 04-施工记录：本阶段所有轮次是否已补录？
□ 04-施工记录：是否存在施工完成但无验收证据的轮次？
□ 05-验收与证据索引：本阶段验收证据是否已索引？
□ 05-验收与证据索引：证据是否可复现？是否 stale？
□ 06-状态口径与更新规则：是否需要修订（如新增状态/触发条件）？
□ D-074 检查：本阶段前端可见能力是否有最小前后端联调证据？
```

**以上任一项未完成，阶段不得标记 accepted。**

## 4. 防最小化施工红线

以下 10 条红线是进度追踪体系的核心防线。违反任一条，对应能力不得标记为 `implemented`/`verified`/`accepted`。

### 红线 1：不得用 placeholder 冒充 implemented

- **禁止**：将仅返回 `"status": "not_connected"` 的占位端点标记为 `implemented`
- **正确做法**：标记为 `partial` + 写明"仅占位骨架，无真实业务逻辑"

### 红线 2：不得用 mock 冒充真实能力

- **禁止**：将硬编码 mock 数据标记为真实能力完成
- **正确做法**：标记为 `partial` + 写明"当前为 mock，真实数据待 R? 阶段接入"
- **例外**：经 D-049 显式定义的体验壳 mock 边界可标记为 `implemented`（仅限 R3 体验壳）

### 红线 3：不得用 "service/API 已写" 冒充 "页面已联调"

- **禁止**：后端 API 已经写完但前端无任何页面调用，却标记为 `implemented`
- **正确做法**：API 部分标记为 `implemented`，页面联调部分标记为 `planned`/`partial`
- **强制**：D-074 要求 R5 起每个前端可见能力必须有最小联调证据

### 红线 4：不得用 "build 通过" 冒充 "功能验收通过"

- **禁止**：npm run build / pytest 通过就标记为 `accepted`
- **正确做法**：build 通过只是 `implemented` 的前提，不是 `accepted` 的充分条件

### 红线 5：不得将本阶段可完成能力无理由标记 future

- **禁止**：当前 R 阶段范围内可实现但为省工而标记 `future`
- **正确做法**：必须写明为什么本阶段不能完成、归属哪一阶段、解除条件

### 红线 6：不得登记 blocked 而不写原因和解除条件

- **禁止**：只写"阻塞"或"后续处理"而不说明原因、影响、推荐处理和解除条件
- **正确做法**：按 02-阻塞项.md 字段完整填写

### 红线 7：不得将用户未确认项写成 accepted

- **禁止**：Agent 自行将功能/方案/验收标记为 `accepted`
- **正确做法**：用户/Copilot/独立验收 Agent 审核通过后方可标记 `accepted`

### 红线 8：不得把历史版本事实直接复制为当前事实源

- **禁止**：从 archive 复制状态/数据/代码作为当前版本的"已完成"
- **正确做法**：历史吸收必须按三步法（自有方案→历史吸收→完善施工），吸收结果须有记录

### 红线 9：最小实现必须有缺口说明

- **禁止**：以"最小实现"替代范围基准内明确要求的能力但不写缺口
- **正确做法**：写明剩余缺口、归属阶段、阻塞原因和验收影响

### 红线 10：不得在未更新追踪材料的情况下结束阶段

- **禁止**：阶段标记 accepted 但追踪材料（功能表/阻塞项/待确认项/施工记录/证据索引）未更新
- **正确做法**：按 §3 收口一致性检查清单逐项检查后更新

## 5. "不能证明什么" 检查规则

对每条验收证据，必须回答"不能证明什么"：

- "build 通过" → 不能证明页面真实调用 API
- "service 存在" → 不能证明前后端联调
- "截图显示 UI" → 不能证明后端真实返回（除非有 Network/Trace/后端日志配套）
- "mock 数据显示正常" → 不能证明真实能力完成
- "API 返回 200" → 不能证明业务逻辑正确（可能是占位实现）

**验收证据必须能对应功能表中的能力项**。证据不足时不得向上标记状态。
