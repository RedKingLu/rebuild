## 0. 目录定位

本目录是 rebuild 项目 **进度追踪与防最小化施工辅助体系**。核心目的：

1. 基于范围基准、验收基准、R 阶段总计划、已完成施工/验收材料和当前工程状态，持续追踪平台能力、阻塞项、待确认项、施工记录和验收证据。
2. 防止后续 Agent 用最小化施工、占位实现、只写 service/API 不接页面、登记 future 但不说明原因等方式，替代平台范围内应完成的全面实现要求。

## 1. 与正式事实源的关系

本目录属于「证据 / 运行记录 / 治理辅助材料」，**不替代正式事实源**。

```
事实源层级（不变）：
  项目治理 > 产品定义 > 架构设计 > 专题规范

本目录定位（新增）：

```

**冲突规则**：若本目录内容与正式文档冲突，以正式文档为准，并在 `03-待确认项.md` 登记冲突。

## 3. 维护规则

### 3.1 强制更新时机

以下事件发生时，**必须**更新本目录对应文件：

| 事件 | 必须更新的文件 |
|------|--------------|
| 阶段方案产出 | 01-功能表（新增/变更能力项状态）、04-施工记录 |
| 阶段施工进行中 | 01-功能表（状态更新）、04-施工记录 |
| 阶段自验/验收 | 01-功能表、04-施工记录、05-验收与证据索引 |
| 阶段收口（accepted） | 全部 6 个追踪文件一致性检查并更新 |
| 发现阻塞 | 02-阻塞项 |
| 发现待确认项 | 03-待确认项 |
| 能力新增/变更/废弃 | 01-功能表 |
| 决策记录更新 | 03-待确认项（若关联待确认项升级） |
| D-074 前后端联调完成 | 01-功能表、05-验收与证据索引 |

### 3.2 阶段收口强制检查

每个 R 阶段标记 accepted 前，必须执行追踪一致性检查：

```text
□ 01-功能表：本阶段能力状态是否已更新？
□ 02-阻塞项：本阶段发现/解决的阻塞是否已登记？
□ 03-待确认项：本阶段发现/确认的待确认项是否已登记或升级？
□ 04-施工记录：本阶段施工/修复/验收轮次是否已补录？
□ 05-验收与证据索引：本阶段验收证据是否已索引？
□ 06-状态口径与更新规则：是否仍适用？是否需要修订？
```

**若未完成以上检查，阶段不得标记 accepted。**

### 3.3 防最小化施工红线（摘要）

完整规则见 `06-状态口径与更新规则.md` §4。

1. 不得用 `placeholder` 冒充 `implemented`
2. 不得用 `mock` 冒充真实能力
3. 不得用 "service/API 已写" 冒充 "页面已联调"
4. 不得用 "build 通过" 冒充 "功能验收通过"
5. 不得将本阶段可完成能力无理由标记 `future`
6. 不得登记 `blocked` 而不写阻塞原因、解除条件和推荐处理
7. 不得将用户未确认项写成 `accepted`
8. 不得把历史版本事实直接复制为当前事实源
9. 不得以"最小实现"替代范围基准内明确要求的能力
10. 不得在未更新追踪材料的情况下结束阶段
