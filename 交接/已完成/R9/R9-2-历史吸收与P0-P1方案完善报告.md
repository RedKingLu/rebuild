### 2.2 修订 1：施工自验 vs 独立评审 vs 独立验收

| 概念 | 执行主体 | 用途 | R9 使用场景 |
|------|---------|------|-----------|
| **施工自验** | 施工 Agent + 自验 Skill | 提交前自查；可用 checklist、测试命令 | R9-3A/B/C/D 每轮执行后 |
| **Review Pass** | Node Worker Agent + Review Skill | 阶段内质量检查；小循环返工判断 | P0/P1 每轮结束 |
| **独立评审** | 非施工 Agent（干净上下文） | 关键设计点/高风险事项复核 | 仅当 Review Pass 发现高风险或用户要求时 |
| **独立验收** | Acceptance Agent | 阶段完成条件验收 | **R9-4 必须使用 Acceptance Agent** |
| **Auto 授权代理** | Auto Review/Authorization Agent | Auto 模式阶段内 L0-L3 授权 | R9-3D Auto 模式 |

**关键约束**：
- 施工 Agent **不得**同时担任自己工作的独立验收 Agent
- Review Pass **不等于**独立验收
- R9-4 独立验收必须由 Acceptance Agent 执行

### 2.3 修订 2：三模式自由切换机制

原 R9-1R "Run 启动后模式锁定" 修订为：

**设计原则**：Workspace 顶部模式切换是用户惯性心智，不应锁死。

| 维度 | 规则 |
|------|------|
| **切换即时性** | 切换立即生效于后续动作 |
| **历史不变** | 已执行动作不回滚、不改历史判断 |
| **执行中保护** | 当前正在执行不可中断动作时，切换进入 pending，动作结束后生效 |
| **记录** | 每次切换写 Trace（mode_change 事件）；若切换导致授权密度变化，写 Audit |
| **阶段 Gate 不可绕过** | 无论什么模式，阶段晋级 Gate 强制用户确认 |
| **L4+ 不可绕过** | Auto 模式不能代理 L4+ 高风险动作 |
| **Manual 切换后** | 后续低风险动作也需要用户逐项确认 |
| **Plan 切换后** | 若有已有阶段内计划，提示是否沿用/重算/废弃 |
| **Auto 切换后** | 自动执行阶段内低风险动作，但仍必须 Review Pass |

**数据模型**：
- `Workspace.current_mode`：顶部 UI 当前选择（即时反映用户意图）
- `RunAction.effective_mode`：每个动作执行时的实际 mode（不可变历史记录）
- `ModeChangeEvent`：记录切换时间、from_mode、to_mode、操作者、reason

### 2.4 修订 3：Auto 授权代理边界

| Auto 可以代理 | Auto 不得代理 |
|--------------|-------------|
| 阶段内 L0-L3 动作授权 | P0→P1 / P1→P2 阶段晋级 Gate |
| 阶段内写盘/读取/识别/建档 | L4+ 高风险动作 |
| Review Pass 后的阶段内返工确认 | 达到最大返工轮数后的人工介入 |
| Artifact/Evidence 生成 | 敏感信息泄露疑似项 |
| | 用户明确要求人工确认的项 |
| | R 阶段验收 accepted 裁决 |

**Auto 授权输出记录**（结构化，写入 Trace/Audit）：
```json
{
  "decision": "approved | rejected | escalate_to_human",
  "reason": "...",
  "risk_level": "L0-L5",
  "evidence_refs": [...],
  "trace_refs": [...],
  "audit_ref": "...",
  "mode": "auto",
  "reviewer": "auto_authorization_agent"
}
```

### 2.5 修订 4：Review Pass 与 Auto Review Agent 概念区分

| 概念 | 是什么 | 谁执行 |
|------|--------|--------|
| **Review Skill**（如 intake-review、profile-review） | 阶段内 Review Pass 的 Skill | Node Worker Agent 加载执行 |
| **Auto Review / Authorization / Safety Agent** | D-019 定义的 5 种 Agent 之一 | 独立 Agent，有自己上下文 |
| **Acceptance Agent** | D-019 定义的 5 种 Agent 之一 | 独立 Agent，用于阶段验收 |

**使用规则**：
- P0/P1 的普通 Review Pass → Node Worker + Review Skill（不切 Agent）
- Auto 模式阶段内授权 → Auto Review Agent 独立执行
- 关键设计评审 / 高风险复核 → Auto Review Agent 独立评审
- R9-4 验收 → Acceptance Agent 独立验收

### 2.6 修订 5：source materialization 实现边界

| 实现方式 | 适用场景 | 约束 |
|---------|---------|------|
| **后端 service 安全库函数** | ZIP 解压、文件复制、索引生成 | `shutil`/`zipfile` + `_guard` 路径检查 |
| **受控 Git service** | Git/GitHub clone | `git_service.py` + timeout + 路径 guard + 脱敏 |
| **受控 subprocess** | 需 shell 的原生命令（如 `git clone`） | 仅在后端 service 内调用，非终端驱动 |
| **终端 UI** | 展示日志、触发受控动作 | **不是** materialization 的主要执行机制 |

### 2.7 修订 6：Trace/Audit 失败处理

| 级别 | 动作类型 | Trace 失败处理 | Audit 失败处理 |
|------|---------|--------------|--------------|
| L0-L1 | 只读/低风险 | 记录 warning，继续；阶段 Gate 前展示 | N/A |
| L2-L3 | 受控执行/外部影响 | 重试 1 次；仍失败 → Evidence Gap | 重试 1 次；仍失败 → 人工 Gate |
| L4-L5 | 高风险/不可逆 | 阻断阶段完成 | 必须阻断，进入人工 Gate |

**关键动作清单**（Trace 失败阻断）：source materialization、intake_report 生成、P1 full profiling、Artifact 写入、Evidence Gap 写入、Gate 决策、mode change、Auto 授权代理决策。

### 2.8 修订 7：测试验收口径

取消 `pytest ≥ N` 硬门槛，改为：

| 验收项 | 标准 |
|--------|------|
| 后端 pytest | **全量 0 failed**（允许 skipped） |
| 前端 build | **exit 0** |
| R9 新增测试覆盖 | 必须覆盖 R9-3A/B/C/D 各子轮关键链路 |
| 浏览器级测试 | Playwright 或等价工具覆盖 P0/P1 小循环、三模式切换、阶段 Gate、Artifact/Evidence 可见性 |
| 测试数量 | 不做固定门槛；增减需在报告中说明原因 |

### 2.9 修订 8：待确认项最终收敛

原 Q-R9-1R-01（轻量 AST）和 Q-R9-1R-02（大项目分片）不再作为开放式问题，改为默认策略：

| 问题 | 默认策略 | 调整条件 |
|------|---------|---------|
| 识别深度 | 先文件级全量识别（14 项） | Review 发现 confidence 不足 → 触发轻量 AST 解析作为返工增强 |
| 大项目分片 | 按顶层目录分片 | 项目结构不适合目录分片 → 按文件类型或模块分片 |

唯一保留需用户裁决的项：
- **Q-R9-2-01**：R9-3C 全量识别施工中，是否需要 AI 模型辅助判断依赖兼容性（如判断某个 NuGet 包是否与信创兼容）？建议：先做文件级识别+规则匹配；若用户需要更深度的兼容性分析，在 R9-3C 返工轮或 P2 评估阶段引入 ModelGateway 辅助分析。

## D-079：OpenCode ACP 协议集成（2026-06-26）

| 字段 | 内容 |
|------|------|
| **决策ID** | D-079 |
| **决策类型** | 技术方案 |
| **状态** | **accepted** |
| **关联** | D-076（执行分层）、D-077（Agent 配置）、D-078（选择机制） |
| **背景** | OpenCode 提供了 ACP（Agent Client Protocol）协议，允许平台通过 `opencode serve` + ACP 客户端与 OpenCode 进行结构化交互，替代旧版 `opencode run --dangerously-skip-permissions` 的危险调用模式。 |
| **决定** | （1）OpenCode 集成采用 ACP 协议：`OpenCodeServer` 管理 `opencode serve` 进程生命周期 → `OpenCodeACPClient` 通过 HTTP/SSE 与 OpenCode 通信 → 权限请求经 SSE 事件流回到平台审核；（2）`qcode_cli` 和 `platform_agent` 类型暂返回 stub（`invoke_status: "deferred_to_r11"`），真实实现归 R11；（3）ACP 集成不改变 D-076 执行分层——代码执行仍走 ExecutionProvider，OpenCode 仅用于 AI 编码 Agent 场景。 |
| **理由** | ACP 协议比旧版 CLI 模式更安全（权限可控、结构化通信）；为 R11 P4 执行阶段打下基础。 |
| **影响/约束** | `opencode_adapter.py` 中 `invoke()` 仅 opencode_cli 走 ACP 真实调用；qcode/platform_agent 返回 stub；ACP 通信不泄露 Key/Token。 |

## D-080：P0/P1 阶段采用小循环机制（2026-06-27）

|------|------|
| **决策ID** | D-080 |
| **决策类型** | 产品方案 |
| **状态** | **proposed**（R9-2 方案阶段，待用户确认后 accepted） |
| **关联** | D-020（NodeLoop 小循环）、D-023（阶段 Gate）、D-025（三执行模式）、R9 P0-P1 |

## D-081：三模式自由切换机制（2026-06-27）

| 字段 | 内容 |
|------|------|
| **决策ID** | D-081 |
| **决策类型** | 产品方案 |
| **状态** | **proposed**（R9-2 方案阶段，待用户确认后 accepted） |
| **关联** | D-025（三执行模式）、D-023（阶段 Gate）、D-034（L5 强制用户 Gate）、R9 |
| **背景** | R9-1R 原设计中"Run 启动后模式锁定"的约束不符合 Workspace 顶部自由切换模式的用户惯性心智。用户应能根据当前任务状态随时调整自动化程度。 |
| **决定** | （1）Manual / Plan / Auto 支持 Workspace 顶部自由切换；（2）切换即时生效于后续动作，不回滚已执行动作；（3）当前正在执行不可中断动作时切换进入 pending；（4）每次切换写 Trace（mode_change 事件），若影响授权密度写 Audit；（5）无论什么模式，阶段晋级 Gate 强制用户确认，L4+ 高风险动作强制用户 Gate；（6）数据模型：Workspace.current_mode（UI 当前选择）+ RunAction.effective_mode（历史不可变）+ ModeChangeEvent（切换记录）。 |
| **理由** | 用户工作区体验类比编程工具的模式切换；锁死模式会导致用户在错误模式启动后被迫重建 Run。 |
| **影响/约束** | 三模式不再是 Run 创建时的一次性参数；后端需支持运行时模式切换 API；前端 ExecModeSwitch onChange 需即时生效并写 Trace。 |
| **验收要求** | Manual/Plan/Auto 自由切换实测通过；切换后后续动作按新模式执行；已执行动作不受影响；切换写 Trace/Audit；阶段 Gate 不受 Auto 绕过。 |
| **开发/施工归口** | R9-3A（数据模型）+ R9-3D（切换机制） |
| **最近更新时间** | 2026-06-27 |

## D-082：施工自验与独立验收分离原则（2026-06-27）

| 字段 | 内容 |
|------|------|
| **决策ID** | D-082 |
| **决策类型** | 过程规范 |
| **状态** | **proposed**（R9-2 方案阶段，待用户确认后 accepted） |
| **关联** | D-016（少Agent多Skill）、D-017（Agent切换条件）、D-019（5种Agent类型）、R9-4 |
| **背景** | R9-1 原方案中"换 Agent 评审/验收"表述模糊，需要明确区分施工自验、Review Pass、独立评审、独立验收、Auto 授权代理的概念边界和执行主体。 |
| **决定** | （1）施工自验：施工 Agent 使用自验 Skill 做提交前自查，可由施工 Agent 完成；（2）Review Pass：阶段内质量检查，Node Worker Agent 加载 Review Skill 执行，不切换 Agent；（3）独立评审：非施工 Agent 对关键设计点/高风险事项做复核，仅在 Review Pass 发现高风险或用户要求时触发；（4）独立验收：Acceptance Agent 对阶段完成条件做验收，R9-4 必须由 Acceptance Agent 独立执行，施工 Agent 不得自验；（5）Auto 授权代理：Auto Review Agent 在 Auto 模式下代理阶段内 L0-L3 授权，不替代阶段 Gate。 |
| **理由** | 防止施工 Agent 自己验收自己工作导致的"既当运动员又当裁判"问题；同时避免为每个评审环节都拆出独立 Agent（回到多Agent碎片化）。 |
| **影响/约束** | R9-4 必须调用 Acceptance Agent；R9-3A~D 的 Review Pass 不切 Agent；施工 Agent 的自验 Skill 明确标记为 self_check 非 acceptance。 |
| **验收要求** | R9-4 独立验收报告由 Acceptance Agent 执行（非施工窗口）；施工自验与 Review Pass 在施工记录中诚实标记执行主体。 |
| **开发/施工归口** | R9-3D（Agent 调用链）+ R9-4（独立验收） |
| **最近更新时间** | 2026-06-27 |
