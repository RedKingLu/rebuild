## 4. R8 遗留项处理建议

### 4.1 D-078 `Project.coding_agent_ref` 字段
**现状**：`Project` 模型（`backend/app/models/project.py`）**无** `coding_agent_ref` 字段。`CodingAgentConfig` 表独立存在，与 Project 无关联。前端 `CodingAgentSelector` 组件（`WorkspacePage.tsx:410-437`）已渲染 `<select>` 下拉框，调 `listCodingAgents()` 获取真实数据，但选择结果仅存本地 state，未持久化。

**处理建议**：
- R9-3 在 `Project` 模型新增 `coding_agent_ref: Mapped[str | None]` 字段（nullable FK → `coding_agent_config.agent_id`）
- 生成 Alembic 迁移
- `PATCH /projects/{id}` 支持更新 `coding_agent_ref`
- 前端 `CodingAgentSelector` 的 `onChange` 调用 `updateProject(id, {coding_agent_ref})`
- 真实 AI 编码调用仍归 R11；R9 只做配置与选择持久化

### 4.2 Coding Agent 选择器 UI
**现状**：已存在于 `WorkspacePage.tsx:410-437`，调真实 API `listCodingAgents()`，选中的 agent 存本地 state。**工程上已就绪**，仅缺持久化连接。

**处理建议**：见 §4.1，补充持久化即可闭合 D-078 R8 部分。

### 4.3 三模式 Manual / Plan / Auto
**现状**：`ExecModeSwitch`（`WorkspacePage.tsx:390-405`）渲染三个按钮（自动/计划确认/手动），状态存 `useWorkspaceStore.execMode`（Zustand 本地 state）。`RunCreate` schema 有 `mode` 字段但 `RunService.create()` **完全不读取**。后端无任何三模式差异逻辑。功能表 GAT-04 标记 `partial`——"前端按钮为静态 Mock，后端未实现执行策略"。

**处理建议**：见 §8（三模式最小真实策略方案）。

### 4.4 终端 cwd 非工作区
**现状**：`LocalSubprocessExecutionProvider._run_subprocess` 使用 `bash -c` 执行命令，**未显式设置 `cwd`** 为项目工作区目录。命令在后端进程的当前工作目录下运行，非项目工作区。`ls` 看不到项目文件。R8-4 验收报告列为 P2（D-P2-1）。

**处理建议**：R9-3 顺手修复——在 `execute()` 调用时传入 `cwd=workspace_path(project_id)`，使终端命令在项目工作区执行。改动量小（1-2 行），不涉及新架构。

### 4.5 输出面板 outputHistory 死态
**现状**：`WorkspacePage.tsx:51-53`：
```tsx
const [outputHistory] = useState<Array<...>>([]);
```
无 setter，永不填充。终端执行结果仅在 `TerminalPanel` 内部 state 可见，"输出"tab 恒为空。R8-4 验收报告列为 P2（D-P2-2）。

**处理建议**：R9-3 顺手修复——将 `outputHistory` 改为 `useState` + 从 `TerminalPanel` 通过 callback 或 store 推送执行结果。或者如果"输出"tab 与"终端"tab 功能重叠，经用户确认后可合并/移除。

### 4.6 `_guard` 前缀安全
**现状**：`_guard` 是 `workspace_service.py` 中的私有路径校验函数（`startswith(str(ws))` 无分隔符），非 HTTP 端点。R8-4 验收报告指出 `projects/p1` 是 `projects/p10` 前缀风险（P2，D-P2-3），但因 UUID 工作区难触发。

**处理建议**：R9-3 顺手加固——改用 `os.path.commonpath` 或加 `os.sep` 后缀，消除前缀匹配风险。

### 4.7 persistence 标记诚实性
**现状**：Trace/Audit `persistence` 硬编码 `file+memory`。R8-4 指出 project_id 为空时实际未落盘仍标 file+memory（P2，D-P2-4）。envelope meta 仍带 R4 默认 `source_status=mock`（P2，D-P2-5）。

**处理建议**：R9-3 顺手修复——persistence 根据实际落盘结果动态标记；envelope meta 的 source_status 更新为 `real`（对已真实化的端点）。

### 4.8 引导向导本体
**现状**：`OnboardingWizard.tsx` 组件已存在（5 步模态：环境选择/Git/模型/执行模式/摘要确认）但**未被任何路由或页面引用**。WorkspacePage 显示诚实占位提示条（"完整引导向导将在 P0 接入阶段（R9）开放"），读取真实 `onboarding_done`。R8 引导方案判定已确认：**向导本体归 R9**。

4. **执行模式倾向**（前端已有开关，待后端真实化）：Manual / Plan / Auto

### 6.2 用户在向导中需要确认/补充的内容
按 §25 引导向导 5 步：

| 步 | 内容 | 数据来源 | 用户动作 |
|----|------|---------|---------|
| 1 | 环境选择 | 读 Environment Profile（R8 已有） | 确认本地/远程、填写 language_hint、framework_hint（可选） |

| 5 | 摘要确认 | 汇聚前 4 步 | 确认或返回修改 → 写入后端 → 设置 onboarding_done=true → 触发 P0 Run |

### 6.4 是否生成 Artifact/Evidence
**是**。P0 必须产生：
- **Artifact**: 接入报告（`intake_report`），含来源类型、文件数、警告/错误、Environment Profile 摘要
- **Evidence candidates**: 源码可访问、工作区已初始化、文件索引已创建、凭据已验证
- **Evidence 状态**: candidate（非 validated——验证归 P5）

### 6.5 Trace/Audit 记录
- **Trace**: 向导每一步写入 Trace（`workspace_action` / `onboarding_step`），接入报告生成为 `intake_action`
- **Audit**: 环境更新（L1）、执行模式选择（L2）、P0→P1 Gate 决策（L3）
- 复用 R8 已有的 TraceWriter / AuditWriter

### 6.6 P0→P1 状态推进
1. 向导完成 → `onboarding_done = True`
2. 创建 Run（P0 起始阶段）→ `current_stage = "p0"`
3. 生成接入报告 Artifact + Evidence candidates
4. 触发 P0→P1 promotion Gate（强制用户确认，D-023）
5. 用户 Gate approve → `current_stage = "p1"` → 进入 P1 建档

### 6.7 三模式在 P0 中的差异
| 模式 | P0 向导 | 接入动作 | Gate |
|------|---------|---------|------|
| Manual | 每步需用户确认 | 每步需用户显式触发 | P0→P1 强制用户 Gate |
| Plan | 用户确认摘要即可 | 计划内动作自动执行 | P0→P1 强制用户 Gate |
| Auto | 可跳过向导（默认值） | 低风险自动 | P0→P1 强制用户 Gate |

**关键**：无论什么模式，P0→P1 Gate 必须用户授权（D-023/D-025）。

### 6.8 异常处理
| 异常场景 | 处理方式 |
|---------|---------|
| 信息缺失（如语言/框架未知） | 标记为 `unknown`，不阻塞；纳入 P1 待确认清单 |
| 环境未知（远程不可达） | 标记 `status=unknown`，向导提示；不阻塞进入 Workspace |
| 模型不可用 | 允许跳过模型配置；P1/P2 可补充 |
| 材料缺失（空项目） | 诚实标记；P0 仍可完成（"空项目已接入"） |
| Git 凭据缺失 | Gate 提示需配置凭据；不阻塞 P0 完成（可在 P1/P2 补充） |

- P1 产物出现在材料视图的 `artifacts/` 和 `materials/` 目录下

### 7.4 技术栈初步识别
**当前版本方案**（不引入重量级代码分析工具）：
1. 扫描项目文件扩展名统计 → 推断主要语言
2. 检测常见构建文件（`package.json`、`pom.xml`、`requirements.txt`、`Makefile`、`go.mod` 等）→ 推断框架/构建系统
3. 检测常见配置文件（`Dockerfile`、`docker-compose.yml`、`.github/` 等）→ 推断部署/CI 形态
4. 结果写入 `tech_stack_hint` Artifact，标记为 `auto_detected`（非权威），用户可在材料视图中修正
5. 不确定的标记为 `uncertain`，纳入待确认清单

**范围限制**：不做 AST 解析、不做依赖版本精确识别、不做安全漏洞扫描。这些归 P2 评估阶段。

### 7.5 Environment Profile 更新

- `status`: `unknown` → `declared`（用户声明）或 `detected`（自动检测）
- `language_hint`: 自动检测补充
- `framework_hint`: 自动检测补充
- 写入 Trace + Audit

### 7.6 风险/待确认项初始清单
P1 自动生成以下 Evidence Gap 候选：
- 技术栈不确定项（如"检测到 Java 和 Python 混合项目，主语言待确认"）
- 依赖缺失（如"Go 项目未找到 go.mod"）
- 配置缺失（如"检测到 Dockerfile 但无 docker-compose.yml"）
- 材料缺失（如"未找到 README 或项目文档"）

用户可在 Evidence 面板查看、补充、关闭（需填写理由）。

### 7.7 P1→P2 输入包
P1 完成后形成进入 P2 的输入包：
- 项目档案（所有 Artifact）
- 技术栈识别结果
- 依赖清单初稿
- Environment Profile（状态 ≥ declared）
- 待确认项清单
- P1 建档摘要

P2 评估阶段直接引用这些 Artifact 和 Evidence。

### 7.8 P1 完成状态记录
- `Run.current_stage = "p1"` → `"completed"`（Stage 状态）
- P1 建档摘要 Artifact 生成
- 所有 Evidence candidates 注册
- P1→P2 Gate 触发（强制用户确认）
- Trace 记录完整建档过程

### 7.9 Trace/Audit 记录
- **Trace**: 技术栈检测、依赖扫描、档案生成、Environment Profile 更新每步写入 Trace
- **Audit**: Profile 更新（L1）、用户编辑档案（L2）、P1→P2 Gate 决策（L3）

### 7.10 不确定项是否阻塞 P1→P2
**不阻塞**。不确定项以 Evidence Gap 形式进入 P2，在 P2 评估阶段处理。但：
- P1→P2 Gate 必须列出所有待确认项，用户知情后确认
- 关键信息缺失（如无法识别任何技术栈、项目完全为空）标记为 Blocking Evidence Gap，需用户显式确认或补充

## 8. 三模式最小真实策略方案

### 8.1 核心原则
三模式（Manual / Plan / Auto）只影响**阶段内动作的授权密度**，不改变：
- P 阶段定义和顺序
- 阶段晋级 Gate 必须用户授权（D-023）
- L5 高风险动作强制用户 Gate（D-034）
- Evidence/Trace/Audit 要求

### 8.2 P0-P1 中三模式的具体差异

| 动作 | Manual | Plan | Auto |
|------|--------|------|------|
| 引导向导 | 每步确认，不可跳过 | 可跳过直接看摘要 | 可完全跳过（用默认值） |
| 环境检测 | 用户触发 | 向导完成后自动 | 项目创建后自动 |
| 技术栈识别 | 用户触发 | P1 启动时自动 | P0 完成后自动 |
| 档案生成 | 用户逐项确认 | 批量生成后用户审查 | 自动生成，用户事后审查 |
| Artifact 生成 | 用户触发 | 自动 | 自动 |
| Evidence 候选 | 自动检测 + 用户确认 | 自动检测 + 用户确认 | 自动检测 |
| 写盘动作（L2） | 每项需用户授权 | 计划内自动，越界回用户 | 低风险自动 |
| 阶段晋级 Gate | **强制用户 Gate** | **强制用户 Gate** | **强制用户 Gate** |

### 8.3 三模式状态保存
| 存储位置 | 字段 | 说明 |
|---------|------|------|
| Run | `execution_mode: Literal["manual", "plan", "auto"]` | Run 级别，一次 Run 内不变 |
| Project | （不存 mode） | Mode 是 Run 属性，非 Project 属性 |
| 前端 | `useWorkspaceStore.execMode` | 当前 Workspace 的 UI 状态，Run 创建时写入后端 |

**实现路径**：
1. R9-3 在 Run 创建 API 中实际读取 `mode` 字段（schema 已有，服务未使用）
2. 前端 `ExecModeSwitch` 的 onChange 在 Run 创建/切换时 POST 到后端
3. 后端根据 `execution_mode` 调整 Gate 密度（R9 最少差异，R10-R11 扩展）

### 8.4 三模式 Trace/Audit
- 所有模式下，动作必须写 Trace
- Audit 密度随模式变化：Manual 更多 Audit（每步授权），Auto 更少（仅高风险 + Gate）

### 8.5 当前版本诚实限制
R9 只实现 P0-P1 范围内的三模式差异。P2-P6 的三模式完整策略（Task Plan 批量授权、Hook+Policy 放行、Auto Review Agent 等）归 R10-R11。R9 做：
- **真实**：三模式在 P0 向导和 P1 建档中的差异行为
- **占位**：三模式对后续阶段的接口预留（`Run.execution_mode` 持久化、Gate density 参数）
- **不伪装**：不假装 Auto 模式已能全自动执行 P2-P6
