## 1. 文档正式化工作流

### 1.1 流转路径

```
产物/草稿/<文件>.md  →  四步分析  →  文档/<目标路径>.md（状态：待审核）  →  用户审核  →  accepted
```

### 1.2 执行步骤

每次只处理一份文档，除非用户明确要求批量处理。

```
Step 1: 判断该文档是否应该具备 → 使用模板 templates.md §5.1
Step 2: 定义应具备内容       → 使用模板 templates.md §5.2
Step 3: 检查草稿是否满足需求  → 使用模板 templates.md §5.3
Step 4: 给出完善计划          → 使用模板 templates.md §5.4
Step 5: 生成正式候选文档      → 使用模板 templates.md §5.5
Step 6: 追加阶段总报告        → 使用模板 templates.md §5.6
Step 7: 更新阶段总表
Step 8: 等待用户审核
```

> Step 1 结论为"否/合并/拆分/改名"时必须停止并等待用户确认。
> Step 4 存在待用户确认项时必须先停止。

### 1.3 总报告维护

不要为每份文档生成零散独立报告。按阶段维护总报告+总表：

```
交接/当前/R?-<阶段名>总报告.md    ← 追加每份文档处理记录
交接/当前/R?-<阶段名>总表.md      ← 同步更新状态行
```

### 1.4 根目录文件特殊规则

根目录级文件（如 AGENTS.md、README.md）按决策记录指定路径写入，同样遵守正式化流程。

## 2. 交接材料工作流

### 2.1 流转路径

```
交接/当前/<交接提示词>.md  →  本轮完成  →  交接/已完成/<轮次>/
```

### 2.2 交接材料必须包含（13 项）

```
项目背景 / 当前阶段 / 当前裁决 / 事实源路径 / 任务目标
执行边界 / 输入资料 / 输出要求 / 禁止事项 / 验收标准
待确认项 / 下一步建议 / Agent 启动自检
```

### 2.3 写入位置

| 状态 | 路径 |
|------|------|
| 当前使用 | `交接/当前/` |
| 完成归档 | `交接/已完成/<轮次>/` |

### 2.4 自检清单

使用 [templates.md §6.2](templates.md#62-交接材料自检清单) 的 checkbox 清单逐项检查。

## 3. 历史版本参考工作流

### 3.1 参考顺序

```
1. 先明确当前版本需求（自有方案）
2. 再确定需要参考什么历史材料
3. 只读历史材料（rebuild-archive/ 或 rebuild-old/）
4. 提取可吸收思想、字段经验、交互心智、失败反例
5. 判断是否适配当前版本
6. 记录吸收/不吸收/风险 → 使用模板 templates.md §4
```

### 3.2 绝对禁止

- 直接复制旧代码
- 直接复制旧文档作为正式文档
- 复活旧 RunEngine
- 复用旧 S0-S7 为当前主流程
- 把旧 F0-F6 当当前 P0-P6
- 让历史目录成为当前运行依赖

### 3.3 三步法集成

历史参考是模块建设三步法（AGENTS.md §7.1）的第二步。必须在自有方案产出后执行，不得跳过第一步直接吸收历史。

## 4. 施工前计划与三步法工作流

### 4.1 三步法（硬规则，来自 AGENTS.md §7.1）

建设任一模块时必须：

```
第一步：先独立提出当前版本自己的方案（不先看旧代码，保证主体性）
第二步：再深度吸收对应历史方案（archive 只读，记录吸收/不吸收/适配/风险）
第三步：用吸收到的经验完善自己的方案，再执行
```

必须先产出三段产物方可进入施工：`自有方案 → 历史吸收记录 → 完善后方案`

### 4.2 施工前检查清单

在写任何代码之前，逐项检查：

```
□ 当前阶段是否允许施工？
□ 三步法是否已完成（自有方案→历史吸收→完善方案）？
□ 事实源是否充足？
□ 涉及路径是否明确？
□ 技术栈是否需要变更（如需→C4申请）？
□ 是否涉及密钥或L4/L5风险？
□ 是否会改变已确认决策？
□ 是否会绕过LangGraph主编排？
□ 是否会复活旧RunEngine？
□ 输出施工计划模板（templates.md §3）
```

> 任一项触发"是（有问题）"→停止，登记待确认项。

### 4.3 施工计划必须包含

```
任务目标 / 当前阶段 / 事实源依据 / 涉及路径
拟修改文件 / 不修改文件 / 依赖条件 / 执行步骤
风险级别 / Gate 要求 / 回滚方案 / 验收标准 / 待确认项
```

### 4.4 最小前后端联调验收门（R5 起，详述源 D-074）

含前端可见能力的 R 阶段，施工与验收必须确认：

```
□ 本阶段新增/变更能力，是否至少有一个页面或入口在运行期真实调用了对应后端端点？
□ 是否在运行的前端实测到对后端的真实请求（Playwright 网络捕获 / 后端 Trace 增量 / Network 面板）？
□ 范围是否在交接/验收报告显式写明（已联调哪条、仍 mock 哪些）？
□ 真实能力未就绪时，是否以诚实 not_connected/mock 标记承载真实请求（而非伪装联调）？
```

> 仅写 service/API 而无任何页面或入口实际调用 → 该阶段未达完成条件，验收记为不通过项。
> "service 已存在""build 通过"不得替代运行期真实请求证据。完整定义见 `01-决策记录.md` D-074、`06-R阶段总计划.md` §3.2.1。

## 5. 安全与密钥检查

### 5.1 允许

识别是否存在：`.env`、配置文件、密钥文件、Provider 配置、认证配置。

### 5.2 绝对禁止

禁止输出或写入：Key、Token、Secret、Password、`.env` 明文、API Key 明文、认证凭据。

禁止写入目标：报告、日志、Trace、Audit、前端页面、截图说明、交接材料、正式文档、Git 提交。

### 5.3 安全记录写法

```
发现某类配置文件，内容已脱敏，需用户或本地环境自行确认。
```

## 6. 阶段总报告与总表维护

### 6.1 总报告追加

每完成一项任务，在阶段总报告中追加一条记录（使用 templates.md §5.6 的字段模板）。

### 6.2 总表同步更新

总表字段：`编号 / 对象路径 / 对象类型 / 输入路径 / 是否应具备 / 处理状态 / 当前版本 / 最后处理时间 / 主要风险 / 待确认项 / 输出路径 / 总报告对应章节 / 审核状态`

处理状态枚举：`未开始 / 评估中 / 待确认 / 已生成待审核 / 已审核通过 / 需返工 / 取消 / 已合并 / 已归档 / 阻塞`

> 禁止只写报告不更新总表。
