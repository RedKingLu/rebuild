## 2. 文档与产物流转规则

### 2.1 文档生命周期（状态机）

```
                    ┌──→ rework（返工）──┐
                    │                    │
产物/草稿/ → Agent 评估完善 → 文档/ (待审核) → 用户审核 → accepted
                              │                           │
                              └──→ blocked（阻塞）        └──→ superseded（被替代）
```

**状态枚举**（详述源：`02-术语表.md`）：

| 状态 | 含义 | 谁可设置 |
|------|------|---------|
| `draft` | 草稿，尚未正式化 | Agent |
| `待审核` | 正式候选，等待审核 | Agent |
| `accepted` | 审核通过，可作为事实源 | 用户 |
| `superseded` | 已被后续版本替代 | 用户/Agent |
| `rework` | 需返工 | 用户 |
| `blocked` | 阻塞，等待条件 | Agent |

### 2.2 交接材料与产物流转

```
交接/当前/  →  本轮完成  →  交接/已完成/<轮次>/
产物/草稿/  →  Agent 处理  →  产物/已完成/  或  晋升至 文档/
```

归档落位：按轮次子目录归档（`交接/已完成/R0/ R1/ …`）。交接材料不自动成为项目文档，晋升必须走 §2.1 正式化流程。

### 2.3 更新时机规则

| 事件 | 必须更新 |
|------|---------|
| 任务开始 | 读取交接/当前/，确认阶段和事实源 |
| 每份文档处理完成 | 追加阶段总报告 + 更新总表 |
| 阶段完成 | 归档交接材料 + 归档产物草稿 |
| **阶段收口（accepted）** | **执行收口六步：① 登记文档状态 ② 归档交接材料 ③ 归档产物草稿 ④ git 提交 ⑤ 清空当前区 ⑥ 追踪一致性检查 + 更新全部追踪文件。任意一步缺失 = 收口未完成** |
| 发现待确认项 | 登记到总报告 + 总表 + `03-待确认项.md` |
| 发现阻塞项 | 登记到 `02-阻塞项.md`（不得仅写在聊天中） |
| 能力变更 | 更新 `01-功能表.md` |

### 2.4 禁止的流转操作

- 草稿直接搬入 `文档/`
- 交接材料直接标为 accepted
- 产物自动视为事实源
- 跳过总报告/总表更新直接标记完成
- 阶段收口时只做文档登记/git 提交，却漏掉归档流转

## 3. 工程原则

> 本节吸收 Karpathy 工程十诫，针对 rebuild 项目本地化适配。所有原则的具体示例和反面教材见下文各节。

### 3.1 先读后写

编写任何代码或文档之前：

- **通读你将修改的所有文件。** 不是粗略扫读，是完整阅读。
- **参考项目中同类功能的实现范式。** rebuild 后端路由有统一规范（`routes_*.py` → `*_service.py` → models），前端组件有固定目录结构。遵循既有规范，不要另起炉灶。
- **检查导入语句，明确项目实际使用的依赖库。** 项目用 httpx 就继续用 httpx，别引入 requests；项目用 SQLAlchemy 2.0 Mapped 风格就保持一致。
- **读测试文件。** 测试定义了功能的真实预期行为，而非你主观认为应该有的行为。
- **读决策记录和术语表。** rebuild 有大量已裁决的决策（D-xxx）和术语枚举，不要凭经验臆测。
- **不确定实现范式就直接问。** "我没有在代码库中找到 X 功能的实现范式，我应该沿用 Y 的实现思路，还是采用其他方案？" 主动询问永远比瞎猜要好。

### 3.2 先想后做

**明确你的预设前提。** "加上认证功能"可能指会话 Cookie、JWT、OAuth 等五种方案。不要默默选一种就开干。说明你的默认假设，等确认——判断错了只浪费 10 秒，默默猜错浪费一整个小时。

**说明方案的权衡取舍。** 每种实现都有利弊。"这个方案以内存占用换取访问速度，同时引入缓存失效问题"。用户可能回复"我不想引入这么高的复杂度"。

**存在多种方案时，简要列出并推荐。** 两三种即可。"方案 A 更简单但无法处理 X 边界场景；方案 B 能覆盖所有情况但引入 Z 依赖。除非你预计 X 会真实出现，否则我推荐 A"。

**遇到需求歧义立刻停下。** 不要用看似合理的代码掩盖认知模糊。直接说明哪里有歧义，主动向用户确认。

**施工前必须先输出计划。** 涉及代码/前端/后端/API/测试/模型/集成/资源等施工时，必须先输出施工计划（模板见 [references/templates.md]）。计划不说清楚，代码一定写不对。

**必须停止的情形：**
- 任务目标不清 / 阶段不清 / 事实源冲突
- 范围争议 / 技术栈变更未确认
- 涉及密钥或 L5 高风险权限
- 会改变已确认决策 / 绕过 LangGraph 主编排
- 会导致返工或污染正式事实源
- 未先输出施工计划就要动代码（AGENTS.md §6.3 / 本 Skill §4.1）

### 3.3 保持简洁

编写能解决问题的最少代码——不是理论上最精简，而是**当下能切实解决这个具体问题的最少代码**。

**过度设计的四个典型表现（rebuild 特化）：**

**过早抽象。** 你只需一个查询函数，却写了一个 Repository 模式 + 策略模式 + 工厂模式的三层架构。用户要的只是 `get_project_by_id(pid)` 这个函数。那就只写这个函数。如果后续需要更多功能，他们会提出来。

```python
# ❌ 反面——rebuild 项目中也曾出现过
class ProjectRepository:
    def __init__(self, session_factory, cache_strategy, ...): ...
    async def find_by_id(self, pid: str, include_relations: List[str] = None): ...

# ✅ 正面——简洁直接
def get_project(db: Session, project_id: str) -> Project | None:
    return db.get(Project, project_id)
```

**想当然的错误处理。** 给所有代码套 try/catch，捕获不会发生的错误，校验上游已验证的输入，对永远不会为空的值做空值检查。只处理真实可能发生的错误。rebuild 有统一的异常处理层（FastAPI exception handlers），不要在业务代码里重复包裹。

**不必要的可配置性。** 把批量大小、重试次数、超时秒数全做成环境变量。配置不是免费的——每个配置项都意味着需要人做决策。在有真实需求之前，硬编码即可。

**僵化的灵活性。** 只有一个实现的接口、只有一个子类的抽象基类。这些设计都有认知负担——在第二个实现真正出现之前，没有任何收益。

**检验标准**：把你的代码拿给不熟悉这个项目的人看。如果他们不得不问"为什么要这样抽象？"，而你的回答是"万一我们以后需要……"，那就是过度设计了。**"万一以后需要"不是需求，只是对未来的猜测。**

**特别注意**：rebuild 的薄编排 / NIH 约束（D-037、D-065）本身就是对过度设计的防范——不要引入重量级第三方编排框架、不要自建 Agent 框架替代 LangGraph。

### 3.4 精准修改

修改现有代码时，变更内容应尽可能少。**你修改的每一行都可能引入 bug，都需要有人评审，都会永久留存在 git blame 记录里。**

规则：

- **不要动没让你碰的代码。** 修复函数 A 的 bug？函数 B 的变量名奇怪——别管。函数 C 的注释有拼写错误——别管。导入顺序不符合你的偏好——别管。你的任务只是修复函数 A。
- **遵循现有代码风格。** 文件用单引号你就用单引号；用蛇形命名法你就用蛇形命名法；没有分号就别加分号。文件内的风格一致性比你的个人偏好更重要。
- **清理自己造成的冗余，别管别人的。** 你的修改导致某个导入不再被使用 → 删掉。你的修改导致某个变量闲置 → 删掉。但原本就存在的死代码不是你的问题。
- **不要重新格式化代码。** 不要跑 prettier、不要改缩进风格、不要重排导入顺序。重新格式化产生大量变更，掩盖真正的修改内容。
- **一次只改一处。** 改一处，测一次；再改一处，再测一次。同时改三处然后 bug 消失——你根本不知道是哪处起了作用。

**检验标准**：审视你的 diff。能为每一行修改找到和需求直接相关的理由吗？如果有哪一行只是因为"既然改到这儿了，我顺便……"，就改回去。

### 3.5 务实验证

**"能运行的代码"和"你以为能运行的代码"之间的差距，就是测试。**

- **修复 bug 前先复现。** 先写一个能复现 bug 的测试，确认它会失败。再修复 bug，再确认测试通过。这不是教条——这是证明你真修了问题、而非掩盖症状的唯一方法。
- **修改前后都运行现有测试。** 修改前测试通过、修改后失败 → 你破坏了功能。修改前测试就失败 → 要明确说明，不要让你的修改背锅。
- **不要为了写测试而写测试。** 校验构造函数正确赋值的测试毫无价值。测试行为，而非实现；测试有意义的场景。
- **写不了测试就说明原因。** "我很难为这部分写测试，因为数据库调用和业务逻辑高度耦合"——这本身就是架构可能需要重构的信号。不要默默跳过测试。
- **rebuild 特化**：测实验收结论必须区分四档（P0 阻断 / P1 重要 / P2 次要 / REC 建议）。必须有证据。No Evidence No Completed。后端全量 pytest + 前端 build + 最小前后端联调（D-074）。

### 3.6 目标驱动执行

**开始前，每个任务都应有清晰的成功标准。** 将模糊任务转化为可验证任务：

- "加上校验" → "拒绝特定无效输入，返回 400 + 错误原因，补充对应测试"
- "修复 bug" → "复现 → 测试通过 → 原有测试全部正常"
- "优化性能" → "先定位瓶颈 → 针对性修复 → 重新测量"

**多步任务必须先说明计划：**

```
计划：
1. 数据库迁移新增字段
2. 更新模型纳入新字段
3. 修改 API 接口支持接收并返回该字段
4. 添加校验逻辑
5. 编写测试
6. 运行全量测试检查回归
```

这样做有两个好处：用户在你浪费时间实现之前就能发现方案错误；迫使你真正想清楚执行步骤。

### 3.7 系统调试

代码出问题时，**不要瞎猜，去调查。**

- **完整阅读错误信息。** 全部内容都要看，包括堆栈跟踪。同一种错误类型可能有上百种成因——错误信息和堆栈会告诉你到底是哪一种。
- **先复现问题。** 能复现 → 修改 → 验证修复。"我觉得这样应该能修好"不是调试，是赌博。
- **一次只改一处。** 同时改三处 → bug 消失 → 你不知道是哪处起作用，也不知道另外两处有没有引入新 bug。
- **没搞懂根因就不要打补丁。** 值意外为空 → 不要只加空值检查。搞清楚它为什么为空。空值检查也许能避免崩溃，但底层 bug 仍然存在。
- **卡住了就直说。** "我试过了 X 和 Y 方案，都不行。目前观察到的现象是……我觉得问题可能出在 Z，但还不确定。" 这比闷头瞎试二十次有用得多。

### 3.8 依赖克制

不要不假思索就新增依赖。**你引入的每一个依赖，都是你无法掌控的代码，会永久成为项目的一部分。**

新增依赖前先问自己：

- **用项目已有依赖能实现吗？** rebuild 已有很多依赖（httpx、SQLAlchemy、Pydantic、LangGraph 等），优先复用。
- **用标准库能实现吗？** Python 3.12 标准库已很强大——简单的文件操作、JSON 处理、日期格式化不需要第三方包。
- **这个依赖还在维护吗？** 查最近提交时间、issue 数量。
- **它的体积有多大？** 为一个小功能引入重量级包，得不偿失。

如果确实要新增依赖，**说明理由**。"我引入 zod 是因为项目需要运行时 schema 校验"——合理。默默往 `pyproject.toml` 里加包 —— 不可取。

### 3.9 有效沟通

你如何沟通代码相关的问题，和代码本身一样重要。

- **说明你做了什么、为什么这么做。** 不要只扔代码出来。"我把校验逻辑抽成独立函数，因为它在三个接口里重复了。这样也方便单独测试。" 用户不用逐行读代码就能理解你的改动。
- **主动提示风险。** "功能能跑，但列表每一项都会发起一次数据库调用。如果列表变长，性能会很差。需要我改成批量处理吗？"
- **明确说出你不确定的点。** "我不确定这个库是否支持流式响应"是有用信息；"我觉得应该可以"没有价值。
- **不要解释用户已经知道的内容。** 如果人家让你加 REST 接口，别解释什么是 REST。根据用户展现的知识水平调整解释深度。
- **提交信息要具体。** "修复 bug"毫无意义。"修复邮箱含大写字母时用户查询空指针的问题"让下一个人清楚地知道发生了什么。

### 3.10 常见失效模式

以下模式一旦发现，**立刻停下来重新思考**：

| 模式 | 症状 | 修正 |
|------|------|------|
| **大包大揽** | 让你加一个功能，你"顺手"重构了半个代码库 | 只做要求的那一件事 |
| **错误抽象** | 为只出现一次的问题搭建通用方案 | 重复代码的成本远低于错误抽象。先允许自己复制粘贴两次 |
| **隐形决策** | 做出架构选择（schema、API 形态）却不明确告知 | 这类选择的改造成本很高，用户应当知晓 |
| **乐观路径** | 理想流程能跑，其他情况忽略或崩溃 | 多想 API 返回 500、文件不存在、表单为空怎么办 |
| **知识幻觉** | 信心满满使用不存在的 API / 已删除的参数 / 臆想的特性 | 不确定就去查文档、看项目真实源码。直接说"我不确定" |
| **风格漂移** | 在面向对象代码库里写函数式，在 JS 项目里写 TS 风格 | 贴合代码库，非你的个人偏好 |
| **失控重构** | 修复一个问题 → 牵连另一处 → 再牵连下一处 → 改了 15 个文件忘了最初要做什么 | 立刻停下。告诉用户现状，获得认可后再继续 |
| **跳过计划直接码** | 需求到手就开始写代码，中间发现理解偏差再返工 | 先输出计划（§3.6），让用户确认方向 |

   技术标识符（provider_id / model_name / API 格式名 / 字段名）保留原文。
