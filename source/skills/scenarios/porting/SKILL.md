# 软件移植（porting）

> 本场景为平台**典型场景之一**。移植的判据是**目标平台上行为等价**，不是"能编译"。目标平台须由项目的 `migration_target` 明确。

## 目标态词表

**跨操作系统**

- Windows → Linux（当前 LTS 发行版）
- Windows → macOS
- Linux → Windows（含 WSL 与原生两条路径，须区分）

**跨 CPU 架构**

- x86_64 → ARM64（aarch64）
- x86_64 → RISC-V
- 32 位 → 64 位（指针宽度与结构体布局变化）

**跨移动 / 终端平台**

- Android → iOS
- Android → HarmonyOS
- 桌面原生 → 跨平台框架（Qt / .NET MAUI / Flutter / Electron）

**构建系统目标态**

- 平台专有构建（MSBuild / Xcode 工程）→ 跨平台构建（CMake / Bazel / SDK-style 工程）

## 迁移与重构模式

- 平台 API 抽象层：把平台相关调用收敛到一层薄适配接口，业务代码只依赖该接口；先抽象、再补第二平台实现。
- 条件编译边界收敛：`#if` / `#ifdef` 只允许出现在适配层内，不得散落业务代码，否则平台组合数爆炸且无法测试。
- 构建系统跨平台化先行：先把构建迁到跨平台构建系统，再处理代码，否则每次验证都要手工搭环境。
- 原生依赖重编译：所有含原生代码的依赖在目标架构上重新构建，交叉编译工具链与目标 sysroot 须固定版本。
- 行为等价抽样：为关键路径建立输入输出样本集，在源平台与目标平台各跑一遍逐项比对，作为移植完成的判据。
- 资源与本地化并行处理：字体、图标、日期与数字格式、区域设置在不同平台的默认值不同，须与代码移植同批验证。

## 常见陷阱与已知不兼容点

- **路径分隔符与大小写敏感文件系统**：Windows 不区分大小写、Linux 区分；硬编码 `\` 与拼错大小写的资源路径在 Linux 上直接找不到文件。
- **换行符差异**：`CRLF` 与 `LF` 在按行解析的文本协议、签名校验、diff 与脚本 shebang 上产生真实故障。
- **字节序与结构体对齐**：二进制序列化格式在跨架构时可能因对齐填充与字节序不同而不可互读，须改用显式定义的序列化格式。
- **P/Invoke 与 JNI 的平台绑定**：函数签名、调用约定、库文件命名（`.dll` / `.so` / `.dylib`）与查找路径全部平台相关，不能只改库名。
- **指针宽度与整型宽度假设**：32 位 → 64 位时 `long` 在 Windows 与 Unix 上宽度不同（LLP64 与 LP64），依赖固定宽度的代码须改用显式宽度类型。
- **权限与沙箱模型差异**：Android → iOS 的文件访问、后台执行、通知权限模型不同，Android 上可行的后台策略在 iOS 上会被系统终止。
- **字体与本地化资源**：目标平台缺少源平台的默认字体，导致布局溢出与缺字；区域设置默认值差异改变日期与小数分隔符解析。
- **大小写不敏感文件系统上的重名**：macOS 默认不区分大小写，Linux 区分，同名不同大小写的文件在跨平台仓库中会静默覆盖。
- **符号可见性与动态链接**：Linux 默认导出全部符号、Windows 需显式导出，未处理时出现"编译通过、运行找不到符号"。
- **进程与信号模型**：`fork` 语义、信号处理、进程间通信原语在 Windows 上无直接对应，须改用平台等价机制。

## 反例与禁止

- 禁止把"能编译"当作"已移植"（须有目标平台上的行为等价验证证据）。
- 禁止在业务代码中散落条件编译分支（须收敛到适配层）。
- 禁止跨架构沿用源平台预编译的原生依赖产物。
- 禁止只在模拟器 / 交叉编译环境验证而不在目标真机 / 目标架构上运行。
- 禁止忽略区域设置与字体差异后声明界面移植完成。
