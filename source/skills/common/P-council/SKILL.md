# P-council（多视角评审委员会）

## 适用阶段与触发条件
- 阶段：跨阶段（主要 P2 选型 → P5 验证），用于 go/no-go 难以单点裁断的场景。
- 触发：目标栈选型有争议（如达梦 vs openGauss vs GaussDB）、高风险迁移决策（停机切换、数据双写、不兼容特性改写）、多个候选方案得分接近、单一 Agent 评审置信度不足。
- 不适用：常规无争议的机械转换、已有明确规范可直接判定的任务。

## 输入
- 待评审议题：方案 A/B/...，含背景、约束、风险点、各方案权衡。
- 已知约束：信创合规要求、性能基线、兼容性边界、可维护性要求、交付时限。
- 触发原因：为何无法单点裁断（分歧点是什么）。

## 执行步骤
1. **设定评审席位**：召集多视角独立子 Agent——安全/合规、性能、兼容性、可维护性（对应 ECC 的 Skeptic/Pragmatist/Critic 三类立场，重新落地为信创四维）。
2. **独立评审**：各席位在不互相串通的前提下，对每个候选方案给出评分、理由、风险与红线触碰判断。
3. **暴露分歧**：汇总时显式列出各席位的一致项与冲突项，不掩盖分歧。
4. **加权汇总**：按权重 安全/合规 > 功能正确 > 性能 > 风格/可维护性 计算综合结论。
5. **形成建议**：输出推荐方案 + 关键理由 + 残留风险 + 需用户最终裁决的开放问题。
6. **路由 Gate**：本 Skill 只产出「建议」，不替代用户裁决；高风险决策走 HITL Gate 由用户确认。

## 输出 / 产物（Artifact / Evidence）
- 评审纪要（Artifact）：每席位的评分/理由/风险，分歧矩阵，加权汇总过程。
- 建议书（Artifact）：推荐方案、置信度、残留风险、待用户裁决项。
- 证据（Evidence）：各方案引用的事实依据（基准测试数据、兼容性清单、合规条款）；模型推理过程为分析，不充当 Evidence。
- 写入 Trace/Audit 并登记 Registry，关联议题与本次 run。

## 质量门 / 验收标准
- 至少覆盖安全/合规、性能、兼容性、可维护性四个视角，且各视角独立产出。
- 分歧被显式呈现，未被合并掩盖。
- 综合结论的权重次序与平台红线一致（安全>功能>性能>风格）。
- 明确标注哪些是建议、哪些必须由用户 Gate 裁决。

## 信创迁移要点
- 目标栈选型须落实信创合规清单（自主可控目录、等保要求）作为安全/合规席位硬约束。
- 兼容性席位关注遗留 SQL 方言、存储过程、字符集、隐式类型转换在达梦/openGauss/GaussDB 上的差异。
- 性能席位以真实基准为准，不以厂商宣称值代替实测。
- 高风险切换（停机/双写/灰度）的回退预案必须在评审范围内。

## 反例 / 禁止
- 禁止各席位互相参考后趋同（破坏独立性）。
- 禁止本 Skill 直接「拍板」高风险决策，绕过用户 Gate。
- 禁止把分歧抹平成单一结论而不披露冲突。
- 禁止以模型臆测代替方案的事实依据（基准/兼容性清单）。
- 禁止在评审记录中泄露任何凭据/连接串/Token。

## 与平台集成
- 各席位子 Agent 经多 Agent harness 调度，模型调用统一走 ModelGateway，用量计入预算。
- 评审结论对齐 HITL Gate：建议→用户裁决，不替代裁决。
- 纪要/建议 → Artifact/Evidence + Trace/Audit + Registry。
- 与 P-coding-standards、P-context-budget 协同控制评审上下文规模与口径。
