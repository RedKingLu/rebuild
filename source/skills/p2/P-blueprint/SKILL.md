# P-blueprint（迁移蓝图）

## 适用阶段与触发条件

- 阶段：P2 评估收尾 / P3 规划。
- 触发：评估完成、目标栈选型有 ADR 支撑后，需把「把系统从 X 迁到信创栈 Y」这一目标转为可执行的多步 / 多 Agent 施工计划。
- 目标：产出迁移蓝图——分解为带自包含上下文 brief 的步骤、明确依赖图、识别可并行项、并经对抗式评审 Gate，对齐平台交接提示词机制实现冷启动可执行。

## 输入

- P0 接入档案、P1 建档、P2 评估报告与选型 ADR。
- P-documentation-lookup 的兼容性证据与「待确认清单」。
- 迁移目标一句话陈述 + 约束（时间窗、停机容忍度、资源）。

## 执行步骤

1. **目标拆解**：将总目标分解为有序工序（schema 迁移 / 数据迁移 / 服务改造 / 中间件适配 / 集成验证），落到 P4 执行的可调度单元。
2. **自包含 brief**：为每步写冷启动上下文 brief——该步要做什么、依赖哪些前置产物、输入输出、目标栈约束、验收口径。要求新 Agent 仅凭 brief 即可开工，不依赖隐性记忆（对齐平台交接 / 接力提示词机制）。
3. **构建依赖图**：用 DAG 表达步骤依赖（如「数据迁移」依赖「schema 迁移」与「类型映射确认」），杜绝断裂 / 环。
4. **识别可并行项**：标出无依赖关系、可并行执行的步骤（如多个独立模块的服务改造），供平台多 Agent 调度。
5. **风险矩阵**：每步评估风险（概率 × 影响），高风险项给出缓解与回滚预案；引用 ADR 中已知负面后果。
6. **对抗式评审 Gate**：以「找漏洞」视角自审蓝图（遗漏依赖 / 低估难度 / 缺回滚 / 并行项实际有隐藏依赖），评审通过后蓝图方可进入 P4。
7. **变更协议**：蓝图为活文档，执行中如需变更，按既定变更协议更新依赖图与受影响 brief，并留痕。

## 输出 / 产物（Artifact / Evidence）

- 《迁移蓝图》：工序分解 + 每步自包含 brief。
- 步骤依赖图（DAG）与可并行项标注。
- 风险矩阵（含缓解 / 回滚预案）。
- 对抗式评审记录与变更日志。
- 蓝图挂 Project/Stage，附 Trace/Audit；引用的评估 / 兼容性数据为 Evidence。

## 质量门 / 验收标准

- 每步 brief 可独立冷启动：不读其他上下文即能理解任务与验收口径。
- 依赖图无环、无断裂；并行标注经对抗评审确认无隐藏依赖。
- 每个高风险项都有回滚预案。
- 蓝图与 P2 评估 / ADR 双向可追溯。

## 场景要点（按项目场景取用）

- schema 迁移必须前置于数据迁移，且类型映射（Oracle/MSSQL → 达梦 DM/openGauss/GaussDB）须在独立步骤先确认并立 brief，否则数据步骤大概率返工。
- 服务改造与数据库迁移的依赖方向要明确：ORM / SQL 方言改写依赖目标库已就绪。
- 中间件适配（东方通 / 宝兰德）与 OS 迁移（麒麟 / 统信）常可与应用层改造并行，但 JDK / 依赖库版本约束须写入相关 brief。
- 停机敏感系统：蓝图须区分可在线迁移与需停机的步骤，数据迁移规划增量 / 双写 / 回切预案。
- 「待确认清单」中的兼容性未决项必须显式作为蓝图前置阻塞项，不得乐观假设。

## 反例 / 禁止

- 禁止 brief 依赖「上一个 Agent 知道的隐性背景」——必须自包含。
- 禁止把有依赖关系的步骤标为可并行。
- 禁止高风险步骤无回滚预案就进入执行。
- 禁止跳过对抗式评审直接交付蓝图。
- 禁止把未确认的兼容性当作「已支持」写进计划。

## 与平台集成

- 蓝图生成、brief 撰写、风险归纳经 ModelGateway 调用，不直接调 Provider。
- 蓝图本身是规划产物（不直接执行外部写）；进入 P4 后的任何 L4-L5 写操作 / 真实库变更须经用户 Gate。
- 蓝图、依赖图、风险矩阵挂 Project/Run/Stage/Node，生成 Artifact/Evidence 并附 Trace/Audit/Registry；变更经变更协议留痕。
- 模型对计划可行性的判断属辅助，不是 Evidence；自检与对抗评审不替代 Acceptance 验收。
- 社区 Skill 默认只读。
