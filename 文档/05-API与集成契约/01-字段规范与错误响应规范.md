## 1. 字段规范定位

字段规范用于保证不同 API、事件、状态、Trace、Audit、前端展示之间使用一致的字段语义。

字段规范回答：

```text
1. 每个字段如何命名；
2. 每个字段如何标注类型、必填性和来源；
3. 哪些字段是对象标识符；
4. 哪些字段是状态；
5. 哪些字段是引用；
6. 哪些字段敏感；
7. 哪些字段必须 Trace；
8. 哪些字段必须 R2 校准；
9. 如何避免 Mission / V26.1 / mock 污染长期契约。
```

字段规范不回答：

```text
1. 最终数据库字段；
2. 最终 ORM 模型；
3. 最终 OpenAPI schema；
4. 前端组件实现；
5. 安全策略本体；
6. 业务流程裁决。
```

## 2. 字段命名原则

R1 建议字段命名采用：

```text
snake_case；
语义清晰；
对象前后一致；
避免缩写；
避免版本号固化；
避免历史旧阶段名；
避免 Mission 产品层残留。
```

推荐：

```text
project_id；
run_id；
stage；
task_graph_id；
node_id；
gate_id；
trace_ref；
audit_ref；
evidence_refs；
artifact_refs；
created_at；
updated_at。
```

避免：

```text
mission_id；
phase15_id；
f0_state；
s0_node；
v26_project_id；
secret_value；
api_key_plaintext；
ui_status_as_source。
```

说明：

```text
1. 历史字段如 mission_id 只能作为迁移待校准项出现（D-054）；
2. 如确有 task_group_id / objective / run_goal 需求，必须说明语义，不得借 Mission 复活产品层；
3. V26.1 只作为当前版本标识，不进入长期字段。
```

## 3. 字段元数据标注规范

R1 每个字段建议标注：

```text
field_name；
type；
required；
description；
source；
example；
r2_calibration_required；
sensitive；
trace_required；
audit_required。
```

可选补充：

```text
allowed_values；
default_value；
nullable；
validation_rule；
owner_domain；
related_fields；
deprecated；
superseded_by。
```

字段说明规则：

```text
1. description 应说明业务语义，不只复述字段名；
2. source 应说明字段来自用户输入、系统生成、LangGraph、Workspace、ModelGateway、Registry、Trace / Audit 或其他来源；
3. required 应区分创建请求必填、更新请求可选、响应必返；
4. sensitive 必须标记是否可能涉及敏感信息；
5. trace_required 表示字段变化是否必须进入 Trace；
6. audit_required 表示字段变化是否必须进入 Audit；
7. r2_calibration_required 默认为 true，除非已由上级事实源明确固定。
```

> 关联决策：D-016（R1 建议 → R2 校准）

## 4. 通用标识符字段

建议统一使用以下标识符字段：

```text
project_id：Project 标识；
run_id：Run 标识；
stage：P0-P6 阶段标识；
stage_plan_id：Stage Plan 标识；
task_plan_id：Task Plan 标识；
task_plan_batch_id：Task Plan Batch 标识；
task_graph_id：TaskGraph 标识；
node_id：Task Node 标识；
edge_id：Task Edge 标识；
gate_id：Gate 标识；
artifact_id：Artifact 标识；
evidence_id：Evidence 标识；
trace_id：Trace 标识；
audit_id：Audit 标识；
resource_id：平台资源标识；
model_call_id：模型调用标识；
integration_id：集成适配标识；
execution_session_id：Execution Session 标识。
```

标识符规则：

```text
1. 标识符应由后端生成或由可信系统生成；
2. 前端不得伪造后端标识；
3. 标识符不得包含明文密钥或用户敏感内容；
4. 标识符不应编码 V26.1；
5. 标识符不得复用历史 Mission 层语义（D-070）。
```

## 5. 状态字段规范

状态字段必须明确所属对象。

建议命名：

```text
project_status；
run_status；
stage_status；
task_graph_status；
node_status；
gate_status；
execution_session_status；
artifact_status；
evidence_status；
resource_status；
model_call_status；
integration_status。
```

不建议仅使用：

```text
status
```

除非字段所在对象上下文已经绝对清晰。

状态规则：

```text
1. 不同对象状态不得混用；
2. completed 必须满足该对象完成条件；
3. blocked 必须有 blocking_reason 或 error_ref；
4. waiting_gate 必须有关联 gate_ref；
5. failed 必须有 error_ref 和 trace_ref；
6. rework_required 必须有 rework_reason 或 rework_plan_ref；
7. canceled 必须有 cancel_reason；
8. 状态变化必须可追踪。
```

## 6. 时间字段规范

建议时间字段：

```text
created_at；
updated_at；
started_at；
completed_at；
resolved_at；
canceled_at；
archived_at；
expires_at；
last_checked_at。
```

规则：

```text
1. 时间字段必须说明时区或采用统一序列化格式；
2. created_at 表示记录创建时间；
3. updated_at 表示最后更新记录时间；
4. completed_at 不得早于 started_at；
5. resolved_at 适用于 Gate / error / review；
6. expires_at 不得被解释为自动批准；
7. 时间字段不得由前端单独作为事实源。
```

R2 需校准：

```text
1. 时间格式；
2. 时区策略；
3. 数据库存储类型；
4. 前端显示格式；
5. SSE 事件时间来源。
```

## 7. 引用字段规范

引用字段用于避免复制内容形成第二事实源（D-068 单一事实源原则）。

建议使用：

```text
workspace_ref；
source_ref；
checkpoint_ref；
artifact_refs；
evidence_refs；
trace_ref；
trace_refs；
audit_ref；
audit_refs；
model_policy_ref；
resource_ref；
error_ref；
review_record_ref；
policy_refs；
gate_ref。
```

引用规则：

```text
1. 引用字段应指向可追踪对象；
2. 引用不得复制完整事实正文；
3. 引用失效时不得自动继续执行；
4. Evidence / Artifact / Trace / Audit 应通过引用传递；
5. 历史 archive 引用必须标记为只读参考；
6. 外部链接引用必须记录来源和可信度。
```

## 8. 敏感字段与脱敏规范

敏感字段包括但不限于：

```text
Key；
Token；
Secret；
Password；
credential；
private_key；
api_key；
access_token；
refresh_token；
.env 明文；
未脱敏连接串；
可还原密钥片段。
```

字段规则：

```text
1. API 不得返回明文密钥；
2. 请求中如必须接收凭据，也应优先转为 credential_ref / secret_ref；
3. 响应中只能返回 redacted、exists、missing、credential_ref 等安全表示；
4. error_message 不得包含敏感明文；
5. trace / audit 不得包含敏感明文；
6. 前端不得展示敏感明文；
7. 日志不得记录敏感明文。
```

建议安全表示：

```text
credential_ref；
secret_ref；
redacted；
has_credential；
credential_status；
last_checked_at；
validation_error_ref。
```

## 9. 分页、排序与筛选字段

列表 API 可采用统一分页字段：

```text
page；
page_size；
next_cursor；
previous_cursor；
has_more；
total_count。
```

排序字段：

```text
sort_by；
sort_order。
```

筛选字段：

```text
filter；
status_filter；
stage_filter；
resource_type_filter；
risk_level_filter；
created_after；
created_before；
updated_after；
updated_before。
```

规则：

```text
1. total_count 如性能成本高，可标记为可选；
2. cursor 分页优先用于事件、Trace、Audit 等高量数据；
3. sort_by 必须限制允许字段；
4. filter 不得支持未经授权的敏感字段查询；
5. R2 需校准具体分页策略。
```

## 10. 布尔能力字段规范

能力字段建议命名：

```text
can_pause；
can_cancel；
can_resume；
can_retry；
can_rework；
can_approve；
can_reject；
can_execute；
can_write；
can_view_audit。
```

规则：

```text
1. can_* 表示当前用户 / 当前上下文下是否允许该动作；
2. can_* 不等于动作一定成功；
3. can_* 不能覆盖 Policy；
4. 高风险动作即使 can_execute 为 true，也可能仍需 Gate；
5. 前端按钮状态不得成为唯一权限事实源。
```

## 11. 请求响应结构规范

### 11.1 成功响应

建议结构：

```text
request_id；
status；
data；
trace_ref；
warnings；
next_actions；
created_at。
```

规则：

```text
1. data 承载业务对象；
2. warnings 承载非阻塞风险提示；
3. next_actions 承载后续建议动作；
4. trace_ref 用于定位请求处理过程；
5. status 应表示请求处理结果，不替代业务对象 status。
```

### 11.2 失败响应

建议结构：

```text
request_id；
status；
error_code；
error_message；
error_details_ref；
trace_ref；
gate_ref；
retryable；
next_actions；
created_at。
```

规则：

```text
1. error_code 必须机器可读；
2. error_message 应面向用户或前端可展示；
3. error_details_ref 指向后端可控详情，不直接暴露敏感内容；
4. gate_ref 在 Gate 阻塞时必填；
5. trace_ref 在可追踪错误中应返回；
6. retryable 表示是否可重试，不表示重试一定成功。
```

## 12. 错误码分类

R1 建议错误类型（与 `00-API与集成契约总览.md` §20 对齐）：

```text
validation_error；
not_found；
permission_denied；
policy_blocked；
gate_required；
gate_not_resolved；
conflict；
state_mismatch；
checkpoint_missing；
trace_missing；
audit_missing；
evidence_missing；
resource_unavailable；
model_unavailable；
integration_failed；
execution_failed；
redaction_required；
internal_error。
```

错误码规则：

```text
1. Policy 禁止必须使用 policy_blocked 或更具体错误；
2. Gate 阻塞必须使用 gate_required 或 gate_not_resolved；
3. Evidence 缺失必须使用 evidence_missing 或 evidence_insufficient；
4. Trace / Audit 缺失必须使用 trace_missing / audit_missing；
5. 状态恢复冲突必须使用 state_mismatch 或 recovery_conflict；
6. 不得将所有错误统一 internal_error；
7. 错误码不得包含敏感信息。
```

## 13. 典型错误语义

### 13.1 validation_error

适用：请求字段缺失、类型错误、格式错误、枚举值非法。

要求：

```text
1. 返回字段级错误引用；
2. 不泄露内部 schema；
3. 不用于 Policy 禁止；
4. 不用于 Gate 阻塞。
```

### 13.2 policy_blocked

适用：Policy 明确禁止操作。

要求：

```text
1. 返回 policy_refs 或 policy_check_ref；
2. retryable 通常为 false，除非策略条件可变；
3. 必须记录 Trace；
4. 高风险或关键阻塞应 Audit。
```

### 13.3 gate_required

适用：动作需要 Gate 才能继续。

要求：

```text
1. 返回 gate_ref；
2. 返回可展示 reason；
3. retryable 为 false，直到 Gate 决策；
4. 前端应展示 Gate，而不是继续重试。
```

### 13.4 gate_not_resolved

适用：Gate 存在但尚未决策，或决策未写入 Audit。

要求：

```text
1. 返回 gate_ref；
2. 返回 gate_status；
3. 不得继续执行阻塞动作；
4. resume 前必须重新校验。
```

### 13.5 evidence_missing / evidence_insufficient

适用：任务或阶段需要 Evidence，但证据缺失或不足。

要求：

```text
1. 不得标记 completed；
2. 返回 evidence_gap_refs 或 required_evidence；
3. 可提供 next_actions；
4. P5 验证中必须明确阻断。
```

### 13.6 checkpoint_missing

适用：resume 或状态恢复需要 checkpoint，但无法读取。

要求：

```text
1. 不得盲目 resume；
2. 返回 checkpoint_ref 或 missing_reason；
3. 进入 recovery_conflict 或 Gate；
4. 记录 Trace / Audit。
```

### 13.7 redaction_required

适用：响应或日志中检测到敏感信息风险。

要求：

```text
1. 原始内容不得返回；
2. 返回脱敏提示；
3. 记录安全 Trace；
4. 必要时进入 Gate 或安全处理流程。
```

## 14. 错误响应与 Gate

Gate 相关错误必须明确。

规则：

```text
1. 需要用户授权时返回 gate_required；
2. Gate 未决策时返回 gate_not_resolved；
3. Gate 被拒绝时返回 gate_rejected 或状态化为 failed / rework_required / canceled；
4. Gate 决策未 Audit 时不得 resume 高风险动作；
5. gate_ref 必须可查询；
6. 前端不得隐藏 Gate 错误。
```

## 15. 错误响应与 Trace / Audit

Trace 要求：

```text
1. validation_error 可按需 Trace；
2. policy_blocked 必须 Trace；
3. gate_required 必须 Trace；
4. execution_failed 必须 Trace；
5. model_unavailable 必须 Trace；
6. resource_unavailable 必须 Trace；
7. state_mismatch / checkpoint_missing 必须 Trace。
```

Audit 要求：

```text
1. 高风险动作失败必须 Audit；
2. Gate 决策失败或异常必须 Audit；
3. Policy 冲突必须 Audit 或进入安全审计策略；
4. 外部系统写操作失败必须 Audit；
5. 删除、不可逆、大规模修改失败必须 Audit。
```

## 16. 错误响应与前端展示

前端展示规则：

```text
1. validation_error 展示可修正字段；
2. policy_blocked 展示策略阻塞，不提示用户反复重试；
3. gate_required 展示 Gate 面板；
4. evidence_missing 展示 Evidence 缺口；
5. checkpoint_missing 展示恢复冲突；
6. redaction_required 不展示原始敏感内容；
7. internal_error 展示通用失败并保留 request_id / trace_ref。
```

前端不得：

```text
1. 将错误吞掉；
2. 将 gate_required 变成普通 toast；
3. 将 evidence_missing 变成 completed；
4. 展示明文密钥；
5. 将 mock 错误处理伪装为真实后端行为。
```
