## 0. 编写原则

```text
1. 范围基准定义"当前版本应做什么、不应做什么、什么需要前置确认"；
2. 本文不重复展开已在其他文档中详细定义的内容——引用而非复述；
3. 尚未确认的设计只能写为"推荐/待确认"；
4. 纳入当前主干的能力必须是完备、健全、可运行、可追溯的主干能力；
5. "后续逐步改进"只能指质量、体验、覆盖深度、性能，不得指主干能力缺失。
```

> 通用禁止与红线完整总表见 AGENTS.md §18；相关决策详见 01-决策记录.md；术语与风险级别（L0-L5）详见 02-术语表.md。（P 阶段晋级 Gate D-023 / Policy 优先 D-031 / Artifact 不自动晋升 D-014 / Manual-Plan-Auto D-025 等通用红线详见 AGENTS §18 + 01-决策记录）

## 1. 范围基准摘要

rebuild 当前版本的范围基准：

```text
围绕"用户拥有源代码的软件重构与迁移项目"，
建设一个可按 P0-P6 流程接入、建档、评估、规划、执行、验证和交付的平台主干。

"主干" = 流程完整 + 对象完整 + 状态完整 + Gate 完整 + Artifact/Evidence/Trace/Audit 可追溯 +
         用户能理解当前阶段/任务/产物/风险/下一步 + 关键能力真实可运行（不是文档或 UI 壳）。
```

定位：泛软件重构；场景 = 典型场景（信创切换 / 软件现代化 / 软件移植）+ 开放扩展，"包括但不限于"，准入靠三判据（D-117 / D-118）。非目标：泛 AI 办公、泛项目管理、纯咨询、通用 Agent 展示、无人自治、通用插件市场、复杂多租户。

> 详细产品定位见 `00-产品定义基准.md` §2；非目标完整清单见本文 §10。

## 2. "完备主干"与"逐步改进"的边界

> 这是本文的核心价值——草稿 v0.2 中用户明确要求的主干完备性原则。以下区分是范围判定的第一准则。

### 2.1 完备主干（不可后延）

纳入当前范围的主路径能力必须具备真实闭环：

```text
P0 接入 — 项目来源/权限/风险/接入记录/Gate 清楚
P1 建档 — 项目结构/源码/材料/配置/环境声明形成可支撑评估的档案
P2 评估 — 风险/可行性/不确定项/待确认项/评估结论可追溯
P3 规划 — Stage Plan / Task Plan(Batch) / TaskGraph / Gate / 验收方式清楚
P4 执行 — 按计划受控执行，产生 Artifact/Trace/Audit，受 Policy/Gate 管控
P5 验证 — 验证动作/结果/失败项/证据/返工建议清楚
P6 交付 — 交付包/说明/Evidence/风险与遗留项清楚
```

**不可后延的主干能力**：

```text
P0-P6 主路径真实流转 | 阶段晋级 Gate | Artifact/Evidence/Trace/Audit
NodeLoop | TaskGraph 边策略 | Policy/Hook/安全边界
Project Workspace 隔离 | 状态恢复基础 | 任务后台状态
Coding/Execution/Runtime 三状态分离 | ModelGateway 基础
资源调用风险分级 | Case 不具备执行权 | 密钥脱敏 | 历史版本只读参考
用户/项目资源优先 → rebuild 本地 → 在线社区的资源顺序
```

### 2.2 允许逐步改进（可后延）

```text
前端体验质量 | 视觉细节 | 交互效率 | 模型效果 | 提示词质量 | 测试覆盖
性能 | 错误处理细节 | 资源推荐质量 | Case/Knowledge 覆盖量
更多技术栈适配 | 更多远程资源接入 | 社区能力成熟度 | 文档功能打磨
```

### 2.3 禁止的表述

不得以这些名义后延主干能力：

```text
"第一版暂缓" | "基础款" | "占位闭环" | "后续补齐" | "体验壳即可"
"P4 先不真实执行" | "Evidence 后续再补" | "Gate 后续再补"
```

## 3. 范围判定方法

判断一个能力是否属于当前范围，按以下 9 步评估：

```text
1. 是否直接服务"软件重构与迁移"？
2. 是否围绕用户拥有源代码的项目展开？
3. 是否支撑 P0-P6 中至少一个启用阶段？
4. 是否属于 P0-P6 主干完备性的必要组成（§2.1）？
5. 是否具备 Evidence/Artifact/Trace/Audit 或 Gate 的可追溯要求？
6. 是否已在 01-决策记录.md 中 accepted？
7. 若未 accepted，是否只是推荐或待确认（而非强行写入范围）？
8. 是否会引起重大实现/权限/安全/模型/Agent/资源/目录/前端架构变化？
9. 若影响重大，是否已提交给用户确认？
```

范围内能力必须能回答：

```text
服务哪个用户场景？→ 对应哪个 P 阶段或平台基础能力？→ 是否主干完备性必要部分？
→ 产生什么 Artifact/Evidence/Trace/Audit？→ 触发什么 Gate？
→ 由哪个专题文档进一步定义？→ 是否已经用户确认？
```

## 5. 增强能力边界

P6 完成仅代表基础主流程可交付，不代表所有增强能力完成。

```text
基础主流程 = P0-P6 主干完备（§2.1 标准），不是"基础款"或"降低要求"
增强能力 = Fusion功能/远程资源调用/社区功能/文档功能（R13-R16分阶段建设合入）
```

增强能力与主干的边界：

```text
· R13 Fusion — 平台增强能力建设阶段。Fusion 在用户使用中仍是模型选项（非特殊阶段）
· R14 远程资源调用 — 首期默认只读探测；写操作需用户确认
· R15 社区功能 — 社区资源默认只读；执行前需安全/许可/审核
· R16 文档功能 — 文档晋升/审核/归档的产品化

增强能力不得提前变成 P0-P6 主链路必须完成条件（除非用户确认变更）。
但如果某项增强能力已被确认纳入主干依赖，则不得以"增强能力"名义后延。
```

## 6. 范围变更控制

以下变化必须先向用户提出推荐、理由和影响，不得直接写入 accepted 范围：

```text
· 将非目标能力纳入范围    · 新增/改变 P0-P6 定义    · 改变 R0-RN 建设顺序
· Fusion 特殊流程化        · 模型固定绑定阶段        · 新增大量固定 Agent 类型
· 改变少Agent多Skill原则   · 改变资源优先级           · 在线社区资源默认执行
· 远程高风险写操作默认执行 · 替换 LangGraph 主编排    · 改变 ModelGateway 路线
· 改变三对象模型            · 历史版本作为当前运行依赖 · Artifact 未审核晋升项目文档
· 将主干能力降格为基础款/占位/后续补齐
```

## 8. 边界检查清单

任何新文档、新设计、新任务、新施工计划，都应检查：

```text
1. 是否服务软件重构与迁移；
2. 是否围绕用户拥有源代码的项目；
3. 是否明确对应 P0-P6 或平台基础能力；
4. 是否把非目标写成目标；
5. 是否把主干降格为基础款；
6. 是否把质量改进误写成能力后延；
7. 是否新增大量 Agent；
8. 是否把 Fusion 写成特殊流程；
9. 是否把在线社区资源提前为默认执行；
10. 是否绕过用户/当前项目资源优先原则；
11. 是否绕过 Gate；
12. 是否缺少 Evidence/Artifact/Trace/Audit；
13. 是否把历史版本当当前事实源；
14. 是否需要先用户确认。
```

> 来源：原 `非目标与边界.md` §14（该文档已取消独立维护，内容合并至本文）。

## 9. 待确认项

```text
1. 典型场景（尤其信创切换）是否需要定义更细的"源栈/目标栈"范围；开放扩展场景的源栈/目标栈是否完全交由用户在场景包内定义；
2. "完备主干"的验收清单是否需要拆成逐项 Gate（进入 08-测试与验收）；
3. 增强能力 R13-R16 是否应在 R9-R12 达"基础可用"后再启动分支；
4. 资源优先级在不同任务类型下是否允许用户手动覆盖；
5. 范围变更日志是否需要独立文件（当前变更日志见 05-交接与报告规范 §11）。
```

## 11. 本文验收标准

本文达到 R1 基本可用标准，当且仅当：

```text
1. 明确"完备主干"与"逐步改进"的边界（§2），不可后延清单明确；
2. 范围判定方法可操作（§3 九步评估）；
3. 已确认核心范围以引用方式呈现，不重复展开（§4）；
4. 增强能力与主干的边界清楚（§5）；
5. 范围变更前置确认规则明确（§6）；
6. 非目标完整清单清晰（§9）；
7. 未自行新增重大设计决策；
8. 未把主干能力降格为基础款/基础循环/占位闭环；
9. 与其他文档的关系清楚（引用而非复述）。
```
