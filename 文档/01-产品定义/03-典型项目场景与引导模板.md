## 0. 产品心智：Project 是唯一用户可见主对象

### 0.1 核心裁决 [用户已确认]

```text
1. 当前版本不设独立 Mission 产品层，不建设 Mission 模板体系；
2. 用户可见主对象为 Project；
3. 单个 Project 直接按 P0-P6 推进重构/迁移/验证/交付；
4. 若需要拆分工作范围 → 优先创建多个 Project；
5. 若同一 Project 内部任务复杂 → 通过 Run / Stage Plan / Task Plan(Batch) / TaskGraph / NodeLoop 表达；
6. 已生成的 `典型场景与Mission模板.md` 标记为 superseded/废弃草稿。
```

> **关联决策**：以上裁决已写入 `01-决策记录.md` 的 D-070（当前版本不设独立 Mission 产品层，状态 accepted）。理由：避免在 Project 与 P0-P6 之间引入额外产品层，防止产品范围漂移为通用任务平台。

### 0.2 正确的心智链

```text
Project → P0-P6 → Run / Stage Plan / Task Plan(Batch) / TaskGraph → Artifact / Evidence / Trace / Audit → Gate → 交付
```

## 1. 项目拆分原则

### 1.1 应创建多个 Project

```text
源码仓库/系统边界明显不同 | 交付对象不同 | 迁移目标不同
权限边界不同 | 运行环境不同且独立 | 风险等级差异大
需要分别交付/验收/归档 | 用户希望清晰分开证据/产物/运行记录
```

### 1.2 不建议拆分（用 TaskGraph 替代）

```text
同一系统的多个模块 | 同一仓库的多个任务 | 同一迁移目标下的多批修改
同一项目的多次验证/返工 | 技术栈局部替换
```

### 1.3 不确定时

平台给出建议和理由（按源码边界/交付边界/权限边界/风险边界/运行环境边界/证据隔离需求判断），等待用户确认。

## 2. 项目引导模板通用结构

引导模板帮助用户创建 Project 时理解项目类型和引导路径。**不用于新增产品流程层。**

```text
项目场景名称    — 用户可理解
适用场景        — 适合什么项目
用户目标        — 用户期望完成什么
适用项目条件    — 需具备的基本条件（源码、配置等）
不适用情况      — 避免模板被滥用
推荐 P 阶段范围 — 通常覆盖哪些阶段（不替代裁剪判断）
关键输入类别    — 引导界面应收集的信息类别（非固定字段）
关键输出类别    — 应产生的报告/计划/产物/证据/交付物
项目拆分建议    — 是否建议拆成多个 Project
任务拆分建议    — 同一 Project 内如何通过 TaskPlan/TaskGraph 拆分
完成条件        — 怎样才算完成
```

所有场景共同遵守的原则（详见对应权威源）：

```text
资源优先级：自身→平台本地→在线社区（用户旅程 §6）
模型选择：不绑定阶段，Fusion=模型选项（用户旅程 §7.3）
Agent/Skill：少Agent多Skill（D-016~D-019）
P阶段晋级Gate：必须用户授权（D-023）
主干完备：不可后延清单（范围基准 §2.1）
```

> 通用禁止与红线完整总表见 AGENTS.md §18；相关决策详见 01-决策记录.md；术语与风险级别（L0-L5）详见 02-术语表.md。（P 阶段晋级 Gate D-023 / Policy 优先 D-031 / Artifact 不自动晋升 D-014 / Manual-Plan-Auto D-025 等通用红线详见 AGENTS §18 + 01-决策记录）

## 3. 典型项目场景

### 场景 A：完整信创迁移项目

端到端信创迁移：接入→建档→评估→规划→执行→验证→交付。

**P 阶段**：P0-P1-P2-P3-P4-P5-P6（完整）。不后延 P4/P5/Evidence/Trace/Audit/Gate。

**关键输入**：项目来源、源码路径/仓库、迁移目标、当前运行方式、已有文档/配置、用户约束、执行模式倾向、模型/资源配置。

**关键输出**：接入记录、项目档案、评估报告、迁移方案、Stage Plan、Task Plan(Batch)、TaskGraph、Artifact、Evidence、Trace/Audit、验证报告、交付包、交付说明、风险与遗留项。

**完成条件**：交付包+说明+Evidence+Artifact+Trace/Audit+验证结论+遗留风险+用户P6 Gate。

---

### 场景 B：迁移评估项目

只判断可行性/风险/工作量，不进入执行。

**P 阶段**：P0-P1-P2。是否进入 P3 必须用户确认。

**关键输出**：接入记录、项目档案、评估报告、风险清单、阻塞项、不确定项、是否建议进入规划的建议+Evidence。

**完成条件**：评估报告完成、风险/阻塞项/待确认项清晰、Evidence可追溯、用户确认是否进入P3或结束。

---

### 场景 C：迁移规划项目

已有档案/评估结果，形成方案+计划+TaskGraph。

**P 阶段**：P0-P1-P2-P3。已有可信档案和评估时可引用，但不得伪装未执行阶段为completed。

**关键输出**：迁移方案、Stage Plan、Task Plan(Batch)、TaskGraph、风险级别、权限边界、Gate计划、验收方式。

**完成条件**：用户确认方案+计划+任务边界、TaskGraph和Gate计划完整、进入P4前置条件明确。

---

### 场景 D：按计划受控执行项目

已有确认计划，执行受控修改。

**P 阶段**：P0-P3确认-P4-P5。缺少可信计划→先入P3。

**关键输出**：Patch、修改说明、执行记录、Trace/Audit、Artifact、中间验证结果、失败和返工建议。

**边界**：不得绕过Policy/Gate、不得执行未授权高风险动作、不得Case当执行能力、不得社区资源默认执行。

**完成条件**：计划内任务执行结果清楚、Artifact+Trace/Audit完整、失败项+返工建议清楚、用户确认是否进入下一阶段。

---

### 场景 E：验证与交付整理项目

已有执行产物，验证是否可交付并整理交付包。

**P 阶段**：P0-P5-P6。执行产物来源不可信或缺Trace/Audit→先回P4或P3。

**关键输出**：验证报告、失败项、返工建议、交付包、交付说明、Evidence、遗留风险、后续建议。

**完成条件**：验证证据完整、交付包完整、风险与遗留项清楚、用户P6 Gate、未通过项不伪装为通过。

---

### 场景 F：局部技术栈替换项目

局部技术栈/依赖/配置/组件替换——属重构范围但不扩大为任意技术改造。

**P 阶段**：P0-P1-P2-P3-P4-P5-P6（或裁剪，但不得跳过必要Gate/Evidence/验证）。

**边界**：不得扩大到全项目无边界重构、不得未经评估替换核心依赖、不得绕过测试/Gate、不得把社区示例直接变Patch。

---

### 场景 G：项目建档与理解项目

先让平台理解项目结构，不立即进入迁移。

**P 阶段**：P0-P1。是否进入P2必须用户确认。

**关键输出**：源码结构摘要、文档索引、依赖清单、配置清单、Environment Profile草案、初始风险、建档Evidence。

**边界**：不得把建档结果直接当迁移方案、不得把未验证推断写成事实、不得全量塞入上下文。

---

### 场景 H：迁移返工/修复项目

针对已有验证失败项或验收反馈进行修复。

**P 阶段**：P0-P2(问题复核)-P3(修复计划)-P4-P5-P6。问题明确可裁剪P1/P2但不跳过计划/执行/验证/证据。

**关键输出**：问题复核结论、修复计划、修复产物、验证报告、遗留风险、返工记录、新Evidence/Trace/Audit。

**完成条件**：返工范围清楚、修复产物可追溯、验证证据完整、失败项关闭或明确遗留、用户确认交付或继续返工。

## 4. 反例：以下不是合格项目模板

```text
· 帮我看看这个系统怎么样
· 自动把项目全部迁好，不用问我
· 直接用网上的方案改代码
· 跳过测试，给我交付报告
· 根据模型判断直接通过验收
· 没有源码也做完整迁移
· 把 Fusion 跑一遍流程
· 让每个阶段都开一个新 Agent
· 在 Project 下再创建 Mission 来跑流程
```

这些请求可转化为合格引导，但必须补齐：项目来源、用户目标、适用P阶段、权限边界、资源来源、风险等级、Gate、Artifact/Evidence/Trace/Audit、完成条件。
