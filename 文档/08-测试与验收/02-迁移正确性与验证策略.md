## 1. 为什么这是核心问题

迁移工具的真正壁垒不在"能不能改代码"，而在"**改完之后，怎么证明它还是对的**"。

```text
用户的真实诉求：迁移后系统行为不变（或变化可控、可解释），且能继续运行与维护。
平台若不能证明正确性，迁移结果就不可信，再多自动化也无价值。
```

本文回答：rebuild 用什么证据、什么方法、在哪个阶段，证明迁移正确性。

> 原则承接：`No Evidence, No Decision. No Trace, No Trusted Result.`（00-项目总览 §9.2）

## 2. 正确性的分层定义

迁移"正确"不是单一概念，按强度分层（按项目能力逐层达成，缺失层须显式登记）：

```text
L-构建正确：迁移后能在目标环境成功构建 / 编译 / 打包。
L-启动正确：服务 / 程序能在目标环境启动、依赖可解析、基本健康检查通过。
L-测试正确：原有测试保留可运行且通过；关键缺测路径补充测试后通过。
L-行为等价：相同输入下关键行为 / 输出与迁移前一致，或差异被显式登记并由用户确认。
L-非功能可接受：性能、资源、安全等非功能指标在可接受范围（或差异已确认）。
```

> **口径校正（2026-09-07，`Q-R20-1-10`，R20-4 真跑证据驱动）**：L-构建正确原写"目标（**信创**）环境"。D-117 把定位扩为**泛软件重构**后，该括注把一个**通用**正确性层级窄化成了信创专属，故删去。
> **证据（不是凭推断改）**：R20-4 现代化跑 `run-390ba1` 在**非信创**目标环境（`net8.0` + `Microsoft.Data.SqlClient 5.2.2`）真实达成 L-构建正确 —— 容器内 `dotnet restore` + `dotnet build -warnaserror` 全绿、`exit_code=0`、`diagnostics=[]`、`build_verified=validated`（宿主无 dotnet SDK ⇒ 必然容器内执行）。⇒ **L-构建正确对非信创目标同样成立且已实测兑现**，原括注是事实错误而非仅措辞偏窄。
> 五个层级本身（构建/启动/测试/行为等价/非功能）与场景无关，**不随场景增减**；**随场景变化的只有各层的具体判定细则**（如信创栈的字符集/排序规则中文往返验证），那部分见本文 §末待确认项与各场景包 `SKILL.md`。
> 本文另有三处信创相关表述（`:13` 等价判定细则待校准 / `:98` "信创源常无法在平台跑原始"举例 / `:124` 待确认项），均为**有界举例或显式待校准项、不含无条件断言**，本次未改，已登记备查。

> 任一层未达成，不得笼统标记"迁移完成"；缺失层进入 P5 验证报告的"未验证 / 风险"清单。

## 3. 验证证据槽位（P5 必备）

P5 验证阶段必须产出以下证据槽位（对应 D-066 执行约束）：

| 槽位 | 内容 | 证据形式 |
|---|---|---|
| 构建证据 | 目标环境构建日志、产物清单 | Evidence + Trace |
| 启动/运行证据 | 启动日志、健康检查、冒烟结果 | Evidence + Trace |
| 测试证据 | 迁移前后测试集、通过率、新增测试 | Artifact + Evidence |
| 回归对比 | 迁移前后行为/输出对比、差异清单 | Evidence |
| 差异登记 | 已知行为差异 + 原因 + 用户确认 | Audit |
| 未验证清单 | 无法验证的部分及原因 | 验证报告 |

证据不足时的写法（承接 05 §12.2）：
**"证据不足，当前只能作为推断或建议，不能标记为验证通过。"**

## 4. 验证方法与能力接入

### 4.1 确定性优先、LLM 补长尾

```text
1. 能用确定性手段证明的（构建/测试/diff/静态检查/等价比对），优先用确定性能力；
2. 确定性无法覆盖的长尾（语义等价判断、风险解释、缺测路径设计），由 LLM / Expert Agent 辅助，但产出须落到可验证证据上；
3. LLM 的判断不自动等于验证通过（呼应 D-035 Fusion、D-031 Policy 优先）。
```

### 4.2 能力以资源形式接入（承接 D-063）

验证相关确定性能力作为 Skill / Tool / Expert Agent / MCP 接入 `平台资源/`，例如：

```text
- 构建/测试执行器（Tool，受 ExecutionProvider + Hook + Policy 约束）
- diff / 行为对比器（Tool / Skill）
- 等价性检查、静态分析（Tool / 确定性 Skill）
- 测试生成 / 缺测识别（Expert Agent + Skill）
- 回归基线管理（Skill）
```

风险分级按 D-042（L0 只读分析 … L3 外部系统写），授权按执行模式与 Risk Level 处理。

## 5. 验证在 P/R 阶段中的位置

```text
P1 建档：**捕获原始源码验收基准（回归基线/特征化测试）**（D-106，2026-07-20）——原始行为/测试是第一类项目事实：①盘点已有测试+断言解读（采集）②LLM 识别缺测路径+设计/生成特征化测试规格 ③原始可跑时捕获黄金输出（采集/verify），不可跑则诚实 evidence_gap（信创源常无法在平台跑原始，可经 R14 远程/延后补齐，不伪造）。
P2 评估：识别"可验证性"风险——哪些部分难以验证，提前登记；定义验收标准（承 §2 五层）。
P3 规划：把验证策略纳入方案（每类改造对应什么验证手段、验证证据如何获取）；把"补齐/运行原始基线"纳入 TaskGraph。
P4 执行：执行同时产出可供验证的中间证据（构建/测试/Trace）。
P5 验证：按本文证据槽位逐层验证，**以 P1 原始基线做行为等价/回归对比**，输出验证报告与差异登记。
P6 交付：交付包必须包含验证结论与剩余风险。

R 阶段落地：R5 接入构建/测试/模型相关验证能力；R11（P4 执行链路）产出可验证中间态；
R12（P5-P6）打通验证与交付链路并按本文校准；**R17.5 P1 阶段重构纳入 baseline capture（D-106）**。
```

## 6. 与"测试"的区别

```text
测试（testing）：手段之一——运行用例、检查结果。
验证（verification）：更广——证明迁移正确性的整体证据体系，含构建/启动/测试/回归/差异/非功能。
本文是验证策略；具体测试计划、用例、回归检查清单是其子集，进入 08-测试与验收 其余文档。
```
