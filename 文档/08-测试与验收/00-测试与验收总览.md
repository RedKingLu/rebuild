## 1. 测试与验收目标

测试与验收体系目标是让 rebuild 的每一阶段、每一模块、每一次交付都能被清楚判断：

```text
1. 做了什么；
2. 是否真实实现（还是仅为体验壳或 mock）；
3. 是否有可重复验证的方法；
4. 是否有 Evidence 支撑（详见 02-术语表 第九部分）；
5. 是否有 Trace 可追溯（详见 02-术语表 第九部分）；
6. 高风险动作是否有 Audit（详见 02-术语表 第九部分）；
7. Gate 是否按规则触发和决策（详见 02-术语表 第八部分）；
8. 安全与脱敏是否符合红线；
9. 是否满足进入下一阶段或交付的条件。
```

验收体系不是只看"功能能点开"，而是同时检查：产品流程、真实能力、迁移正确性、证据链、安全链路、状态恢复、用户体验、文档一致性和可持续演进。

## 3. 验收层级

R1 建议验收层级：

```text
L0 文档一致性验收；
L1 静态结构验收；
L2 单元 / 组件级验收；
L3 API / 契约验收；
L4 前后端联调验收；
L5 主链路验收；
L6 安全与权限验收；
L7 迁移正确性验收（详见本目录 02-迁移正确性与验证策略.md）；
L8 用户体验验收；
L9 发布冻结验收。
```

规则：

```text
1. 低层级通过不代表高层级通过；
2. API 契约通过不代表主链路通过；
3. 前端体验通过不代表真实能力通过；
4. 主链路通过不代表迁移正确性通过；
5. 迁移正确性缺证不得标记 completed（D-066）；
6. 发布冻结必须汇总所有必要证据。
```

R 阶段验收关注：

```text
R0：历史版本归档与目录骨架；
R1：基本可用文档基线；
R2：文档完善、独立审核与验收；
R3：前端主干与体验壳（必须标记 mock / 未接真实服务）；
R4：基础工程骨架与 API 契约落地（开始替换建议契约为实现契约）；
R5：模型网关与模型策略；
R6：Agent / Skill / 资源基础；
R7：集成与项目接入；
R8：工作区真实化；
R9：P0-P1 最小真实链路；
R10：P2-P3 评估与规划链路；
R11：P4 执行链路；
R12：P5-P6 验证与交付；
R13：Fusion 功能开发及合入；
R14：远程资源调用开发及合入；
R15：社区功能建设及合入；
R16：文档功能建设及合入；
R17：全量联调、体验打磨与发布冻结。
```

规则：

```text
1. R 阶段验收不得混用 P 阶段完成状态；
2. R3 体验壳必须标记 mock / 未接真实服务；
3. R4 起需要逐步替换建议契约为实现契约；
4. R9-R12 必须按 P0-P6 主链路逐步形成真实证据；
5. R17 必须检查 mock 是否替换或显式保留；
6. 每个 R 阶段验收必须有报告或记录。
```

## 5. P0-P6 产品流程验收总览

P0-P6 是面向用户项目的可裁剪产品流程。阶段契约详见 `文档/03-流程与运行时/01-P0-P6阶段契约.md`。

阶段验收关注：

```text
P0 接入：源码接入、项目边界、Workspace 初始状态；

P2 评估：迁移范围、风险、依赖、改造点；

P4 执行：命令 / Tool / MCP / Git / 写盘真实执行链路；
P5 验证：构建、运行、测试、回归、等价或差异登记证据（详见本目录 02-迁移正确性与验证策略.md）；
```

```text
6. P5 验证证据不足不得 completed（D-066）；
7. P6 完成只代表基础主流程可交付，不代表增强能力全部完成。
```

## 6. 迁移正确性验收

迁移正确性是产品核心验收项，完整定义与证据槽位见本目录 **`02-迁移正确性与验证策略.md`**（D-066 详述源）。

本文仅列出验收要点：

```text
正确性分层：L-构建正确 → L-启动正确 → L-测试正确 → L-行为等价 → L-非功能可接受；
P5 证据槽位：构建证据、启动/运行证据、测试证据、回归对比、差异登记、未验证清单；
任一层未达成不得笼统标记"迁移完成"。
```

规则：

```text
1. P5 不得以"看起来完成"或"代码就绪"通过；
2. 验证必须有 Evidence，必须可 Trace；
3. 验证不通过或证据不足时不得 completed；
4. 差异必须显式登记，接受风险必须写 Audit；
5. 具体验证器、阈值、信创目标栈等价判定细则待 R5/R11/R12 校准（详见 02-迁移正确性与验证策略.md）。
```

## 7. Evidence 验收

Evidence 验收关注证据是否足以支撑 claim、阶段完成和交付结论。Evidence 完整定义见 `02-术语表.md` 第九部分。

检查项：

```text
Evidence 是否关联 claim；
Evidence 是否有来源和验证状态；
Evidence 是否有 Trace；
Evidence 是否存在缺口（Evidence Gap 必须可见）；
Evidence candidate 与 Evidence validated 是否区分；
Evidence 是否被错误地从 Artifact 自动晋升；
Evidence 是否脱敏。
```

规则：

```text
1. Evidence candidate 不得显示为 validated；
2. Artifact 不自动成为 Evidence；
3. 模型输出不自动成为 Evidence；
4. 资源输出不自动成为 Evidence；
5. No Evidence / No Trace 不得 trusted result。
```

## 8. Trace 验收

Trace 验收关注执行过程是否可追溯。Trace 完整定义见 `02-术语表.md` 第九部分。

检查项：

```text
Run / Stage / Node 状态变化；
模型调用、资源调用、命令执行；
Tool / MCP 调用；
文件写入、Git 操作；
Gate 决策、Audit 写入；
错误和阻断、脱敏事件。
```

规则：

```text
1. Trace 缺失必须可见；
2. Trace 不等于 Evidence，Trace 不证明结果正确；
3. Trace 不得包含密钥；
4. Trace 写入失败不得静默；
5. 状态恢复不得依赖终端或前端 UI。
```

## 9. Audit 验收

Audit 验收关注关键决策和高风险动作是否可审计。Audit 完整定义见 `02-术语表.md` 第九部分和 `文档/07-安全与权限/05-Audit审计规范.md`。

必须检查：

```text
P 阶段晋级 Gate；
高风险动作（L4/L5，详见 02-术语表 第七部分）；
外部系统写操作、Git remote write；
高风险 Tool / MCP；
Policy blocked 高风险事件；
Evidence Gap 风险接受；
凭据状态变更；
Audit 写入失败。
```

规则：

```text
1. Gate 决策必须有 Audit；
2. 高风险动作必须有 Audit；
3. Audit 缺失必须可见；
4. Audit 不等于用户授权本身，Audit 不等于 Evidence；
5. Audit 不得包含密钥。
```

## 10. Gate / Authorization 验收

Gate / Authorization 验收关注授权是否按规则阻塞和恢复。Gate 完整定义见 `02-术语表.md` 第八部分和 `文档/03-流程与运行时/04-Gate与中断恢复流程.md`。

检查项：

```text
P 阶段晋级 Gate；
Stage Plan / Task Plan / Task Plan Batch Gate；
高风险动作 Gate、写盘 Gate、Patch apply Gate；
Git remote write Gate、外部系统写操作 Gate；
Evidence Gap Gate；
Policy blocked 展示；
Gate 决策 Audit；
Gate 后状态刷新。
```

规则：

```text
1. Gate 不得只显示 toast；
2. Gate 未决策不得继续执行；
3. Policy blocked 不得提供批准继续；
4. L5 必须用户 Gate（详见 02-术语表 第七部分）；
5. P 阶段晋级必须用户授权；
6. Gate resolved 必须以后端状态为准。
```

## 11. API / SSE 验收

API / SSE 验收关注建议契约向实现契约的落地情况。API 契约详见 `文档/05-API与集成契约/`。

API 检查项：

```text
字段是否存在、语义是否一致；
错误码是否可映射前端；
Gate / Policy / Risk / Trace / Audit 引用是否可查询；
redaction_status 是否可见；
mock 字段是否显式；
R1 建议契约是否在 R2/R4 校准。
```

SSE 检查项：

```text
事件是否触发；
事件是否只作为刷新提示（非唯一状态源）；
断线恢复是否重新查询；
事件 payload 是否脱敏；
resync_required 是否生效；
mock SSE 是否标记。
```

规则：

```text
1. SSE 不是唯一状态源；
2. 浏览器缓存不是事实源；
3. 事件缓存不能作为授权事实源；
4. 错误响应不得泄露密钥；
5. API 实现与文档冲突时必须登记并校准。
```

检查项：

```text

日志 / 前端 / Trace / Audit / 导出是否脱敏；

模型上下文是否不含密钥；
redaction_required 是否不可绕过。
```

规则：

```text

2. Policy 可绕过为阻断级缺陷（P0）；
3. L5 未 Gate 为阻断级缺陷（P0）；

```

R1 建议缺陷分级：

```text
P0 阻断：违反安全红线、核心链路不可用、证据链断裂但显示完成、密钥泄露、Policy 可绕过、L5 未 Gate；
P1 关键：主链路功能失败、Gate / Evidence / Trace / Audit 关键缺失、状态恢复错误、真实能力误标；
P2 重要：体验误导、错误文案不清、部分 API 字段缺失、非核心链路异常；
P3 一般：样式、低影响文案、非阻塞展示问题；
P4 建议：体验优化、长期增强建议。
```

处理规则：

```text
1. P0 不得通过验收；
2. P1 原则上不得发布冻结，除非用户明确裁决并登记风险；
3. P2 必须有修复计划或延期裁决；
4. P3 / P4 可纳入后续优化；
5. 所有缺陷必须有证据、复现路径和归属阶段。
```

## 16. 验收报告规范

验收报告建议包含：

```text
验收对象、验收范围、事实源；
测试方法、测试环境、执行记录；
通过项、失败项；
缺陷分级；
Evidence 引用、Trace 引用、Audit 引用；
Gate 状态；
安全脱敏检查；
结论、待确认项、下一步建议。
```

规则：

```text
1. 报告不得包含密钥；
2. 报告不得把推断写成事实；
3. 报告不得隐藏失败；
4. 报告不得用"基本可用"掩盖 P0/P1；
5. 报告必须区分 mock 与真实能力；
6. 报告应可供独立 Agent 复核。
```

---

## 17. 独立验收 Agent 规则

独立验收 Agent 应遵守：

```text
非迎合式评审（详见 AGENTS.md §6.4）；
先查事实源；
区分事实、推断和建议；
不因用户期望弱化风险；
不隐藏缺陷；
不把 mock 当真实；
不把代码存在当功能可用；
不把命令成功当业务完成；
不泄露密钥；
输出可复核报告。
```

独立验收 Agent 不得：

```text
1. 修改被验收对象后再宣布通过，除非验收范围明确允许；
2. 用历史事实替代当前事实；
3. 跳过 Evidence / Trace / Audit 检查；
4. 将未确认项后延不登记；
5. 迎合式给出通过结论。
```

## 18. 状态与完成判定

完成状态必须以后端事实源、Evidence、Trace、Audit 和 Gate 决策共同判断。

不得作为完成事实源：

```text
前端本地状态、浏览器缓存、SSE 事件缓存；
终端窗口状态、容器状态；
模型输出、Artifact 生成；
Audit 存在（不等于授权）、Trace 存在（不等于正确）；
用户口头说"可以了"。
```

规则：

```text
1. completed 必须有明确后端状态；
2. P 阶段 completed 必须满足阶段完成条件；
3. P5 completed 必须有验证证据（D-066）；
4. Gate 未决策不得 completed；
5. Evidence 不足不得 completed；
6. Trace / Audit 缺失时不得显示可信完成。
```

## 19. Mock 与真实能力验收

R3 可先建设体验壳，但验收必须标记能力状态。

能力状态标记：

```text
真实可用；
真实可用但受限；
已配置未验证；
未接真实服务；
Mock 数据；
静态演示；
只读参考；
被 Policy 阻断；
等待 Gate。
```

规则：

```text
1. mock 不得验收为真实能力；
2. static_demo 不得验收为真实能力；
3. not_connected 不得验收为真实能力；
4. 体验壳可以通过 R3 体验壳验收，但不得通过真实链路验收；
5. R17 必须检查 mock 是否已替换或显式保留；
6. 用户验收需清楚知道哪些能力真实可用。
```

## 20. 发布冻结验收

发布冻结前必须检查：

```text
R 阶段必要项是否完成；
P0-P6 基础主链路是否完成；
P5 验证证据是否齐备（详见本目录 02-迁移正确性与验证策略.md）；
P6 交付材料是否齐备；
Gate / Evidence / Trace / Audit 链路是否完整；
安全与脱敏是否通过；
mock / not_connected 是否处理；
P0/P1 缺陷是否清零或裁决；
文档是否与实现一致；
用户与 Copilot 是否完成最终审核。
```

规则：

```text
1. 发布冻结不得带 P0 缺陷；
2. 发布冻结不得带未裁决 P1；
3. 密钥泄露必须阻断发布；
4. 迁移正确性缺证必须阻断发布（D-066）；
5. 关键 Gate / Audit 缺失必须阻断发布；
6. mock 未标记必须阻断发布。
```

## 22. 测试与验收红线

```text
1. 不得将测试通过等同于产品验收通过；
2. 不得将代码就绪等同于 P5 验证通过；
3. 不得将模型调用成功、命令 exit_code=0、Tool 执行成功等同于业务完成；
4. 不得将 Artifact 生成等同于 Evidence validated；
5. 不得将 Trace 存在等同于结果可信；
6. 不得将 Audit 存在等同于用户授权或验收通过；
7. 不得将 Gate 未决策状态显示为已通过；
8. 不得将 mock / 静态演示 / 未接真实服务显示为真实能力；
9. 不得在测试日志、验收报告、截图、Trace、提交或交接材料中泄露密钥；
10. 不得隐藏 Evidence Gap；
11. 不得隐藏 Trace / Audit 缺失；
12. 不得隐藏 P0/P1 缺陷；
13. 不得将被裁剪阶段显示为 completed；
14. 不得使用旧 Phase / 旧 F0-F6 / 旧 S0-S7 作为当前主流程；
15. 不得引入 Mission 产品层；
16. 不得在长期 API、DB、路由、组件、状态字段中固化 V26.1；
17. 不得把 R1 建议契约伪装为实现契约。
```

> 通用禁止与红线完整总表见 AGENTS.md §18；相关决策详见 01-决策记录.md；术语与风险级别（L0-L5）详见 02-术语表.md。
