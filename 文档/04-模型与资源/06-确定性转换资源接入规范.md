## 1. 确定性转换的接入形态选择

> D-063 定义了 4 种接入形态。本文展开每种形态的选择指南。

### 1.1 以 Skill 接入

**适合**：转换方法说明、操作步骤、规则选择流程、多工具组合流程、验证清单。Skill 描述"如何转换"但不直接执行——执行仍由 Agent/NodeLoop 调用 Tool/MCP 完成。

### 1.2 以 Tool 接入

**适合**：AST/codemod 可执行工具、批量替换、差异比对、测试生成器、静态检查器、Patch 生成器。Tool 是主要的转换执行载体。必须有输入输出契约、风险级别、权限边界和 Trace。

### 1.3 以 Expert Agent 接入

**适合**：需要专业判断的转换方案选择、复杂迁移风险分析、多工具组合建议、转换失败原因分析、等价性风险解释。Expert Agent 辅助决策——不是最终验收主体。

### 1.4 以 MCP 接入

**适合**：外部转换服务、外部扫描器、外部测试平台、外部代码分析、远程知识或规则库。MCP 涉及外部系统写操作时必须 Gate。

### 1.5 形态选择速查

| 需求 | 推荐形态 | 关键约束 |
|---|---|---|
| 定义转换步骤/规则 | Skill | 不直接执行，由 Agent 调用 |
| 执行 AST/codemod/比对 | Tool | 必须有输入输出契约 + Trace |
| 选方案/判风险/解失败 | Expert Agent | 非验收主体 |
| 外部转换服务 | MCP | 外部写必须 Gate |

## 2. 确定性转换特有的接入字段

> 通用 Registry 字段由 R4 定义（见 04 §1）。确定性转换资源在通用字段基础上，额外需要以下概念级信息：

```text
converter_type          — 转换器类型（ast/codemod/diff/equiv_check/test_gen/scanner）
supported_languages     — 支持的语言
supported_file_patterns — 支持的文件模式
write_scope             — 写入范围（none/dry_run/patch_draft/workspace/external）
dry_run_supported       — 是否支持 dry-run
rollback_supported      — 是否支持回滚
idempotency_note        — 幂等性说明
```

> R4/R6 校准：具体字段定义和存储由 R4 数据建模和 R6 资源基础施工时落实。dry_run_supported/rollback_supported 不得虚标——必须经过验证。

## 3. Patch 与写盘边界（6 级优先级）

这是确定性转换最关键的约束——写盘操作的逐级升级路径。

### 3.1 优先级（从低风险到高风险）

```text
Level 1 — 只读分析        → 分析代码，不产生任何文件变更
Level 2 — dry-run         → 模拟转换，输出变更预览但不写盘
Level 3 — 生成 Patch 草案  → 生成 Patch 文件，由用户或 Agent 审核后决定是否应用
Level 4 — 应用 Patch      → 在受控 Workspace 内应用 Patch（需 Task Plan 授权）
Level 5 — 受控写盘        → 批量修改文件（需 Gate，write_scope 必须明确）
Level 6 — 外部写操作      → 写入远程仓库/工单/第三方系统（需 Gate + Audit）
```

### 3.2 升级规则

```text
1. Level 1-2：Policy/Hook 检查即可——不需要 Gate
2. Level 3：生成 Patch 草案是默认推荐路径——安全且可逆
3. Level 4：需要 Task Plan 授权 + write_scope 校验
4. Level 5：必须 Gate（大规模修改/批量文件）
5. Level 6：必须 Gate + Audit（外部系统）
6. 删除或不可逆操作：无论规模，最低 Level 5 处理，必要时 Level 6
```

### 3.3 写盘后必须

```text
1. 生成 Trace（changed_files + patch_ref + write_scope）
2. 支持验证或说明无法验证的原因
3. 外部写操作必须 Audit
4. Patch 必须可追踪到转换规则和输入文件
```

## 4. 确定性转换 × P4 / P5 关系

### 4.1 P4 执行阶段

P4 可调用确定性转换资源执行迁移/重构任务。

```text
调用前提：
1. 必须基于已批准 Task Plan/TaskGraph
2. 必须检查转换资源的适用范围（语言/框架/文件类型）
3. 优先 dry-run 或生成 Patch 草案，再在授权下应用

必须记录：
输入文件和转换规则 → 变更文件和 Patch → Trace → Audit（如 L3+）

失败处理：
转换失败 → 进入返工或失败路径；P4 完成 ≠ P5 验证通过
```

P4 交给 P5 的产出：Patch、变更文件列表、转换报告、Trace/Audit、自验证结果、待验证项。

### 4.2 P5 验证阶段

P5 可调用确定性验证资源证明正确性。可调用：构建验证、测试生成器、回归基线对比、差异比对、关键行为等价检查、静态分析、兼容性检查。

```text
硬约束：
1. P5 不得以"看起来完成"通过
2. P5 必须基于可验证 Evidence——构建成功/运行可达/测试保留/回归对比/关键行为等价
3. 确定性验证输出仍需进入 Evidence 流程——不是自动 validated
4. 验证不通过或 Evidence 不足 → 不得标记 completed → 返工路径
```

## 5. 与 LLM 的协作边界

确定性转换与 LLM 的互补关系：

```text
确定性转换          LLM
──────────────    ──────────────
处理可规则化部分    补长尾
可重复/可追踪      不确定性/概率性
输出=Patch/报告    输出=建议/解释
```

协作规则：

```text
1. 优先用确定性转换处理可规则化、可重复、可追踪的部分
2. LLM 辅助分析长尾、生成建议、解释失败、补充复杂迁移判断
3. LLM 输出不得直接成为 Evidence（与 01 §12 一致）
4. LLM 不得批准确定性转换写盘——写盘授权必须走 Policy/Gate
5. LLM 不得降低风险级别
6. 二者均遵守 Policy/Gate/Audit——输出均回到 NodeLoop/TaskGraph
```

```text

R12（P5-P6）：差异比对/等价检查等是否支撑 P5 Evidence；验证失败是否进入返工；P6 交付能否索引转换 Trace
```

## 7. 红线

```text
1. 不得把确定性转换设计为独立主线引擎（D-063）
2. 不得让确定性转换绕过统一资源调用流程/Registry/TaskGraph/NodeLoop
3. 不得让确定性转换绕过 Policy/Gate/Audit
4. 不得无 Trace 执行转换
5. 不得无 Gate 执行 L5 高风险转换
6. 不得将转换成功直接标记为 P5 验证通过
7. 不得将转换输出自动标记为 Evidence validated
8. 不得默认执行社区转换器
9. 不得直接复用历史 archive 转换脚本为 active Tool
10. 不得虚标 dry_run_supported / rollback_supported
11. 不得泄露 Key/Token/Secret/Password
12. 不得引入 Mission 产品层
```

> 通用禁止与红线完整总表见 AGENTS.md §18；相关决策详见 01-决策记录.md；术语与风险级别（L0-L5）详见 02-术语表.md。
