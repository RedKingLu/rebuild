## 2. 基础能力与增强能力的划分

### 2.1 基础能力

基础能力是支撑 P0-P6 主链路闭环的必要能力，不得以后续增强为名后延。

基础能力包括：

```text
项目创建；
本地目录接入；
ZIP 接入；
Git 接入；
GitHub 接入；
Project Workspace；
Environment Profile 基础声明；
Execution Session 基础执行；
命令执行基础能力；
构建/测试/运行基础链路；
外部执行器候选接入边界；
Tool/MCP/Expert Agent 资源登记基础；
Policy/Gate/Audit/Trace；
Artifact/Evidence candidate；
P5 验证证据槽位；
P6 交付材料脱敏。
```

### 2.2 增强能力

增强能力是在基础闭环可用后深化的能力。

增强能力包括：

```text
Fusion 功能开发及合入；
远程资源调用增强；
社区功能建设及合入；
文档功能建设及合入；
token/成本预算增强；
资源推荐；
资源市场化；
高级专家 Agent 编排；
高级 MCP 生态；
跨项目资源复用；
复杂远程资源安全策略；
更细粒度成本治理；
高级文档检索、对齐、差异分析。
```

## 3. R13-R16 增强顺序

当前增强顺序为：

```text
R13：Fusion 功能开发及合入；
R14：远程资源调用开发及合入；
R15：社区功能建设及合入；
R16：文档功能建设及合入。
```

执行说明：

```text
1. 该顺序用于当前版本增强能力排序；
2. 如后续发现文档功能、远程资源安全、社区审核或 Fusion 模型体系对前置阶段产生阻塞，可提出变更申请与理由；
3. R13-R16 不得成为 R7/R8/R11/R12 基础能力缺失的借口；
4. 增强能力进入实现前必须先确认基础能力已经真实可用或明确其依赖关系。
```

## 4. Fusion 边界

> **上游详述源**：`02-Fusion作为模型能力.md`。Fusion 是什么、怎么融合、输出格式见 02。本文只定义它不是什么、边界在哪。

Fusion 是模型能力或模型策略。

可做：

```text
多模型结果融合；
模型输出比较；
模型置信度辅助判断；
模型策略选择；
复杂问题多视角分析；
候选方案排序建议；
验证报告辅助总结。
```

不得做：

```text
1. 不作为独立产品阶段；
2. 不作为特殊流程；
3. 不作为特殊评审引擎；
4. 不作为独立运行时角色；
5. 不绕过 Policy/Gate/Audit；
6. 不自动等于授权；
7. 不自动等于验收通过；
8. 不替代 P5 验证证据。
```

Fusion 与 P0-P6 的关系：

```text
P1：可辅助建档摘要；
P2：可辅助风险分析；
P3：可辅助方案比较；
P4：可辅助执行建议；
P5：可辅助验证报告分析，但不替代证据；
P6：可辅助交付摘要，但不替代交付 Gate。
```

## 5. 远程资源调用增强边界

远程资源调用增强不同于基础远程环境和 Execution Session。

基础能力应包括：

```text
Environment Profile 基础声明；
Execution Session 基础创建；
命令执行；
构建；
测试；
运行；
输出脱敏；
Trace/Audit。
```

增强能力可包括：

```text
更多远程 Provider；
托管 Runner；
跨机器资源调度；
远程资源池；
远程资源配额；
复杂网络策略；
远程资源审计增强；
高级连接诊断；
跨项目远程资源复用。
```

红线：

```text
1. 不得把基础命令执行后延到 R14；
2. 不得把基础 Environment Profile 后延到 R14；
3. 不得把基础 Execution Session 后延到 R14；
4. 不得将远程连接成功写成环境验证通过；
5. 不得绕过远程资源安全策略。
```

## 6. 社区功能边界

> **上游详述源**：`04-平台资源与Registry规范.md`。社区资源分类、登记、来源信任等级见 04。本文只定义社区资源的默认约束与增强方向。

社区功能用于资源共享、案例沉淀和生态扩展，但默认不是执行能力。

社区资源包括：

```text
Case / Skill / Template / Tool / MCP /
Expert Agent / Knowledge / Example / Best Practice
```

默认规则：

```text
1. 社区资源默认只读参考；
2. 社区 Case 不具备执行权；
3. 社区 Skill 进入执行前必须审核；
4. 社区 Tool/MCP 进入执行前必须经过安全、许可、权限和审核流程；
5. 社区资源输出不自动成为当前事实；
6. 社区资源不得默认进入项目 Workspace 写盘。
```

社区功能增强可包括：

```text
资源上传 / 审核 / 评分 / 引用 / 适配 /
版本管理 / 权限 / 安全扫描 / 使用记录 / 跨项目经验复用
```

> **R15-4-C0 修订执行注（2026-07-09，用户裁决 Q-R15-1 / Q-R15-2，覆盖上述「审核」口径）**：
> 本节默认规则第 3/4 条「社区 Skill/Tool/MCP 进入执行前必须（平台内）审核」的口径，在 R15 阶段被以下裁决修订，以 `01-决策记录.md` D-061 修订执行注为准：
> 1. 社区资源合格性由**发布侧**保证，平台内**不设资源审核状态机**；平台内统一为**启用 / 禁用 / 软删除**。
> 2. 资源**动作**风险仍统一走既有 **L1-L5**（资源启用免审核 Gate；高危动作层仍按 L1-L5 触发动作 Gate）。
> 3. Agent 自动引入社区资源触发**一次** P121 Gate；用户主动启用的资源不二次 Gate。
> 4. 上述「增强可包括：审核 / 评分」中的「平台内审核 / 用户评分体系」不在 R15 建设范围（红线：不做泛市场/社交/评分）。
> 本注不覆盖历史原文，仅登记 R15 生效口径。

## 7. 文档功能边界

文档功能增强用于提升文档生成、对齐、检索、差异分析和治理体验。

基础文档治理已经要求：

```text
文档事实源分层；
项目文档、交接材料、产物、证据、运行记录、参考资料身份区分；
Artifact 不自动晋升为项目文档；
产品验收基准归入测试与验收目录；
不预建空文档；
新增文档必须证明必要性。
```

文档功能增强可包括：

```text
文档检索；
文档差异分析；
文档引用图谱；
文档一致性检查；
文档事实源冲突检测；
文档生成辅助；
文档验收辅助；
文档导出；
文档变更影响分析。
```

红线：

```text
1. 文档功能增强不得替代事实源治理；
2. 文档 UI 不得伪造项目文档正式状态；
3. Artifact 不得自动晋升项目文档；
4. 文档功能不应导致事实重复；
5. 文档功能不得把未审核草稿显示为正式版。
```

## 9. 确定性转换边界

> **上游详述源**：`06-确定性转换资源接入规范.md`。转换器接入流程、字段规范、Patch 优先级见 06。本文只定义其作为增强能力的定位与"不是什么"。

确定性转换是资源能力，不是独立主线引擎。

可做：

```text
AST 转换 / codemod / 规则替换 / 配置迁移 /
依赖版本转换 / SQL-ORM 转换 / 接口签名转换 / 静态格式化和重写
```

必须：

```text
1. 作为 Skill/Tool/Expert Agent/MCP 资源接入；
2. 登记来源、权限、风险和 Trace；
3. 输出优先形成 Patch/diff；
4. Patch apply 按风险触发 Gate；
5. 转换结果进入 P5 验证；
6. 不绕过 Policy/Gate/Audit。
```

不得：

```text
1. 不构建独立确定性转换主引擎作为主线；
2. 不让转换结果自动成为业务正确；
3. 不让转换成功自动成为 P4/P5 completed；
4. 不让确定性转换器绕过资源调用流程。
```

## 10. 增强能力与主链路关系

增强能力与 P0-P6 的关系：

```text
P0：增强能力不应阻塞源码接入；
P1：增强能力可辅助建档，但不替代事实源；
P2：增强能力可辅助评估，但不替代风险登记；
P3：增强能力可辅助方案比较，但不替代计划 Gate；
P4：增强能力可辅助执行，但不替代执行 Trace；
P5：增强能力可辅助验证分析，但不替代验证 Evidence；
P6：增强能力可辅助交付材料，但不替代交付 Gate。
```

基本原则：

```text
1. 增强能力可以提高效率；
2. 增强能力不能替代 Gate；
3. 增强能力不能替代 Evidence；
4. 增强能力不能替代 Trace/Audit；
5. 增强能力不能让主链路变成 mock 链路。
```

```text
R12：P5-P6 验证交付，验证证据链必须真实；
R13：Fusion 增强；
R14：远程资源调用增强；
R15：社区功能增强；
R16：文档功能增强；
R17：全量联调、体验打磨与发布冻结。
```

## 12. 变更与前置条件

如果增强能力需要提前，应满足：

```text
1. 明确阻塞的基础链路；
2. 明确为什么不提前会影响 R7/R8/R11/R12；
3. 明确变更范围；
4. 明确影响文档；
5. 明确安全和验收影响；
6. 经过用户确认；
7. 登记到决策记录或变更控制。
```

如果增强能力需要后移，应满足：

```text
1. 不影响 P0-P6 基础闭环；
2. 不影响 R7/R8/R11/R12 的必要能力；
3. 有明确风险登记；
4. 有替代或降级方案；
5. 经用户确认。
```

## 13. 与安全和验收的关系
