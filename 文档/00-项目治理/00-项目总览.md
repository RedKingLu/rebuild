## 1. 平台一句话定义

**rebuild 是一个面向软件重构与迁移的软件重构平台（泛软件重构）；在用户拥有源代码的前提下，帮助用户完成项目迁移、重构、验证与交付。场景体系分「典型场景 + 开放扩展」两层：信创切换 / 软件现代化 / 软件移植为典型场景（平台重点支持、配套资源相对更丰富），并"包括但不限于"这三类，支持用户自由修改与自定义场景；准入以三判据把门（D-117 / D-118）。**

rebuild 的核心不是泛化任务自动化平台，也不是单纯的多 Agent 展示系统，而是围绕"有源代码的软件项目如何安全、可控、可追溯地完成迁移和重构"建立产品流程、Agent 协作、模型调用、受控执行、验证评审和交付归档能力。

## 3. 产品定位

### 3.1 平台定位

rebuild 的定位是：

```text
软件重构平台
```

重点应用领域是：

```text
软件重构与迁移（泛软件重构）——典型场景：信创切换 / 软件现代化 / 软件移植；
并"包括但不限于"这三类（详见 §3.1 下方 V26.2 段与 D-117）
```

> **V26.2 第二阶段扩展（用户 2026-09-02 裁决）**：平台进入第二阶段，**不再局限于信创替换，成为泛软件重构平台**。场景体系分两层——
>
> **① 典型场景**（平台重点支持，**配套资源相对更丰富**：P 系列 skill / 知识条目 / 案例 / 资源库引用 / 选型候选）：
>
> ```text
> xinchuang_switch  信创切换      向国产化软硬件栈替换（原主模式）
> modernization     软件现代化    OS / 运行时 / 框架 / 前端组件版本过低的现代化改造
> porting           软件移植      跨平台移植（Windows→macOS、Android→iOS、Android→鸿蒙 等）
> ```
>
> **② 开放扩展**："**包括但不限于**"上述典型场景，**支持用户自由修改与自定义场景包**（可复制典型场景包后改写）；**不得实现为固定枚举**，新增场景须为"新增场景包目录、零代码改动"。
>
> 任何场景须同时满足**准入三判据**方可进入 P0-P6：**① 有源代码 ② 有可判定的目标态 ③ 产出物可机器验证**。三判据的完整定义、判定口径与拒绝准入路径的**详述源 = `01-决策记录.md` D-118**；场景体系两层结构与场景包结构的**详述源 = D-117**。本文不复制细节（AGENTS §6.2）。

典型前提是：

```text
用户拥有待迁移或待重构项目的源代码。
```

平台要解决的问题是：

```text
在已有源代码的情况下，帮助用户完成项目盘点、迁移评估、方案规划、受控改造、验证评审和交付归档。
```

### 3.2 核心场景动作

无论落在哪一类场景（典型场景或用户自定义场景），核心场景动作一致，包括但不限于：

```text
1. 对已有项目进行源码接入；
2. 建立项目事实源；
3. 识别技术栈、依赖、运行环境和迁移风险；
4. 制定迁移或重构方案；
5. 在受控执行机制下完成代码、配置、依赖或工程结构调整；
6. 验证改造结果；
7. 形成可交付、可追溯、可继续维护的成果。
```

### 3.3 不应偏离的边界

rebuild 不应扩展为泛软件工程平台——定位扩展为泛软件重构（D-117）不改变本节任何边界。

以下内容始终不作为核心目标：

```text
1. 通用 AI 办公平台；
2. 通用 Agent 市场；
3. 泛项目管理平台；
4. 无源代码情况下的纯咨询平台；
5. 面向所有软件工程任务的通用自动化平台；
6. 只展示 Agent 能力而不完成迁移和重构闭环的平台。
```

## 4. 第一性原理

rebuild 从以下问题出发：

```text
用户拥有一个旧项目或待迁移项目的源代码，希望借助 AI 和 Agent 降低迁移、重构、验证与交付成本，同时避免失控、误改、返工和不可追溯。
```

因此，平台必须优先保障：

```text
1. 项目事实可建立；
2. 风险和范围可评估；
3. 方案和计划可审核；
4. 执行动作可控制；
5. 产物和证据可追溯；
6. 验收和交付可复核；
7. 不确定项可停下并交给用户确认。
```

平台的核心闭环不是"Agent 自动干完所有事"，而是：

```text
接入源代码
→ 建立事实源
→ 评估风险
→ 制定方案
→ 受控执行
→ 验证评审
→ 交付归档
```

## 6. P0-P6 与 R0-RN 的区别

### 6.1 P0-P6：平台产品流程

P0-P6 是 rebuild 面向用户项目的可裁剪产品流程。

```text
P0 接入
P1 建档
P2 评估
P3 规划
P4 执行
P5 验证
P6 交付
```

P 阶段用于描述用户项目如何在平台中推进，不用于描述 rebuild 自身如何建设。

P 阶段可以按 Project 引导模板裁剪。例如：

```text
只做评估：P0 → P1 → P2 → P6
只做规划：P0 → P1 → P2 → P3 → P6
完整迁移/重构交付：P0 → P1 → P2 → P3 → P4 → P5 → P6
```

裁剪规则：

```text
1. 被裁剪掉的阶段不得伪装为已完成；
2. 被启用的阶段必须有 Gate、Artifact、Evidence 和完成条件；
3. P6 可以作为任意裁剪流程的收尾；
4. 正式交付建议包含验证或明确的风险确认。
```

## 9. 核心设计原则

### 9.1 源代码前提

平台面向用户拥有源代码的项目——"有源代码"是准入三判据第 ① 条，也是平台第一性前提（D-118）。

这意味着平台能力应围绕以下对象展开：

```text
源码目录
Git 仓库
ZIP 源码包
项目依赖
配置文件
构建脚本
运行环境
测试与验证材料
```

### 9.2 事实源优先

任何评估、规划、执行和验证，都必须基于项目事实源，而不是基于 Agent 的想象。

核心原则：

```text
No Evidence, No Decision.
No Artifact, No Completed.
No Trace, No Trusted Result.
```

### 9.3 少 Agent，多 Skill

默认不为计划、编排、执行、评审等相似职责过度拆 Agent。

优先使用：

```text
同一 Agent + 不同 Skill + 不同上下文 + 不同工具权限
```

只有在以下情况才切换 Agent：

```text
1. 需要干净上下文；
2. 需要更换模型；
3. 权限边界不同；
4. 责任边界不同；
5. 并行任务需要隔离；
6. 需要专家能力；
7. 独立验收。
```

### 9.4 Fusion 只是模型

Fusion 是一种模型能力或模型策略，不是特殊流程、特殊阶段或特殊评审引擎。

平台可以提示 Fusion 更适合评审、建议、方案比较等任务，但不为 Fusion 设计额外流程特权。

### 9.5 Gate 必须有明确裁决主体

P 阶段晋级 Gate 必须由用户授权。

阶段内部 Gate 根据执行模式区分：

```text
Manual：用户审计划、任务和授权动作。
Plan：用户审 Stage Plan 和 Task Plan；计划内动作由 Hook + Policy 检查。
Auto：Agent 审 Stage Plan 和 Task Plan；阶段内授权由 Hook + Policy + Auto Review Agent 处理。
```
