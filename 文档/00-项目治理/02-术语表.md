## 0. 术语使用总则

### 0.1 平台名与版本号

- 平台名称是 `rebuild`。
- `V26.1.1` 是当前基线发布号，不是平台名称。
- 长期目录、API、数据库表、包名、模块名、前端路由、运行时路径不得写死版本号。

正确写法：

```text
平台：rebuild
当前版本：V26.1.1
当前阶段：R20 施工完成（R0~R19 已完成；V26.2 在建，R21 待启动）
```

不建议写法：

```text
rebuild 26.1 平台
V26.1 平台
/api/v26.1/...
v26_1_runtime
```

### 0.2 P 阶段与 R 阶段不得混用

- `P0-P6` 是 rebuild 面向用户项目的产品流程阶段。
- `R0-RN` 是 rebuild 当前版本自身建设阶段。
- 用户项目走 P 阶段；平台建设走 R 阶段。

### 0.3 历史术语处理

以下历史术语不作为当前版本主流程术语：

```text
Phase 15
旧 F0-F6
旧 S0-S7
旧 RunEngine
旧 VNext 主流程
```

如需引用，必须标注为历史参考，并说明当前版本如何吸收、改写或废弃。

### 0.4 术语与决策的对应

本文档中每个术语应尽量标注其关联的决策编号（D-XXX），以便读者从术语追溯到决策依据。决策记录见：`文档/00-项目治理/01-决策记录.md`。

# 第二部分：产品流程术语

## P0-P6

P0-P6 是 rebuild 面向用户项目的可裁剪产品流程。

```text
P0 接入
P1 建档
P2 评估
P3 规划
P4 执行
P5 验证
P6 交付
```

> 关联决策：D-009

## P0 接入

用户项目进入 rebuild 的阶段。

典型输入包括：

```text
本地目录
Git 仓库
ZIP 源码包
GitHub 仓库
```

目标是让平台获得项目源代码或项目资料，并建立初步项目记录。

> 关联决策：D-058

## P1 建档

基于接入材料建立项目事实源。

典型内容包括：

```text
项目结构
技术栈
依赖
构建方式
运行方式
配置文件
已有文档
风险线索
```

## P2 评估

对项目迁移或重构风险进行评估。

典型产出包括：

```text
迁移评估报告
风险清单
阻塞问题
待用户决策项
Evidence 引用
```

## P3 规划

形成迁移或重构方案与执行计划。

典型产出包括：

```text
方案选型
方案设计
执行计划
TaskGraph
Stage Plan
关键 Gate
```

## P4 执行

在受控权限、安全策略和 Gate 下执行迁移或重构任务。

典型对象包括：

```text
Patch
代码变更
配置变更
构建脚本调整
测试修复
执行日志
Trace / Audit
```

## P5 验证

验证 P4 的执行结果是否满足目标。

典型内容包括：

```text
测试结果
验证报告
问题清单
回归风险
验收建议
```

## P6 交付

整理并交付当前流程成果。

典型产出包括：

```text
交付说明
最终产出清单
剩余风险
后续建议
归档索引
```

P6 完成只代表基础主流程完成，不代表所有增强能力完成。

> 关联决策：D-059

## Mission（已废弃）

> **⚠️ 已废弃**（D-070，2026-06-23）。当前版本不设独立 Mission 产品层。用户可见主对象为 Project。

原定义（仅保留作历史参考）：一次用户目标或用户项目任务。

## Mission Template（已废弃）

> **⚠️ 已废弃**（D-070）。替代为 `03-典型项目场景与引导模板.md`。

## Project（用户可见主对象）

用户可见主对象。表示一个待迁移、待重构、待验证或待交付的软件项目。单个 Project 直接按 P0-P6 推进。若需拆分工作范围 → 创建多个 Project。

> 关联决策：D-070

## Project 引导模板

帮助用户创建 Project 时选择合适的项目场景和 P 阶段覆盖范围。替代已废弃的 Mission Template。

> 关联决策：D-070

示例：

```text
只做评估模板：P0 → P1 → P2 → P6
完整迁移模板：P0 → P1 → P2 → P3 → P4 → P5 → P6
```

## Stage

阶段。可指 P 阶段或 R 阶段，必须结合上下文明确。

建议写法：

```text
P2 评估阶段
R4 基础工程骨架阶段
```

不建议只写：

```text
阶段 2
下一阶段
```

## Stage Completion Package

阶段完成包。用于汇总某个阶段的产物、证据、Trace、Audit、问题、风险和进入下一阶段的建议。

典型字段：

```text
阶段目标
已完成任务
产物清单
Evidence 引用
Trace / Audit 摘要
未决项
风险项
进入下一阶段建议
用户裁决选项
```

> **落地（D-107，2026-07-21）**：每 P 阶段产物写入 `artifacts/{stage}/` 独立文件夹，并产出 `artifacts/{stage}/_stage_package.json` 作为本阶段完成包清单（每产物 `{文件名,类型,一句话描述,是否下阶段关键}` + 证据/风险摘要 + 进入下一阶段建议）；下一阶段读前序各阶段清单后**按需加载**产物内容（非写死文件名列表）。R17.5 P2 轮统一 P0/P1/P2 落地，P3-P6 遵循。

## 场景（scenario）

场景指一个**重构/迁移的类型**（做哪一类改造），例如向国产化栈替换、版本现代化、跨平台移植。

在实现上，`Project.scenario` 为**自由文本 id**（非 Python Enum、非前端固定常量），场景集合由场景包目录动态发现。

场景体系分两层：

```text
典型场景（typical）—— 平台重点支持、配套资源相对更丰富
开放扩展（open）   —— "包括但不限于"典型场景，支持用户自由修改与自定义
```

**与「典型项目场景」不是同一概念**——见下方「典型项目场景（易混淆）」条目。

> 关联决策：D-117（两层场景体系，**详述源**）、D-118（准入三判据，**详述源**）、AGENTS.md §1 / §10-27

## 典型场景（typical scenario）

平台**重点支持**的场景，当前三个：`xinchuang_switch`（信创切换）/ `modernization`（软件现代化）/ `porting`（软件移植）。

"典型"的实质含义 = **平台配套资源相对更丰富**（P 系列 skill、知识条目、案例、资源库引用、选型候选），**不是"平台只支持这三类"**。

**禁止表述**："平台仅支持三种场景"、"三类场景是全集"、把三类降级为"普通示例"。

> 关联决策：D-117（详述源）

## 开放扩展（open scenario）

典型场景之外、由用户新建或改写而来的场景。用户既可新建场景包，也可复制典型场景包后改写；场景包不得被锁为只读内置资产。

无专用场景包时走 `_generic` 兜底包，并诚实标注"无专用场景知识"，**不得静默套用信创口径**。

> 关联决策：D-117（详述源）、AGENTS.md §10-27

## 场景包（scenario package）

承载单个场景知识的目录，位于 `source/skills/scenarios/<id>/`，运行期扫描发现。**新增场景 = 新增一个场景包目录，零 Python 与前端代码改动。**

> 关联决策：D-117（目录结构与内容清单的详述源）、D-108（skill-first）

## 准入三判据（scenario admission criteria）

任何场景须**同时**满足三条方可进入 P0-P6：**① 有源代码 ② 有可判定的目标态 ③ 产出物可机器验证**。任一不满足 → 平台诚实告知不适用并拒绝准入，不得降级为"尽力而为"的咨询式输出。

判定口径、`migration_target` 承载关系与拒绝准入路径的**详述源 = D-118**，本表不复制。

> 关联决策：D-118（详述源）、00-项目总览 §9.1（源代码前提）

## 典型项目场景（易混淆）

`文档/01-产品定义/03-典型项目场景与引导模板.md §3` 的「典型项目场景 A-H」指**单个 Project 的 P 阶段覆盖范围形态**（如"仅评估 P0-P2"、"仅规划 P0-P3"、"验证与交付整理"），回答的是"**这个项目走到哪一步**"。

本表「典型场景」（D-117）指**重构/迁移的类型**，回答的是"**这个项目做哪一类改造**"。

两者**正交、不可合并**：一个项目同时具备一个 `scenario`（如 `modernization`）与一种项目场景形态（如"场景 B：迁移评估项目"）。

> 关联决策：D-070（不设 Mission 产品层）、D-117

# 第四部分：Agent 与 Skill 术语

## Agent

具备明确上下文、模型、权限、工具和职责边界的执行主体。

Agent 不是简单"角色名"，必须由 Agent Definition Contract 描述。

> 关联决策：D-016, D-017, D-018

## Skill

可复用的方法、流程或能力单元。

当前版本强调：默认少 Agent、多 Skill。

> 关联决策：D-016

## R 系列 Skill

用于 rebuild 当前版本建设的 Skill。

典型用途：

```text
文档编写
交接整理
独立验收
施工自检
旧决策覆盖检查
```

建议存放于：

```text
skills/R-建设执行/
```

> 关联决策：D-008

## P 系列 Skill

用于未来 rebuild 平台运行时，服务用户项目 P0-P6 流程的 Skill。

典型用途：

```text
P0 接入
P1 建档
P2 评估
P3 规划
P4 执行
P5 验证
P6 交付
```

P 系列 Skill 不应与 R 系列建设 Skill 混放。

> 关联决策：D-008

## Agent Definition Contract

Agent 的结构化定义契约。

至少包含：

```text
Agent ID
名称
类型
可用阶段 / 可用 node
核心职责
禁止职责
System Prompt 模板
Context Recipe
Memory Policy
Model Policy
Tool Policy
Skill Policy
MCP Policy
输入契约
输出契约
Artifact 契约
Evidence 契约
Gate 触发规则
自验证清单
验收标准
失败 / 阻塞 / 升级规则
安全与密钥规则
```

> 关联决策：D-018

## Node Worker Agent

Node 内主工作体。负责读取上下文、生成计划、调用 Skill、执行任务、自验证和提交节点产物包。

> 关联决策：D-019

## Acceptance Agent

独立验收 Agent。

不参与施工，用于检查产物、Evidence、Trace、Gate、完成条件是否满足要求。

> 关联决策：D-019

## Auto Review Agent

Auto Mode 下用于计划审核、授权建议和安全解释的 Agent。

可在第一版中合并 Plan Review 与 Authorization / Safety Review 职责，但职责边界必须清晰。

> 关联决策：D-019, D-028

## Expert Agent

专家 Agent。按需调用，提供领域判断或专项评审，不直接替代主流程执行。

> 关联决策：D-019

## Conversation / Gate Agent

负责向用户展示 Gate、解释状态、收集用户裁决和传递确认结果的 Agent。

> 关联决策：D-019

## 平台助手（AI 精灵 / 客服对话 Agent）

平台级内置助手。用户可见形态为浮动的 "AI 精灵" 图标，点击展开对话面板，用于帮助用户使用平台（对话答疑、使用引导），并在对话面板内可切换模型/服务商作**连通性自测**（验证某模型·服务商是否接入成功，仅影响助手自身会话）。代用户操作平台（建 Project/Run、报状态）为 [规划 / R-future] 能力。

与 `Conversation / Gate Agent` 区分：后者是**项目内**就 Gate/状态与用户交互的运行时 Agent；平台助手是**平台级**使用助手，独立于 P0-P6 迁移编排与 Agent/Skill 资源体系。

> 详述源：`01-决策记录.md` D-073。红线：不泛 AI 平台化；代操作走 Policy/Gate 授权；模型自测复用 ModelGateway 且不泄露密钥。

> 关联决策：D-073（详述源）、D-039（ModelGateway）、D-070（不设 Mission）。

# 第五部分：运行时与流程术语

## Node

流程中的一个运行节点。

Node 可以对应某个阶段任务、子任务、检查点、Gate 或资源调用步骤。

## NodeLoop

每个 Node 内部的标准小循环。

标准流程：

```text
接收任务
读取上下文
生成计划
判断是否拆分子任务
执行任务 / 子任务
自验证
生成节点产物包
交给 Acceptance Agent 验收
根据验收结果流转 accepted / rework / blocked / escalated / failed
```

> 关联决策：D-020

## Task

Node 内的具体任务。

Task 应有明确输入、输出、风险级别、权限边界、产物要求和验收条件。

## TaskGraph

任务图。用于表示任务之间的依赖、并行、汇总、返工、Gate 和升级关系。

## Edge Policy

TaskGraph 边策略。

用于描述任务之间如何流转，而不只是"下一步"。

典型字段：

```text
edge_type
trigger_condition
dependency
parallel_group
merge_strategy
retry_policy
failure_policy
gate_policy
model_policy_override
context_passing_policy
artifact_passing_policy
evidence_passing_policy
```

> 关联决策：D-022

## Run

一次执行实例。

用户在某个 Project 下启动一次 Run 后，平台会产生一个或多个 Run（**不经由已废弃的 Mission 层**，D-070）。

Run 应记录：

```text
run_id
run_goal          ← 运行目标轻量标注（原暂用 mission_id，已按 D-070 校准为 run_goal，不构成 Mission 产品层）
project_id
current_stage
status
active_gate
started_at
updated_at
trace / audit 引用
```

## Flow Runtime

流程运行时。负责阶段推进、节点执行、Gate、checkpoint、状态恢复和事件输出。

当前版本确定 LangGraph 为主编排底座。

## LangGraph

当前版本确定的主编排底座。

P0-P6 主流程、阶段跳转、Gate、checkpoint、interrupt/resume 应落在 LangGraph 编排体系中。

不得以自研状态机替代主编排。

> 关联决策：D-037

## Checkpoint

运行检查点。用于保存流程状态，以支持恢复、暂停、继续和审计。

## Interrupt / Resume

中断与恢复机制。

当流程遇到 Gate、风险、用户确认或外部授权时，中断等待；获得确认后恢复执行。

# 第六部分：计划与执行模式术语

## Execution Mode

执行模式。当前版本包括：

```text
Manual Mode
Plan Mode
Auto Mode
```

执行模式只影响阶段内部 Gate 密度和授权方式，不改变 P0-P6 产品流程，也不改变 P 阶段晋级必须用户授权的规则。

> 关联决策：D-024, D-025

## Manual Mode

手动模式。

用户审核：

```text
Stage Plan
Task Plan
授权动作
阶段晋级
```

适合高风险、不确定性高或用户希望强控制的任务。

> 关联决策：D-025

## Plan Mode

计划模式。

用户审核 Stage Plan、Task Plan 或 Task Plan Batch；计划内动作由 Hook + Policy 检查并放行；越界、风险升级、不确定项回用户；用户审核阶段晋级。

> 关联决策：D-025, D-026, D-027

## Auto Mode

自动模式。

Agent 审核 Stage Plan 和 Task Plan；阶段内授权由 Hook + Policy + Auto Review Agent 处理；高风险、低置信度、冲突、超范围回用户；用户审核阶段晋级。

> 关联决策：D-025, D-028

## Stage Plan

阶段计划。

阶段开始时生成，说明本阶段目标、任务结构、产物、风险、可用资源、完成条件。

## Task Plan / To-do Plan

任务计划。

具体任务执行前生成，说明任务步骤、工具、文件范围、模型、风险、预期产物、验收标准。

## Task Plan Batch

批量任务计划。

当前不设置固定数量限制。后续如出现用户体验、执行安全、上下文膨胀、批量越界或验收困难等瓶颈，再提出调整申请与理由。

即使不限制数量，也必须说明：

```text
批次目标
任务范围
风险级别
权限边界
验收方式
异常升级策略
```

> 关联决策：D-029

## Plan Delta

计划变更。

当执行过程中出现范围、风险、任务结构、模型、资源或权限变化时生成。

典型触发条件：

```text
新增写盘范围
新增外部调用
风险升级
任务拆解变化
模型 / Fusion 切换
引入关键 Case / Skill / MCP
```

# 第七部分：Gate 与安全术语

## Gate

需要裁决、确认、授权或检查的控制点。

Gate 可以由用户、Policy、Agent 或系统触发，但 P 阶段晋级 Gate 必须由用户授权。

> 关联决策：D-023

## Stage Transition Gate

阶段晋级 Gate。

每个启用的 P 阶段进入下一阶段前必须触发，由用户授权。

> 关联决策：D-023

## Human Gate

人工确认 Gate。

需要用户明确确认的 Gate。

## Policy Gate

策略 Gate。

由确定性 Policy / Rule 触发，例如密钥泄露、高风险命令、越权写盘、L5 操作等。

## Acceptance Gate

验收 Gate。

用于检查产物、Evidence、Trace、Audit 和完成条件是否满足要求。

## Escalation Gate

升级 Gate。

当 Agent 无法判断、风险升级、权限不足、上下文冲突或用户裁决缺失时触发。

## Hook

触发点或拦截点。

Hook 本身不等于安全判断，只负责在关键动作前后触发检查。

示例（**设计层挂点清单，非"已接线"清单**——见下方接线现状核验）：

```text
PreToolUse
PostToolUse
PreWrite
PostWrite
PreCommand
PostCommand
PreMCPCall
PostMCPCall
PreStageTransition
PreDelivery
```

> **接线现状核验（2026-09-07，R21 文档收口，读代码实测）**：上述 10 个挂点中，当前
> 只有 **`PreToolUse`** 与 **`PostToolUse`** 两个被真实代码调用——`backend/app/services/
> hook_engine.py::run_hooks()` 被 `tool_registry.py::execute_tool()` 在真实工具分派前后
> 各调用一次（`PreToolUse` 在 :604，可 block；`PostToolUse` 在 :666，advisory）。其余 8 个
> 挂点（`PreWrite`/`PostWrite`/`PreCommand`/`PostCommand`/`PreMCPCall`/`PostMCPCall`/
> `PreStageTransition`/`PreDelivery`）在 `backend/` 全目录（含测试）**零命中**——即
> **定义已具、运行时未接线**，不得读作已生效的安全控制点或已覆盖对应动作类别。
> 当前唯一注册的内置实现体（`hook_engine._BUILTIN_HOOKS`）也只有 1 个：
> `pre_write_policy`（拦截写 `source/` 与写入疑似明文密钥，D-099①/D-032）。
> 详见 `backend/app/services/hook_engine.py` 模块头部注释（自述接线范围）与
> `tool_registry.execute_tool()` 的两处 `run_hooks(...)` 调用点。

## Policy / Rule

确定性规则。

优先级高于 Agent 判断。

示例：

```text
Case 永远无执行权
外部 Agent 不得自我批准
密钥不得输出
L5 高风险动作暂定必须用户 Gate
所有授权结果进入 Audit
```

> 关联决策：D-030, D-031

## Security / Authorization Agent

复杂风险解释和授权建议 Agent。

它不能覆盖 Policy，也不能批准 Policy 禁止的动作。

> 关联决策：D-030

## Risk Level

风险级别。

用于判断命令、Tool、MCP、写盘、Git、远程调用等动作的授权方式。

当前原则：不硬编码命令清单，而是识别动作所属级别。

> 关联决策：D-033

## L0（只读参考）

无破坏性风险。只读文件、只读 API、查看状态、读取文档等。

不需要额外授权。

> **实现现状核验（2026-09-07，R21 独立验收 Q-R21-2）**：`execution_provider._classify_risk()` 当前**只返回 L1/L3/L4/L5 四值，从不返回 L0**——只读命令被归为 L1，非只读命令按其它规则归类。本级**已定义、当前实现未使用**，非代码缺陷（不影响任何 Gate 触发行为），如实标注防止术语定义与实现口径长期漂移不被发现。若后续要让 `_classify_risk` 真正区分 L0，属**放松/收紧授权阈值**的架构层决策，须走用户裁决通道（见 `证据/进度追踪/03-待确认项.md` Q-R21-2），不得顺手改。

## L1（方法调用）

低风险。调用纯函数、运行分析脚本、生成报告、运行测试等。

低风险动作在 Plan / Auto Mode 下可由 Hook + Policy 放行。

## L2（受控执行）

中等风险。本地命令执行、文件写入（限定范围）、Git 本地操作等。

需要 Hook 检查 + 范围校验。

> **实现现状核验（2026-09-07，R21 独立验收 Q-R21-2；2026-09-09 追溯代码路径后修正）**：`execution_provider._classify_risk()` 当前**从不返回 L2**——本地命令执行统一落在 L1（Python 无 subprocess/os.system 等敏感调用时）或 L3（shell 未知命令/Python 含敏感调用）。本级**已定义、当前实现未使用**，非代码缺陷。
>
> 补充追溯（方案 C 评估过程中核实）：`_classify_risk()` 在四个调用点（local/container/toolchain_container/workspace_local）均是**先**过 DENY 硬编码模式检查（直接归 L5、执行前 block+gate，与 L0/L2 是否启用无关），**再**对通过检查的内容分类——此时代码已经执行完毕（或即将无条件执行），分类结果只作为 `result["risk_level"]` 写回审计/Trace，**不再反过来决定是否执行**。真正决定"这个工具要不要先过 `action_approval` Gate"的，是 `tool_registry.execute_tool()` 里更早读取的 **`ResourceEntry.risk_level`**（工具注册时的静态风险位，已完整覆盖 L0-L5，见 `app/seed.py`）——Gate 在 `ExecutionProvider.execute()` 被调用之前就已解决。因此：即使给 `_classify_risk()` 补上 L0/L2 判定分支，也**不会改变任何现有 Gate 的触发结果**（上一版注释"直接补 L2 判定会改变部分命令的 Gate 触发阈值"的推断不准确，此处更正）。是否要补这两个分支，仍属架构层的口径完整性决策，若要做仍应留痕说明动机（不是因为会改变授权行为），而不是被"可能改变 Gate 阈值"的错误理由挡住。

## L3（外部系统写操作）

高风险。远程系统调用、外部 API 写操作、数据库变更等。

Plan Mode 下需要用户确认，Auto Mode 下需 Auto Review Agent 审核。

## L4（系统级操作）

很高风险。系统配置变更、服务启停、用户权限变更等。

Plan Mode 下需要用户确认，Auto Mode 下强制升级到用户。

## L5（不可逆/生产操作）

极高风险。生产发布、Git push、删除大量文件、破坏性数据库操作、密钥操作等。

当前暂定 L5 动作全部强制用户 Gate，所有模式下均须用户确认。

> 关联决策：D-034

rebuild 的模型网关抽象层。

模型配置档案。

## ModelStrategy

模型选择策略。

当前原则：模型选择不绑定阶段，而按用户指定、Task / Node override、Agent 默认、Project 默认、System 默认的优先级解析。

> 关联决策：D-036

## Fusion

一种模型能力或模型策略。

Fusion 不作为特殊流程、特殊阶段、特殊评审引擎或独立运行时角色。

Fusion 不绕过 Policy / Gate / Audit，Fusion 输出不自动等于授权或验收通过。

> 关联决策：D-035

## ExecutionProvider

执行提供方。

负责将 Agent 的抽象动作（调用工具、执行命令、调用模型、访问 MCP 等）映射为具体执行。它是 Tool、Command、MCP、外部 Agent Wrapper 的统一执行入口，受 Hook + Policy + Gate 约束。

> 关联决策：D-030, D-033

## 能力接缝（Capability Seam）

用于登记"一项能力"在代码库中是否成套落地的最小分析单元：一项能力 = **接口声明方**（interface）+ **实现提供方**（implementation）+ **使用消费方**（consumer）三个角色，缺一不可。

```text
接口声明方（interface）：定义能力的调用契约——函数签名 / Protocol / 抽象基类 / 消息格式；
                        只声明"怎么调用"，不关心具体怎么做。
实现提供方（implementation）：真正执行该接口约定行为的具体代码（一个或多个实现类/函数）。
使用消费方（consumer）：在真实运行路径上调用该接口的代码——不是文档/注释/计划中"将调用"，
                        而是 grep/读代码可实测到的真实调用点。
```

新增一项能力时，应确保这三个角色**一并设计到位**：

```text
不得只加实现而不明确消费方 —— 写了实现体但没有任何真实运行路径调用它，
  等价于"看起来完成"而实际不生效（呼应 AGENTS.md §10-17：把"已写接口"当"已联调"）；
不得只定义接口而没有真实实现 —— 接口空转、调用即报错或落到 stub，
  同样不构成可信能力。
```

三个角色中任一缺失，都不构成一条完整可信的能力接缝；验收时不得记为 `implemented`/`accepted`。本表仅登记该原则的定义；平台既有接缝（ExecutionProvider / ModelGateway / Registry 驱动的 Tool / Registry 驱动的 Hook 等）的三角色真实代码坐标登记于 `证据/进度追踪/01-功能表.md`"能力接缝登记"节，本表不复制。

> 关联：AGENTS.md §10-17（禁止把已写接口当已联调）、D-063（确定性能力以 Skill/Tool/Expert Agent/MCP 形式接入，同样需三角色齐备）、本表 ExecutionProvider / ModelGateway / Tool / Hook 词条。

## Resource

资源。

包括文档、Case、Knowledge、Skill、Tool、MCP、社区资源、在线资源、Expert Agent 等。

> 关联决策：D-041

## Knowledge

知识材料。

通常为文档片段、规则说明、经验总结、架构说明等。

## Case

案例。

可检索、可引用、可比较，但无执行权。

Case 不是 Skill，也不是 Tool。

> 关联决策：D-040

## Tool

工具。

可被调用执行某类操作。Tool 的调用必须受权限、Policy、Gate 和 Audit 约束。

## MCP

Model Context Protocol 或其相关外部能力接入机制。

在当前文档中，MCP 表示可被平台发现、调用或接入的外部能力来源之一。

## Expert Agent

专家 Agent。

用于领域判断、专项分析或外部能力补充，不默认参与主流程执行。

> 关联决策：D-019

## Community Resource

社区资源。

默认只读参考，不得默认执行。进入使用前需要安全、许可、权限和审核流程。

> 关联决策：D-061

## Online Resource

在线资源。

来自互联网或远程系统的参考资料。需要记录来源、可信度和使用 Trace。

# 第十一部分：Workspace 与执行术语

## Project

通常对应一个待迁移或待重构的软件项目。

## Project Workspace

项目工作区。

每个用户项目必须有独立 Project Workspace，文件、产物、Evidence、runs、任务状态按 project_id 隔离。

> 关联决策：D-050

## Environment Profile

环境描述档案。

声明项目需要的运行环境、依赖、语言、服务、数据库、中间件等。

它不是运行环境本身。

> 关联决策：D-051

## Execution Session

执行会话。

记录一次具体执行过程，包括命令、构建、测试、Patch、外部 Agent 调用、Trace 和 Audit。

> 关联决策：D-051

## Coding State

编码状态。

包括文件、编辑、产物、协作等。

> 关联决策：D-055

## Execution State

执行状态。

包括命令、构建、测试、Patch、外部 Agent、执行日志等。

> 关联决策：D-055

## Runtime State

运行状态。

包括服务、数据库、中间件、预览环境等。

> 关联决策：D-055

## Background Task

后台任务。

退出工作区 UI 不等于停止任务。后台任务必须可见、可暂停、可取消、可恢复。

> 关联决策：D-052, D-054

## Active Gate

当前阻塞或等待处理的 Gate。

如果 Run 暂停在 Gate，应能在项目、概览或工作区看到 active_gate。

# 第十五部分：上下文与记忆术语

## Context 分层

Context 按层组装，不全量塞入。当前版本分为 7 层（C0-C6）：

```text
C0 Global Policy Context       — 全局安全策略、合规约束
C1 Product Definition Context  — 产品定义、阶段体系、术语
C2 Scope / Baseline Context    — 当前项目范围、基线文档
C3 Project / Run Context       — 当前任务目标、运行实例
C4 Node Task Context           — 当前节点/任务上下文
C5 Evidence / Artifact Context — 证据、产物引用
C6 Dynamic Retrieval Context   — 按需检索的补充上下文
```

> 关联决策：D-043

## Memory 分层

Memory 分层管理，不同类型记忆有不同的生命周期和访问策略：

```text
Policy Memory        — 硬规则、安全策略（只读，长期）
Project Memory       — 项目级持久事实（跨 Run）
Run Memory           — 单次运行内有效（Run 结束清理）
Agent Working Memory — Agent 当前工作上下文（临时）
```

禁止进入记忆的内容：

```text
密钥、Token、env 明文
未确认推断
临时错误日志
一次性任务计划
已过期旧版事实
```

> 关联决策：D-044
