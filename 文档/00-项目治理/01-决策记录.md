
P 阶段和 R 阶段不得混用。

### 1.4 当前关键裁决


## D-074：每个 R 阶段必须包含本阶段能力的最小前后端联调

状态：accepted（2026-06-25 用户新增裁决）

> 本条为"R 阶段最小联调要求"的**唯一详述源**。其余文档（R 阶段总计划、Skill 施工/验收工作流、AGENTS.md）只引用本条、写本文特有项，不复制（D-068 引用规则）。

### 背景

R4-4 独立验收发现（条件项 C-B）：R4-3 交付了 `frontend/src/services/`（7 个 API service 模块）与后端 16 域 API，但**没有任何页面、store 或组件实际 import / 调用 service 层**——页面仍全部读 R3 静态 mock，前端运行期对后端的真实请求数为 0。即"service 层 / API 已写"被当成"已联调"，二者不等价。

### 决定

从 R5 起，**每个 R 阶段的完成条件必须包含：本阶段新增/变更的能力，至少有一条最小但真实的前后端联调闭环**，即：

```text
1. 后端：该能力对应的 API / SSE / 服务端点可被真实调用并返回。
2. 前端：至少有一个页面、入口或交互真实调用该端点（运行期可观测到请求），
   并把结果（或其状态/来源标记）渲染到界面，而非仅停留在 service/store 定义。
3. 可观测证据：验收时须能在运行的前端实测到对后端的真实请求（如 Playwright
   网络捕获、Network 面板、后端 Trace 增量），不得仅以"service 已存在""build 通过"代替。
```

### 边界与说明（关键）

```text
1. "最小"即可：一个阶段不要求把所有页面接通，但不允许该阶段的标志性能力"零页面调用"。
   范围与功能点须在该阶段交接/验收报告中显式写明（已联调哪条、仍 mock 哪些）。
2. 真实能力未就绪时（如模型/资源/集成在早期阶段为 not_connected），联调闭环可以是
   "调用占位/mock API 并如实展示 not_connected/mock 标记"——闭环要求的是"前端真实打到后端"，
   不是"后端必须有真实能力"。诚实标记（D-049/真实能力标记）优先于伪装联调。
3. 不得借联调要求绕过既有红线：不得提前实现真实 LangGraph 主编排、不得引入真实模型/Agent/
   Git/文件写盘（除非该阶段本就以此为目标并经 Gate），联调本身仍受 L0-L5 / Gate 约束。
4. 仅写 service/API 而无任何页面或入口实际调用，视为该阶段未达完成条件（验收不通过项）。
```

### 适用范围

```text
- 适用：R5 起所有含前端可见能力的 R 阶段。
- 追溯：R4 的页面级联调缺口（C-B）已知并登记，作为 R4→R5 衔接的明确遗留工作项，
  不据此判 R4 不通过（R4 定位为 API 骨架阶段）。本条对 R4 不追溯惩罚，只约束 R5 起。
- R4-修复轮已落地一条示范联调（项目列表页真实调用 /api/projects + 来源标记 + 回退），
  作为本条的首个落地样例。
```

```text
- 详述源：本条 D-074。
- 阶段完成条件：D-010（R 阶段定义）、06-R阶段总计划.md §3 阶段通用规则、§23 红线。
```

## D-098：模型策略体系——单一事实源 + 全局统一/自定义双模式 + 可用性回退（2026-06-28）

| 字段 | 内容 |
|------|------|
| **决策ID** | D-098 |
| **状态** | **accepted**（用户裁决，2026-06-28；强化 D-036/D-039，落实 B-ORCH-02） |
| **关联** | D-036（模型选择优先级）、D-039（ModelGateway）、B-ORCH-02（绕过网关）、Q-MODEL-1（解析不一致）、R9-5-2/R9-5-7 |
| **背景** | 摸排+排障发现：运行期模型选择存在**三处不一致**——agent_loop 硬编码 `openai/deepseek-chat`+`api.deepseek.com`、opencode 硬编码 `maas...glm`/`deepseek-v4-flash`、ModelGateway 按策略解析（用户真实策略=maas/glm）。两处硬编码绕过了用户策略，导致"每个地方默认模型不一致"。 |
| **决定（单一事实源）** | （1）**所有模型调用的模型/endpoint/key 必须从用户策略经 ModelGateway/ProviderRegistry 解析，禁止任何调用点硬编码模型名或 endpoint**（agent_loop、opencode 等必须改为按策略解析）；（2）运行期实际所用模型 = 用户在前端设定的真实策略（须验证策略有效性/可用性）。**（3）动态引用原则（用户裁决 2026-06-28 补充）：用户真实策略动态存于 `user_strategies.yaml` override（用户经平台 UI 配置）/ 未来 project 全局·自定义绑定，由 ProviderRegistry 启动加载并动态覆盖；出厂 `model_profiles.yaml` 的 system-default 仅作 bootstrap 兜底，【不得固化用户的真实选择】。** |
| **决定（工作区模型策略，两模式）** | 工作区按模型策略选择默认模型，提供两种模式（**自动模式因实现复杂暂占位/暂不做**，先做两种）：<br>**① 全局统一（global_unified）**：用户在引导界面指定**一个**模型，之后所有调用都走这个模型（project 级 `global_model_ref`）。<br>**② 自定义（custom）**：按用户在资源/Agent 界面的配置，为**每个 Agent** 设置模型（不调整则用系统默认）；各 Agent 调用时用其对应模型。 |
| **决定（每 Agent 模型 + 回退策略）** | 自定义模式下，Agent 配置界面新增**模型策略（回退链）选择**：当该 Agent 对应模型**不可用**时，按策略选择后续可用模型（承 AgentDefinition.model_policy_ref / ModelStrategy 的 fallback_profile_refs）。回退须基于**真实可用性探查**（configured + 可达），非臆测。 |
| **决定（优先级，承 D-036）** | 解析优先级：用户临时指定 → Agent 自定义模型(custom 模式) → Project 全局模型(global 模式) → System 默认策略；每级按可用性回退到 fallback 链/任一可用 configured 模型。 |
| **理由** | 消除"每处默认不一致"，让运行期模型=用户真实意图；同时支持"一刀切全局"与"精细到 Agent"两种用户心智；可用性回退保证某模型挂掉时不中断。 |
| **影响/约束** | agent_loop/opencode 去硬编码改走策略解析（B-ORCH-02）；project 增 `model_strategy_mode`(global_unified/custom) + `global_model_ref`；AgentDefinition 用 model_policy_ref 承每-Agent 模型+回退；引导界面（global 模式选模型）+ 资源/Agent 配置界面（custom 模式每-Agent 选模型+回退策略）须落地（前端，R9-5-7 协同）；自动模式占位待后续。所有模型调用经 ModelGateway，禁止硬编码（红线）。 |
| **验收要求** | (1) `grep` 后端无调用点硬编码模型名/endpoint（agent_loop/opencode 改为策略解析）；(2) global 模式：引导选定模型后所有调用走该模型；(3) custom 模式：每 Agent 用其配置模型，未配=系统默认；(4) 模型不可用时按回退链选下一个可用模型（可用性真实探查）；(5) 运行期实际模型与用户前端策略一致。 |
| **最近更新时间** | 2026-06-28 |
