### 1.2 产品定位

rebuild 是一个面向软件重构与迁移的软件重构平台（泛软件重构）；在用户拥有源代码的前提下，帮助用户完成项目迁移、重构、验证与交付。场景体系分「典型场景 + 开放扩展」两层：信创切换 / 软件现代化 / 软件移植为典型场景（平台重点支持、配套资源相对更丰富），并"包括但不限于"这三类，支持用户自由修改与自定义场景；准入以三判据把门（详见 D-117 / D-118）。

### 1.3 阶段体系

```text
P0-P6 = rebuild 面向用户项目的可裁剪产品流程。
R0-RN = rebuild 当前版本自身建设阶段。
```

P 阶段和 R 阶段不得混用。

## D-003：产品定位为软件重构平台，首期聚焦信创迁移

状态：accepted（**定位范围已由 D-117 部分覆盖 —— 见下方修订注；本条"防止定位漂移"的边界约束仍然有效**）

### 决定

rebuild 是面向软件重构与迁移的软件重构平台，首期重点应用于信创迁移，在用户拥有源代码的前提下帮助用户完成迁移、重构、验证与交付。

### 理由

防止定位漂移。当前版本不应扩展为泛 AI 办公平台、泛项目管理平台、纯咨询平台或通用 Agent 展示平台。

### 影响

产品流程、Agent 运行时、资源调用、前端体验、API 和验收标准应围绕源码项目展开。

> **修订注（2026-09-05，R20-1，C4；用户 2026-09-02 裁决）**：本条"**首期聚焦信创迁移**"的范围限定**已被 D-117 部分覆盖**——V26.2 起 rebuild 定位为**泛软件重构平台**，场景体系为「典型场景 + 开放扩展」两层，信创迁移收敛为**典型场景之一**（`xinchuang_switch`）。本条**未被废弃**：①「rebuild 是面向软件重构与迁移的软件重构平台」仍然成立；②「以用户拥有源代码为前提」升级为 D-118 准入判据①；③「理由」段的四条禁止（泛 AI 办公 / 泛项目管理 / 纯咨询 / 通用 Agent 展示）**完全保留、不因定位扩展而放宽**（D-117 决定⑥）。当前定位口径的详述源 = **D-117 / D-118**。

平台资源/                        ← 平台运行期资源

## D-074：每个 R 阶段必须包含本阶段能力的最小前后端联调

状态：accepted（2026-06-25 用户新增裁决）

> 本条为"R 阶段最小联调要求"的**唯一详述源**。其余文档（R 阶段总计划、Skill 施工/验收工作流、AGENTS.md）只引用本条、写本文特有项，不复制（D-068 引用规则）。

### 背景

R4-4 独立验收发现（条件项 C-B）：R4-3 交付了 `frontend/src/services/`（7 个 API service 模块）与后端 16 域 API，但**没有任何页面、store 或组件实际 import / 调用 service 层**——页面仍全部读 R3 静态 mock，前端运行期对后端的真实请求数为 0。即"service 层 / API 已写"被当成"已联调"，二者不等价。

### 决定

从 R5 起，**每个 R 阶段的完成条件必须包含：本阶段新增/变更的能力，至少有一条最小但真实的前后端联调闭环**，即：

```text
1. 后端：该能力对应的 API / SSE / 服务端点可被真实调用并返回。
2. 前端：至少有一个页面、入口或交互真实调用该端点（运行期可观测到请求），
   并把结果（或其状态/来源标记）渲染到界面，而非仅停留在 service/store 定义。
3. 可观测证据：验收时须能在运行的前端实测到对后端的真实请求（如 Playwright
   网络捕获、Network 面板、后端 Trace 增量），不得仅以"service 已存在""build 通过"代替。
```

### 边界与说明（关键）

```text
1. "最小"即可：一个阶段不要求把所有页面接通，但不允许该阶段的标志性能力"零页面调用"。
   范围与功能点须在该阶段交接/验收报告中显式写明（已联调哪条、仍 mock 哪些）。
2. 真实能力未就绪时（如模型/资源/集成在早期阶段为 not_connected），联调闭环可以是
   "调用占位/mock API 并如实展示 not_connected/mock 标记"——闭环要求的是"前端真实打到后端"，
   不是"后端必须有真实能力"。诚实标记（D-049/真实能力标记）优先于伪装联调。
3. 不得借联调要求绕过既有红线：不得提前实现真实 LangGraph 主编排、不得引入真实模型/Agent/
   Git/文件写盘（除非该阶段本就以此为目标并经 Gate），联调本身仍受 L0-L5 / Gate 约束。
4. 仅写 service/API 而无任何页面或入口实际调用，视为该阶段未达完成条件（验收不通过项）。
```

### 适用范围

```text
- 适用：R5 起所有含前端可见能力的 R 阶段。
- 追溯：R4 的页面级联调缺口（C-B）已知并登记，作为 R4→R5 衔接的明确遗留工作项，

  作为本条的首个落地样例。
```

## 决策记录维护规则

1. 新决策必须追加登记，不得覆盖历史条目。
2. 若决策被修订，必须新增"修订决策"并标明替代关系。
3. 历史版本决策仅作参考，不直接复制为当前版本决策。
4. 决策必须包含：决定、理由、影响或约束、验收要求。
5. 不确定项必须进入"待确认项"（第十七部分），不得后延或口头忽略。
6. 已由用户明确确认的事项不得继续登记为未确认。
7. 草稿阶段用户已明确给出结论的事项，应直接合并为正式决策草案，而不是继续放在待确认项中。
8. 每份决策的状态（accepted / accepted（措辞经用户 2026-09-17 批量接受） / deprecated / superseded）必须显式标注。
