
P 阶段和 R 阶段不得混用。

### 1.4 当前关键裁决


## D-074：每个 R 阶段必须包含本阶段能力的最小前后端联调

状态：accepted（2026-06-25 用户新增裁决）

> 本条为"R 阶段最小联调要求"的**唯一详述源**。其余文档（R 阶段总计划、Skill 施工/验收工作流、AGENTS.md）只引用本条、写本文特有项，不复制（D-068 引用规则）。

### 背景

R4-4 独立验收发现（条件项 C-B）：R4-3 交付了 `frontend/src/services/`（7 个 API service 模块）与后端 16 域 API，但**没有任何页面、store 或组件实际 import / 调用 service 层**——页面仍全部读 R3 静态 mock，前端运行期对后端的真实请求数为 0。即"service 层 / API 已写"被当成"已联调"，二者不等价。

### 决定

从 R5 起，**每个 R 阶段的完成条件必须包含：本阶段新增/变更的能力，至少有一条最小但真实的前后端联调闭环**，即：

```text
1. 后端：该能力对应的 API / SSE / 服务端点可被真实调用并返回。
2. 前端：至少有一个页面、入口或交互真实调用该端点（运行期可观测到请求），
   并把结果（或其状态/来源标记）渲染到界面，而非仅停留在 service/store 定义。
3. 可观测证据：验收时须能在运行的前端实测到对后端的真实请求（如 Playwright
   网络捕获、Network 面板、后端 Trace 增量），不得仅以"service 已存在""build 通过"代替。
```

### 边界与说明（关键）

```text
1. "最小"即可：一个阶段不要求把所有页面接通，但不允许该阶段的标志性能力"零页面调用"。
   范围与功能点须在该阶段交接/验收报告中显式写明（已联调哪条、仍 mock 哪些）。
2. 真实能力未就绪时（如模型/资源/集成在早期阶段为 not_connected），联调闭环可以是
   "调用占位/mock API 并如实展示 not_connected/mock 标记"——闭环要求的是"前端真实打到后端"，
   不是"后端必须有真实能力"。诚实标记（D-049/真实能力标记）优先于伪装联调。
3. 不得借联调要求绕过既有红线：不得提前实现真实 LangGraph 主编排、不得引入真实模型/Agent/
   Git/文件写盘（除非该阶段本就以此为目标并经 Gate），联调本身仍受 L0-L5 / Gate 约束。
4. 仅写 service/API 而无任何页面或入口实际调用，视为该阶段未达完成条件（验收不通过项）。
```

### 适用范围

```text
- 适用：R5 起所有含前端可见能力的 R 阶段。
- 追溯：R4 的页面级联调缺口（C-B）已知并登记，作为 R4→R5 衔接的明确遗留工作项，
  不据此判 R4 不通过（R4 定位为 API 骨架阶段）。本条对 R4 不追溯惩罚，只约束 R5 起。
- R4-修复轮已落地一条示范联调（项目列表页真实调用 /api/projects + 来源标记 + 回退），
  作为本条的首个落地样例。
```

```text
- 详述源：本条 D-074。
- 阶段完成条件：D-010（R 阶段定义）、06-R阶段总计划.md §3 阶段通用规则、§23 红线。
```

## D-075：BYOK 加密持久化落地方式（2026-06-25）

| 字段 | 内容 |
|------|------|
| **决策ID** | D-075 |
| **决策类型** | 技术方案 |
| **状态** | **accepted-暂定**（R6-3 落地，待用户裁决） |
| **关联** | Q-009（升级为决策）、D-032（密钥脱敏）、§12.1 红线 |
| **背景** | R5 用户导入供应商的 Key 仅进程内存（volatile），重启丢失。R6 需实现 Key 安全持久化。 |
| **决定** | 采用 AES-256-GCM + HKDF 加密方案：Key 经 `REBUILD_MASTER_KEY` → HKDF-SHA256 派生 → AES-256-GCM 加密后存入 credential 表（`encrypted_key` LargeBinary）；API 响应固定返回 `masked_key: "****"` 和 SHA-256 `key_fingerprint`；Provider 通过 `credential_ref` 引用 Credential；解密仅在 ModelGateway 内部执行。 |
| **理由** | AES-256-GCM 是工业标准对称加密；HKDF 派生支持多租户隔离；复用 V10 byok_crypto.py 已验证设计；零泄露保障（API/日志/Trace/Audit/DB 均无明文）。 |
| **影响/约束** | 生产环境必须设置强随机 `REBUILD_MASTER_KEY`（≥32 bytes）；Dev fallback 固定串仅用于本地开发；显式 Provider 无 credential_ref 且无 env key 时返回明确错误，不跨 Provider fallback。 |
| **验收要求** | pytest 133 passed（含 BYOK 加密往返/零泄露/Audit/fallback 测试）；DB grep sentinel=0；API 响应 masked_key="****"。 |
| **开发/施工归口** | R6-3（后端：credential 表+AES-256-GCM+API；前端：SettingsPage BYOK 入口待 R7） |
| **最近更新时间** | 2026-06-25（R6-3 二轮返工） |

## D-076：执行能力分层——代码执行与 AI 编码 Agent 严格分离（2026-06-26）

| 字段 | 内容 |
|------|------|
| **决策ID** | D-076 |
| **决策类型** | 架构方案 |
| **状态** | **accepted**（用户裁决 2026-06-26） |
| **关联** | D-037（LangGraph 主编排）、D-065（NIH 约束）、D-074（最小联调）、R8-5 专项修复 |
| **背景** | R8 之前某轮施工将 `opencode_adapter.execute()` 作为所有命令/脚本的执行路由器，调用 `opencode run --command "..."` 跑 shell 片段，把 OpenCode（AI coding agent）当成了 shell wrapper，导致概念错误、过度耦合、选择缺失三重问题。 |
| **决定** | 两条路径永远严格分离，不得交叉：<br>**[代码执行路径]** 命令/脚本/构建/测试 → `ExecutionProvider`（`LocalSubprocessExecutionProvider` / `ContainerExecutionProvider`）→ 自有 subprocess / Docker，完全不依赖任何 AI 编码 Agent CLI；<br>**[AI 编码 Agent 路径]** P4 编码任务 → LangGraph 主编排 → `CodingAgentAdapter`（选外部 Agent 时）或平台自有 LangGraph 节点（默认）。 |
| **理由** | OpenCode/qcode 等是接受自然语言任务、自主改代码的 AI agent，不是 shell wrapper；混用导致误用且无法实现用户选择机制；分离后各路径职责清晰、可独立演进。 |
| **影响/约束** | `LocalSubprocessExecutionProvider` 必须内联自有 subprocess 逻辑，不得 import opencode_adapter 的 execute 函数；opencode_adapter 重写为 AI 编码 Agent 适配器接口（Stub）；`POST /execute`（Workspace 终端）不得依赖 OpenCode CLI 是否安装。 |
| **验收要求** | OpenCode CLI 未安装时终端执行仍正常；`POST /coding-agents/{id}/invoke` 返回 Stub；pytest 全通过。 |
| **开发/施工归口** | R8-5 执行集成专项修复 |
| **最近更新时间** | 2026-06-26 |
