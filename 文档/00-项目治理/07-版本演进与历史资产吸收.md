## 1. 为什么需要这份文档

rebuild 已历经多次版本演进与重启。如果不把"为什么重启、上一代留下了什么、哪些该带走哪些该丢"显式记录下来，就会陷入"文档重写跑步机"：每代重复造轮子、反复丢弃可运行资产，却不沉淀教训。

本文的目标：把历史变成**资产与教训**，而不是包袱或空白。

## 2. 版本演进旅程（事实，来自用户口述 + archive）

```text
V8   ── 进展顺利，但一直调试不通。
        最初只想做 V10「重新梳理」，并未打算重构。
          ↓ 梳理中发现：根本没有用 LangGraph，而是自研运行时，导致难以调试。
V10  ── 临时用 VNext（LangGraph 运行时）替换自研 RunEngine，
        但对接总是失败，历史包袱太重。
          ↓
V26.0 ── 重新启动，但发现建设太快、描述太简单；因刚启动不久，索性整体抛弃。
          ↓
V26.1 ── 重新开始细化工作，按 R0→R1→…→R17 步骤逐步建设（当前）。
```

archive 佐证：
- V10 含完整 `backend/app/vnext/` LangGraph StateGraph（S0-S7）、61 文档体系、753 测试规模、`docs/archive/legacy-runengine/`（旧自研运行时已代码级归档）。
- V26.0（26.0.1）F0-F4 真实跑通：langgraph 0.6 + ExecutionProvider + ModelGateway，15 pytest + Playwright 全绿，后端 ~2713 行 + 前端 ~762 行 + spike-v0。

### 2.1 重启根因小结（教训之母）

```text
1. 自研运行时 → 难调试、难以平滑切换到成熟框架（→ 催生 D-037、D-065）。
2. 包袱过重 → VNext 对接失败（→ 催生 D-062：不直接继承旧代码骨架）。
3. 建设过快、描述过简 → V26.0 早夭（→ 催生 R 阶段逐步细化、先文档基线）。
```

> **元教训**：V26.1 应被视为**最后一次整体重启**。此后以增量演进为主，重大重启需专门论证（D-062）。

## 4. 历史资产吸收策略（四类）

> 分类口径：**吸收**=可直接继承/沿用；**借鉴**=参考思路但当前版本重新实现；**抛弃**=禁止复用；**教训**=见 §3。
> 注：以下"借鉴"项的代码级取舍需 R2/R3 深读校准（§5）。

### 4.1 应吸收（直接继承 / 沿用）

```text
- V10 安全红线规范              → 全文审核后继承（信创/迁移安全底线）。
- V10 合规文档（IP/许可证条款） → 继承，进入 文档/07-安全与权限/ 或合规专题。
- V10 大文件分步写入规范（§10） → 继承为工作准则（已在 AGENTS.md/Skill 分步写入体现）。
- 独立验收机制 + 诚实口径 + 欠账登记 → 继承为 R 阶段验收硬规则。
```

### 4.2 应借鉴（参考思路，当前版本重新实现）

```text
- VNext LangGraph StateGraph 架构（节点划分、StateGraph 编排、MigrationState reducer、Checkpointer、interrupt/resume）
  → 理解 S0-S7 编排模式，按当前 P0-P6 + LangGraph 重新落地（不复制旧代码）。
- SSE 事件体系（事件类型、流式推送；注意 tool.confirm / tool.confirm_resolved 命名教训）。
- Gate interrupt/resume 机制。
- 三幅式工作区前端 + 功能模块结构 + Zustand 状态管理 + Playwright E2E 结构
  → 对齐 V26.1 前端心智（D-045~D-049）参考重建。
- 三执行 profile（skeleton/mock_llm/real_llm）设计 → 参考概念，重新实现。
- 模型网关 LiteLLM 集成模式 → 参考多服务商适配，按 D-039 薄抽象重建。
- 能力体系契约模型（Prompt/Skill/Tool/Case/MCP/Agent + Registry + 欠账登记）→ 参考资源契约设计。
- Agent/Experts 体系、数据库 Schema、Docker 部署配置 → 参考划分与方案，重新构建。
```

### 4.3 应抛弃（禁止复用）

```text
- 旧自研 RunEngine（调试不通、催生重启的直接根因）。
- 旧 S0-S7 / 旧 F0-F6 作为当前主流程（当前用 P0-P6）。
- VNext 旧运行时的回退/兼容残留路径（归档须彻底，不保留回退）。
- skeleton 伪装 real_llm 等任何"伪完成"模式。
- OpenCode 等未经真实验证的模拟器集成路径。
```

### 4.4 应内化教训

见 §3 全表。核心三条：**独立验收+诚实口径**、**单一事实源防膨胀**、**薄编排/不自研主编排**。

## 5. 历史资产代码级深读：并入各对应 R 阶段，按"三步法"执行

> 处置裁决（2026-06-23）：本文列出的历史资产代码级深读**不单独成阶段**，而是**并入各对应 R 阶段**；每个模块建设遵循"三步法"。已登记为 **D-067** 并写入 `AGENTS.md §11.1` 作为硬规则。

**三步法（每模块必做）：**

```text
第一步：先独立提出当前版本自己的方案（不先看旧代码，保证主体性）；
第二步：再深度吸收对应历史方案（archive 只读，记录 吸收/不吸收/适配方式/风险）；
第三步：用吸收到的经验完善自己的方案，再执行。
必须先产出"自有方案 → 历史吸收记录 → 完善后方案"三段产物，方可施工。
```

**深读任务并入的阶段映射（在该阶段建模块时按三步法执行）：**

```text
R3 前端主干         ← V10/V26.0 三幅式布局、features、stores、Playwright e2e；对照 Target Demo。
R4 工程骨架/API     ← V10/V26.0 API 与 SSE 映射、目录结构。
R5 模型网关         ← V10 app/gateway/ 与 V26.0 app/model/ 对比，定 ModelGateway 薄抽象边界；
                       V26.0 spike-v0（Go+LangGraph）可采纳结论。
R6 Agent/Skill/资源 ← V10 capabilities/ 契约模型；Agent/Experts 体系。
R11/R12 执行与验证   ← VNext graph/state/gates/checkpointer/compatibility 编排模式；验证能力接入。
专题（07-安全与权限） ← V10 安全红线规范 / 合规文档全文审核后继承。
```

> 每条深读结论必须按 `AGENTS.md §11` 记录：参考路径、可吸收内容、不吸收内容、适配方式、风险。不直接复制旧代码、不复活旧主流程。
