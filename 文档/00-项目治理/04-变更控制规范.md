## 0. 本文目标

本文用于回答：

```text
1. 什么是 rebuild 当前版本中的"变更"；
2. 哪些变更可以直接执行，哪些变更必须申请；
3. 变更申请应包含哪些内容；
4. 变更由谁审核、谁批准、谁执行、谁验收；
```

```text
No Evidence, No Decision.
```

## 1. 变更控制总原则

### 1.1 变更必须显式化

任何会改变事实源、目录、文档、代码、流程、资源、权限、技术栈、验收标准或用户可见行为的动作，都必须被识别为变更。

禁止把变更伪装成：

```text
微调
顺手修一下
先占位
后面补齐
临时处理
不影响主流程
只是优化
```

如果它改变了事实、规则、目录、实现、权限、流程或用户体验，就必须纳入变更控制。

### 1.2 变更必须有理由

任何变更必须说明：

```text
为什么要变更；
不变更会有什么问题；
变更会影响什么；
是否有替代方案；
是否需要用户裁决；
如何验证变更结果。
```

### 1.3 变更必须可追溯

变更必须留下记录。

记录至少包括：

```text
变更编号
变更标题
变更类型
变更原因
影响范围
申请人 / Agent
决策人
执行人
审核人
状态
相关文件
相关证据
风险与回滚方案
验收结果
```

### 1.4 不确定项不得后延

如果出现以下情况，必须停下并登记待确认项：

```text
资料缺失
事实源冲突
路径不清
阶段不清
范围争议
技术栈变更
安全或权限风险
用户体验重大变化
影响已确认决策
影响正式事实源
可能导致返工
```

禁止写：

```text
后续再说
先按这个做
先占位
以后补齐
第一阶段暂缓但不登记
```

## 3. 变更分级

变更按影响范围分为五级。

### C0：记录性变更

不改变事实、不改变规则、不改变目录、不改变实现，仅补充记录或修正文案。

示例：

```text
修正错别字
补充文档更新时间
补充引用路径
补充已确认状态说明
```

处理方式：

```text
可直接执行；
需记录在总报告或变更日志；
不得改变决策含义。
```

### C1：局部内容变更

影响单个文档、单个交接材料、单个产物或单个局部说明，不改变总体结构和已确认决策。

示例：

```text
完善某份文档章节
补充验收标准
调整某个模板表述
```

处理方式：

```text
需写明修改理由；
更新对应总报告或总表；
正式候选仍为待审核。
```

### C2：结构性变更

影响目录结构、文档结构、材料身份、资源分类、流程章节或跨多个文件的一致性。

示例：

```text
新增 平台资源/ 目录
移动 P 系列 Skill 到 平台资源/skills/P系列/
新增文档分区
合并多个治理文档
```

处理方式：

```text
必须提出变更说明；
说明影响范围；
说明迁移路径；
需要用户或 Copilot 审核后执行。
```

> **实例**：2026-06-23 用户确认的"平台资源/ 目录提案"即为 C2 变更——新增根目录 `平台资源/`，将 P 系列 Skill 从 `skills/` 迁入，同步修订 D-008。

### C3：规则性变更

影响已确认规则、执行准则、Gate、Policy、阶段边界、Agent / Skill 权限或验收标准。

示例：

```text
修改 P 阶段晋级 Gate 规则
修改 L5 强制用户 Gate 规则
修改 AGENTS.md 中的硬规则
修改技术栈变更规则
修改草稿晋升正式文档流程
```

处理方式：

```text
必须提交正式变更申请；
必须列出替代方案和风险；
必须经用户确认；
确认后登记到决策记录或对应规范。
```

### C4：架构或技术栈变更

影响主编排、模型网关、后端框架、前端框架、数据库、运行时依赖、Workspace / Execution 架构等。

示例：

```text
替换 FastAPI
替换 React / Vite
改用 PostgreSQL 作为首期默认数据库
改用 LiteLLM Proxy 取代 LiteLLM SDK Adapter
绕开 LangGraph 自研状态机
引入 Dapr / Temporal 作为运行时依赖
```

处理方式：

```text
必须提交技术栈或架构变更申请；
必须说明影响范围、替代方案、迁移成本、风险、回滚方案、验收方式；
未经用户确认不得执行。
```

### C5：安全、高风险或不可逆变更

影响密钥、安全、权限、外部系统写操作、发布、删除、大规模迁移或不可逆操作。

示例：

```text
Git push
生产发布
删除大量文件
破坏性数据库操作
密钥读取、轮换或导出
远程系统写操作
不可逆变更
```

处理方式：

```text
必须用户 Gate；
必须有回滚方案；
必须有 Audit；
不得由 Agent 自行批准；
默认不得批量批准。
```

### 3.6 C0-C5 与 L0-L5 的关系：正交（明确结论）

> 本结论于 2026-06-23 R1 第一部分验收时确定，解决原 §17/§18 中"C0-C5 是否需要映射到 L0-L5"的待确认项。

C0-C5（变更分级）与 L0-L5（风险级别，定义见 `02-术语表.md` 第七部分）是**两个正交维度，不做 1:1 映射**：

```text
C0-C5 = 变更治理维度 —— 衡量"一次变更触及项目事实/规则/结构/实现的范围有多大"，决定审批与登记流程。
L0-L5 = 执行风险维度 —— 衡量"单个动作（命令/写盘/外部写/发布等）有多危险"，决定执行期授权方式。
```

二者可自由组合，互不蕴含：

```text
- 一次 C1 局部文档完善，可能只涉及 L0 只读动作；
- 一次 C2 目录重构，可能涉及 L2 受控写盘，但治理上仍是结构性变更；
- 一次 C4 架构变更，落地时可能触发 L4/L5 动作（如服务启停、发布）；
- 一个 L5 动作（如 Git push）即使只是 C0 记录性变更的一部分，仍必须走 L5 用户 Gate。
```

仲裁规则：

```text
1. 同时适用 C 级与 L 级时，按"两者中更严格的 Gate"处理（取严不取宽）；
2. C 级决定"变更要不要申请、谁审批、怎么登记"；L 级决定"执行这一步动作要不要用户授权";
3. 不得用 C 级豁免 L 级（例如不能因为"只是 C0 记录性变更"就放行其中的 L5 动作）；
4. 不得用 L 级豁免 C 级（例如不能因为"动作都是 L0 只读"就跳过 C3/C4 的变更申请）。
```

## 4. 变更状态

变更状态统一使用以下枚举：

```text
draft             草案
proposed          已提出
needs_info        信息不足
needs_user_gate   等待用户裁决
approved          已批准
rejected          已拒绝
in_progress       执行中
implemented       已实现 / 已写入
under_review      待审核
accepted          已验收通过
superseded        已被替代
rolled_back       已回滚
blocked           阻塞
```

### 4.1 状态使用规则

- `draft`：Agent 草拟，尚未提交正式申请。
- `proposed`：已提交变更申请。
- `needs_info`：事实源不足，需要补充材料。
- `needs_user_gate`：需要用户裁决。
- `approved`：已获授权，可以执行。
- `rejected`：已拒绝，不得执行。
- `in_progress`：变更执行中。
- `implemented`：变更已写入，但尚未验收。
- `under_review`：等待审核。
- `accepted`：审核通过并成为正式事实。
- `superseded`：被后续变更替代。
- `rolled_back`：已回滚。
- `blocked`：当前阻塞。

## 7. 文档变更控制

### 7.1 草稿到正式候选

草稿不能直接成为正式文档。

必须经过：

```text
1. 判断该文档是否应该具备；
2. 定义该文档应具备哪些内容；
3. 检查草稿是否满足需求；
4. 给出完善计划；
5. 生成正式候选文档；
6. 状态标记为待审核；
7. 用户与 Copilot 审核通过后，方可 accepted。
```

### 7.2 修改待审核文档

待审核文档可以继续修改，但必须在总报告或变更日志中记录：

```text
修改内容
修改原因
影响范围
是否需要重新审核
```

### 7.3 修改 accepted 文档

accepted 文档不得直接覆盖修改。

必须：

```text
1. 提出变更申请；
2. 说明修改原因；
3. 保留旧版本或变更记录；
4. 写入新版本；
5. 标明 superseded 关系；
6. 重新审核。
```

### 7.4 删除或合并文档

删除、合并、拆分、重命名文档属于 C2 及以上变更。

必须记录：

```text
原路径
新路径
迁移理由
被替代关系
是否保留归档
对引用的影响
```

## 8. 目录变更控制

目录变更至少属于 C2。

### 8.1 目录变更必须说明

```text
新增 / 删除 / 移动 / 重命名目录
目录职责
影响哪些材料
是否改变写入权限
是否影响 AGENTS.md 或版本与目录策略
是否需要更新文档索引
是否需要迁移旧文件
```

### 8.2 目录变更后必须更新

```text
03-版本与目录策略.md
AGENTS.md
相关交接材料
相关总表或索引
必要时更新 README.md
```

### 8.3 并行目录禁止

禁止产生同一概念多个并行目录。

示例：

```text

交接材料/
handoff/
资料-本轮交接/
```

如发现并行目录，必须提出收敛方案。

```text

是否影响已有文档或实现

```

## 11. 工程实现变更控制

涉及代码、API、前端、后端、模型、Workspace、ExecutionProvider、数据库、运行时等，必须先输出施工计划。

施工计划至少包括：

```text
任务目标
当前阶段
事实源依据
涉及路径
拟修改文件
不修改文件
依赖条件
执行步骤
风险级别
Gate 要求
回滚方案
验收标准
待确认项
```

以下情况必须停止并申请变更或用户确认：

```text
当前阶段不允许施工
事实源不足
路径不清
技术栈变更未确认
涉及密钥或高风险权限
涉及 L5 动作
会改变已确认决策
会绕过 LangGraph 主编排
会复活旧 RunEngine 或旧流程
会把草稿/产物直接晋升为正式文档
```

## 14. 回滚规则

C2 及以上变更必须考虑回滚。

回滚方案至少包括：

```text
回滚对象
回滚前状态
回滚步骤
回滚后验证
是否影响其他文件
是否需要用户确认
```

以下变更没有回滚方案不得执行：

```text
目录迁移
文档合并或删除
代码结构调整
数据库结构变更
平台资源权限变更
安全策略变更
L5 高风险动作
```

---

## 15. 验收规则

变更完成不等于验收通过。

变更验收必须检查：

```text
是否按申请执行
是否改变了未授权范围
是否更新相关文档
是否更新总报告 / 总表 / 变更日志
是否有证据
是否有回滚记录或说明
是否存在待确认项
是否需要用户与 Copilot 审核
```

正式候选文档状态仍为：

```text
待审核
```

直到用户与 Copilot 审核通过。

## 16. 禁止事项

禁止：

```text
1. 未申请就执行 C2 及以上变更；
2. 未经用户确认就执行 C4 / C5 变更；
3. 以"后续补齐"绕过当前必须确认的问题；
4. 把草稿直接升级为正式文档；
5. 直接覆盖 accepted 文档且不保留变更记录；
6. 修改历史归档作为当前版本实现；
7. 复活旧 RunEngine、旧 S0-S7、旧 F0-F6 主流程；
8. 绕开 LangGraph 主编排硬规则；
9. 把 P 系列 Skill 放入 R 系列建设 Skill 目录；
10. 把平台运行 Tool / MCP / Agent 随意散落到文档目录；
11. 输出或写入密钥、Token、Secret、Password；
12. 外部 Agent 自我批准高风险动作；
13. 无证据标记 completed；
14. 无 Gate 标记 accepted。
```
