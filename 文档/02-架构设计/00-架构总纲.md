## 0. 架构总纲编写原则

```text
项目治理 > 产品定义 > 架构设计 > 专题规范
```

因此本文只回答：

```text
1. 产品定义如何落成系统结构；
2. rebuild 架构应分成哪些层；
3. 哪些能力属于主干架构；
4. 哪些能力应作为资源、适配层、专题模块或增强能力接入；
5. 哪些内容应下沉到流程、模型资源、API、UX、安全、测试验收等专题文档。
```

本文不回答：

```text
1. 是否修改产品定位；
2. 是否修改 P0-P6；
3. 是否修改 R 阶段计划；

9. 是否改变产品验收口径（D-071）。
```

如果本文与上级决策或产品定义冲突，以上级为准，并登记待确认项。

## 1. 架构目标

rebuild 当前版本架构目标是：

```text
围绕用户拥有源代码的 Project，构建一个可按 P0-P6 推进软件重构与迁移的、
可追溯、可验证、可恢复、可审计的平台主干。
```

架构必须支撑：

```text
1.  Project 作为用户可见主对象（D-070）；
2.  P0-P6 作为用户项目流程（D-009）；
3.  R0-RN 作为 rebuild 自身建设阶段（D-010）；
4.  LangGraph 作为主编排底座（D-037）；
5.  Project Workspace / Environment Profile / Execution Session 三对象（D-051）；
6.  Coding State / Execution State / Runtime State 三状态分离（D-055）；
7.  ModelGateway 作为模型调用抽象（D-039）；
8.  Agent / Skill / Tool / MCP / Case / Knowledge / Policy / Template 作为平台资源体系（D-008-REV1）；
9.  Gate、Artifact、Evidence、Trace、Audit 贯穿主链路；
10. P5 验证能够证明迁移/重构结果的正确性（D-066）。
```

架构不得被降级为：

```text
1. 只有前端 mock 的演示壳；
2. 只跑通状态流转但没有真实 Artifact / Evidence 的基础循环；
3. 只调用模型但无 Workspace、Trace、Audit、Gate 的聊天工具；
4. 只生成建议但无法执行、验证和交付的咨询系统；
5. 以旧版本代码或旧阶段体系为骨架的迁移工程（D-062）；
6. 用自研状态机替代 LangGraph 的运行时（D-037, D-065）；
7. 用 Mission 产品层插入 Project 与 P0-P6 之间（D-070）。
```

## 2. 架构分层总览

rebuild 采用以下架构分层：

```text
┌────────────────────────────────────────────────────────────┐
│  Arch-L7  API 与前端交互层                                    │
│      FastAPI · REST · SSE · React+Vite+TS · Gate交互        │
├────────────────────────────────────────────────────────────┤
│  Arch-L8  测试、验证与交付层                                  │
│      P5验证 · 迁移正确性 · 构建验证 · 回归基线 · 交付包      │
├────────────────────────────────────────────────────────────┤
│  Arch-L1  产品流程层                                          │
│      Project · P0接入→P1建档→P2评估→P3规划→P4执行→P5验证    │
│      →P6交付 · 场景引导 · 用户Gate                           │
├────────────────────────────────────────────────────────────┤
│  Arch-L2  编排与运行时层                                      │
│      LangGraph主编排 · NodeLoop · StagePlan · TaskPlan       │
│      TaskGraph · interrupt/resume · checkpoint · 三执行模式   │
├────────────────────┬───────────────────────────────────────┤
│  Arch-L3 Agent/Skill/资源层 │  Arch-L4 模型网关层                  │
│  Node Worker Agent   │  ModelGateway · LiteLLM Adapter      │
│  Acceptance Agent    │  ModelProfile · ModelStrategy         │
│  Authorization Agent │  Fusion(模型能力) · 成本预算          │
│  Expert/Gate Agent   │  模型选择优先级(不绑定P阶段)           │
│  R/P Skill · Tool    │                                      │
│  MCP · Case · Knowl. │                                      │
├────────────────────┴───────────────────────────────────────┤
│  Arch-L5  工作区与执行环境层                                  │
│      Project Workspace · Environment Profile                │
│      Execution Session · 三状态分离                          │
├────────────────────────────────────────────────────────────┤
│  Arch-L6  数据、事件、证据与审计层                             │
│      DB · LangGraph checkpoint · workspace文件 · event log   │
│      Artifact · Evidence · Trace · Audit · Gate决策记录      │
├────────────────────────────────────────────────────────────┤
│  Arch-L0  治理与策略层                                        │
│      决策记录 · 事实源层级 · 变更控制 · AGENTS.md · 历史只读  │
└────────────────────────────────────────────────────────────┘
```

> **备注**：本文 Arch-L0~Arch-L8 为架构分层编号，与风险级别 L0-L5（`02-术语表.md`）属于不同维度，互不冲突。阅读时请根据上下文区分。

各层职责如下。

### 2.1 Arch-L0 治理与策略层

负责：

```text
决策记录；
文档事实源层级；
变更控制；
交接规范；
安全硬规则；
历史资产只读参考；
目录治理；
AGENTS.md 执行准则。
```

架构要求：

```text
1. 系统设计不得绕过治理层硬规则；
2. 变更技术栈、主编排、模型网关、安全策略、目录事实源时必须走变更控制；
3. 历史资产只能受控吸收，不得直接作为当前运行骨架（D-062）；
4. 决策记录是最高事实源，架构文档不得另立决策事实源（D-068）。
```

### 2.2 Arch-L1 产品流程层

负责：

```text
Project；
P0 接入 → P1 建档 → P2 评估 → P3 规划 → P4 执行 → P5 验证 → P6 交付；
Project 场景引导；
用户 Gate。
```

架构要求：

```text
1. Project 是用户可见主对象（D-070）；
2. 不引入独立 Mission 产品层；
3. P0-P6 可裁剪，但被裁剪阶段不得伪装 completed；
4. 被启用阶段必须具备 Gate、Artifact、Evidence、Trace/Audit 和完成条件；
5. 阶段晋级必须用户授权（D-023）。
```

### 2.3 Arch-L2 编排与运行时层

负责：

```text
LangGraph 主编排；
阶段跳转；
Run 推进；
NodeLoop；
Stage Plan；
Task Plan / Task Plan Batch；
TaskGraph；
interrupt / resume；
checkpoint；
Manual / Plan / Auto 执行模式。
```

架构要求：

```text
1. LangGraph 是主编排底座（D-037）；
2. 不以自研状态机替代主编排（D-065）；
3. 自研部分只作为状态 schema、API、SSE、Adapter、Evidence/Artifact/Trace 数据层、
   Workspace Service、ExecutionProvider、Policy/Audit 等外部服务或适配层；
4. NodeLoop 是节点内部标准小循环（D-020）；
5. TaskGraph 边策略必须显式（D-022）；
6. 执行模式只影响阶段内部 Gate 密度和授权方式，不改变 P0-P6 和阶段晋级 Gate（D-024）。
```

### 2.4 Arch-L3 Agent / Skill / 资源层

负责：

```text
Node Worker Agent；
Acceptance Agent；
Auto Review / Authorization / Safety Agent；
Expert Agent；
Conversation / Gate Agent；
R 系列建设 Skill；
P 系列平台运行 Skill；
Tool；
MCP；
Case；
Knowledge；
Policy；
Template；
确定性转换资源。
```

架构要求：

```text
1. 默认少 Agent、多 Skill（D-016）；
2. Agent 切换必须由条件触发（D-017）；
3. R 系列 Skill 与 P 系列 Skill 隔离（D-008, D-008-REV1）；
4. P 系列 Skill 属于平台资源，归入 平台资源/skills/P系列/（D-008-REV1）；
5. Case 是经验材料，不具备执行权（D-040）；
6. 确定性转换以 Skill/Tool/Expert Agent/MCP 形式接入，不作为独立引擎主线（D-063）；
7. 所有资源调用记录来源、风险、权限和 Trace（D-041）。
```

### 2.5 Arch-L4 模型网关层

负责：

```text
ModelGateway；
LiteLLM SDK Adapter；
ModelProfile；
ModelStrategy；
Provider 配置；
模型选择优先级；
Fusion 模型能力；
token/成本预算能力。
```

架构要求：

```text
1. ModelGateway 是模型调用抽象层（D-039）；
2. LiteLLM SDK Adapter 是当前暂定底层适配路线；
3. 模型选择不绑定 P 阶段（D-036）；
4. Fusion 是模型能力/ModelProfile/ModelStrategy，不是特殊流程（D-035）；
5. Fusion 不绕过 Policy/Gate/Audit；
6. token/成本预算属于模型模块功能，不进入主流程硬依赖（D-064）。
```

### 2.6 Arch-L5 工作区与执行环境层

负责：

```text
Project Workspace；
Environment Profile；
Execution Session；
文件持久化；
环境声明；
命令执行；
构建、测试、Patch、外部 Agent 执行；
服务、数据库、中间件、预览等 Runtime 能力。
```

架构要求：

```text
1. 每个 Project 有独立 Project Workspace（D-050）；
2. Project Workspace 负责项目文件持久化；
3. Environment Profile 负责环境声明化；
4. Execution Session 负责执行按需隔离；
5. 退出工作区 UI 不等于停止任务（D-052）；
6. 容器、终端、前端 UI 不能作为状态源（D-053）；
7. Coding State / Execution State / Runtime State 必须分离（D-055）。
```

### 2.7 Arch-L6 数据、事件、证据与审计层

负责：

```text
数据库；
LangGraph checkpoint；
workspace 文件；
event log；
Artifact；
Evidence；
Trace；
Audit；
Gate 决策记录；
资源调用记录；
模型调用记录。
```

架构要求：

```text
1. 状态恢复由数据库、LangGraph checkpoint、workspace 文件、trace/audit、event log 共同承担（D-053）；
2. Artifact 不自动晋升为项目文档（D-014）；
3. Evidence 不得后补成事实；
4. 执行动作必须有 Trace；
5. 高风险动作和 Gate 决策必须有 Audit；
6. No Evidence / No Trace = No Trusted Result（D-066）。
```

### 2.8 Arch-L7 API 与前端交互层

负责：

```text
FastAPI 服务；
REST API；
SSE/事件流；
React + Vite + TypeScript 前端；
Project 列表；
项目概览；
Project Workspace；
Agent 对话；
文件视图；
任务状态；
Gate 交互；
Artifact/Evidence/Trace/Audit 检视。
```

架构要求：

```text
1. R1 输出建议契约，R2 校准为实现契约（D-056）；
2. 前端必须显式标记 mock/未接真实服务能力（D-049）；
3. 工作区采用独立全屏 IDE 心智（D-046）；
4. Agent 对话 Tab 常驻（D-047）；
5. 文件面板支持代码视图与材料视图（D-048）；
6. Evidence、Trace、Audit 在右侧检视；
7. 前端状态不是系统事实源（D-053）。
```

### 2.9 Arch-L8 测试、验证与交付层

负责：

```text
P5 验证；
迁移正确性证明；
构建验证；
运行/启动验证；
测试保留与生成；
回归基线对比；
关键行为等价或差异登记；
交付包；
交付说明；
遗留风险。
```

架构要求：

```text
1. P5 验证必须产出可验证证据（D-066）；
2. "看起来完成"或"代码就绪"不得作为验证通过；
3. 验证失败或证据不足不得标记 completed；
4. 确定性验证能力可作为 Skill/Tool/Expert Agent/MCP 接入（D-063）；
5. P6 交付必须可追溯到 Artifact、Evidence、Trace、Audit。
```

## 3. 核心对象与边界

### 3.1 Project

Project 是用户可见主对象（D-070）。

架构含义：

```text
1. Project 绑定独立 Project Workspace；
2. Project 按 P0-P6 推进；
3. Project 下可有 Run、Stage Plan、Task Plan、TaskGraph、Artifact、Evidence、Trace、Audit；
4. Project 是前端入口、工作区入口、任务状态入口和交付入口；
5. 不在 Project 与 P0-P6 之间插入 Mission 产品层。
```

### 3.2 Run

Run 是 Project 内一次执行或推进记录。

架构含义：

```text
1. Run 记录当前阶段、任务状态、Gate 状态、后台任务状态；
2. Run 可关联 Stage Plan、Task Plan、TaskGraph；
3. Run 可产生 Artifact、Evidence、Trace、Audit；
4. Run 不替代 Project；
5. Run 不应被 Mission 产品层包裹。
```

### 3.3 Stage Plan

Stage Plan 表达阶段级计划。

架构含义：

```text
1. 描述某个 P 阶段的目标、范围、风险、权限边界、输出和 Gate；
2. Plan Mode 下用户审核 Stage Plan；
3. Auto Mode 下 Stage Plan 可由 Agent 审核，但阶段晋级仍必须用户 Gate（D-028）；
4. Stage Plan 不是一次性大计划的替代品，而是多层计划体系的一层（D-026）。
```

### 3.4 Task Plan / Task Plan Batch

Task Plan 表达任务级计划。

架构含义：

```text
1. 描述任务目标、范围、输入、输出、风险、权限、验证方式；
2. Task Plan Batch 可批量组织任务，但必须清晰说明批次边界（D-029）；
3. Task Plan 不得越过 Stage Plan 和 Gate；
4. Task Plan 是 TaskGraph 的任务来源之一。
```

### 3.5 TaskGraph

TaskGraph 表达任务依赖和执行路径。

架构含义：

```text
1. 支持串行、并行、混合和嵌套循环（D-021）；
2. 边策略必须显式（D-022）；
3. TaskGraph 传递 Artifact、Evidence、Context 和 Gate 信息；
4. TaskGraph 的失败策略、重试策略、合并策略必须可解释；
5. TaskGraph 不应被前端 UI 状态替代。
```

### 3.6 Artifact

Artifact 是执行产物。

架构含义：

```text
1. Artifact 可来自建档、评估、规划、执行、验证、交付；
2. Artifact 必须可关联 Project/Run/Stage/Task；
3. Artifact 不自动晋升为项目文档（D-014）；
4. Artifact 晋升必须经过 Gate 或验收。
```

### 3.7 Evidence

Evidence 是结论和验收的证据。

架构含义：

```text
1. 关键结论必须有 Evidence；
2. 验收结论必须有 Evidence；
3. 验证结论必须有 Evidence；
4. Evidence 不得后补成事实；
5. 无 Evidence 的内容只能标记为建议、推断、待验证或不通过。
```

### 3.8 Trace / Audit

Trace 记录过程，Audit 记录关键决策和高风险动作。

架构含义：

```text
1. 执行动作必须有 Trace；
2. Gate 决策必须有 Audit；
3. 高风险动作必须有 Audit；
4. 模型调用、资源调用、Tool/MCP 调用应可追踪；
5. Trace/Audit 是状态恢复和验收可信度的基础（D-053）。
```

### 3.9 平台助手（平台级薄助手组件）

平台助手（AI 精灵 / 客服对话 Agent）是**平台级、薄的内置助手组件**，独立于 LangGraph 迁移主编排与项目运行时。

架构含义：

```text
1. 不进入 LangGraph 主编排，不作为 P0-P6 节点或 Run 内角色；
2. 独立于 Arch-L3 的 Agent/Skill 资源体系，是平台级使用助手，不是迁移编排 Agent；
3. 模型连通性自测复用 ModelGateway（D-039）薄抽象，不另起调用通道，
   仅影响助手自身会话，不改变平台/项目默认模型（不违背 D-065 薄编排）；
4. 代用户操作 [规划]（建 Project/Run、报状态）须经 Policy/Gate 授权，
   L3+ 强制用户确认，纳入 Audit；
5. 不得泄露 Key/Token/Secret（D-032）。
```

> 详见 `文档/00-项目治理/01-决策记录.md` D-073。

## 4. 主编排架构

### 4.1 LangGraph 的位置

LangGraph 是 rebuild 的主编排底座（D-037）。

负责承载：

```text
P0-P6 主流程；
阶段跳转；
Gate；
checkpoint；
interrupt/resume；
节点流转；
运行状态推进。
```

### 4.2 自研部分的边界

允许自研：

```text
状态 schema；
API；
SSE；
Adapter；
Evidence/Artifact/Trace 数据层；
Workspace Service；
ExecutionProvider；
Policy/Audit 服务；
业务规则和领域逻辑。
```

不允许自研替代：

```text
主编排状态机；
LangGraph 的阶段流转职责；
LangGraph checkpoint/interrupt/resume 主能力。
```

### 4.3 薄编排原则（D-065）

编排层必须保持薄。

架构含义：

```text
1. 编排层只负责流程、状态、节点和中断恢复；
2. 业务能力下沉到 Agent/Skill/Tool/Resource；
3. 模型能力下沉到 ModelGateway；
4. 安全能力下沉到 Policy/Hook/Authorization；
5. 证据和审计下沉到 Evidence/Trace/Audit 数据层；
6. 不在编排层堆积复杂业务判断。
```

## 5. 工作区与执行环境架构

### 5.1 三对象模型（D-051）

当前版本采用：

```text
Project Workspace：项目文件持久化；
Environment Profile：环境声明化；
Execution Session：执行按需隔离。
```

### 5.2 Project Workspace

Project Workspace 负责：

```text
1. 保存当前项目源码；
2. 保存项目文档和材料；
3. 保存 Artifact；
4. 保存 Evidence；
5. 保存运行记录；
6. 保存 Trace/Audit 的文件型产物或索引；
7. 按 project_id 隔离文件与任务状态。
```

Project Workspace 不负责：

```text
1. 作为执行隔离边界本身；
2. 作为唯一状态源；
3. 作为权限判断唯一依据；
4. 替代数据库和 checkpoint。
```

### 5.3 Environment Profile

Environment Profile 负责声明：

```text
1. 项目运行环境；
2. 依赖要求；
3. 构建要求；
4. 测试要求；
5. 外部服务要求；
6. 环境风险和限制。
```

Environment Profile 是声明，不等同于正在运行的执行环境。

### 5.4 Execution Session

Execution Session 负责：

```text
1. 执行命令；
2. 运行构建；
3. 运行测试；
4. 生成 Patch；
5. 调用外部 Agent/Tool/MCP；
6. 按需隔离执行上下文。
```

Execution Session 不得绕过：

```text
Policy；
Hook；
Gate；
Trace；
Audit。
```

### 5.5 三状态分离（D-055）

必须区分：

```text
Coding State：文件、编辑、产物、协作；
Execution State：命令、构建、测试、Patch、外部 Agent；
Runtime State：服务、数据库、中间件、预览。
```

架构要求：

```text
1. 三者分别持久化、隔离和审计；
2. 预览可打开不等于验证通过；
3. 命令执行成功不等于运行服务健康；
4. 文件修改完成不等于迁移完成；
5. 终端存在不等于任务可信。
```

## 6. Agent / Skill / 资源架构

### 6.1 Agent 架构原则（D-016, D-017）

默认采用：

```text
同一 Agent + 不同 Skill + 不同上下文 + 不同工具权限
```

仅在以下条件触发时切换 Agent：

```text
需要干净上下文；
需要更换模型；
权限边界不同；
责任边界不同；
并行任务需要隔离；
需要专家能力；
需要独立验收。
```

### 6.2 必要 Agent 类型（D-019）

第一阶段保留少量必要 Agent 类型：

```text
Node Worker Agent；
Acceptance Agent；
Auto Review / Authorization / Safety Agent；
Expert Agent；
Conversation / Gate Agent。
```

这些类型是职责边界，不代表每个 P 阶段都要固定一个 Agent。

### 6.3 Skill 架构原则（D-008, D-008-REV1）

Skill 分为：

```text
R 系列建设 Skill：用于 rebuild 当前版本建设；
P 系列平台运行 Skill：用于未来 rebuild 平台在用户项目 P0-P6 中运行。
```

架构要求：

```text
1. R 系列与 P 系列隔离；
2. P 系列 Skill 放入 平台资源/skills/P系列/（D-008-REV1）；
3. Skill 不等于任意脚本；
4. Skill 不得绕过 Policy/Gate/Audit；
5. 社区 Skill 不得默认执行（D-061）。
```

### 6.4 资源架构原则

平台资源包括（D-008-REV1）：

```text
agents；
skills；
tools；
mcp；
cases；
knowledge；
policies；
templates；
registry。
```

资源调用统一记录：

```text
来源；
风险；
权限；
Trace。
```

资源使用顺序（D-042）：

```text
用户/当前项目自己的资源；
rebuild 本地资源；
在线社区资源。
```

### 6.5 Case 边界（D-040）

Case 是经验材料。

Case 不得直接转为：

```text
可执行脚本；
Tool；
Executable Skill；
Patch；
自动迁移方案；
自动代码修改。
```

### 6.6 确定性转换资源（D-063）

AST/codemod 等确定性转换能力应作为：

```text
Skill；
Tool；
Expert Agent；
MCP。
```

它们不作为独立确定性转换引擎主线。

## 7. 模型与 Fusion 架构

### 7.1 ModelGateway（D-039）

ModelGateway 是模型调用抽象层。

负责：

```text
模型 Provider 适配；
模型选择优先级；
ModelProfile；
ModelStrategy；
调用记录；
fallback/retry/cost/latency 等模型策略扩展；
Fusion 作为模型能力的挂载。
```

### 7.2 模型选择原则（D-036）

模型选择不绑定 P 阶段。

优先级：

```text
用户临时指定；
Task/Node override；
Agent 默认模型；
Project 默认模型；
System 默认模型。
```

### 7.3 Fusion（D-035）

Fusion 是：

```text
模型能力；
ModelProfile；
ModelStrategy。
```

Fusion 不是：

```text
特殊 P 阶段；
特殊 R 阶段；
特殊评审引擎；
独立运行时角色；
默认必经 Agent；
授权主体；
验收主体。
```

Fusion 不得绕过：

```text
Policy；
Gate；
Audit；
Evidence；
用户确认。
```

### 7.4 成本与 token 预算（D-064）

成本与 token 预算属于模型模块功能。

架构处理：

```text
1. 归入 ModelGateway/模型策略；
2. 不作为 P0-P6 主流程默认 Gate；
3. 可在 R5 或后续阶段按需实现；
4. 不阻塞 P0-P6 主干。
```

## 8. 安全与授权架构

### 8.1 三层安全机制（D-030）

安全机制采用：

```text
Hook；
Policy/Rule；
Security/Authorization Agent。
```

### 8.2 Policy 优先级（D-031）

Policy 是硬约束，优先级高于 Agent 判断。

架构要求：

```text
1. Security/Authorization Agent 不能批准 Policy 禁止的动作；
2. Policy 冲突必须暂停并升级；
3. Policy 结果应进入 Trace/Audit；
4. Policy 不应写死为简单命令白名单（D-033）。
```

### 8.3 风险分级（D-033, D-034）

以下动作必须先映射风险级别：

```text
命令；
Tool；
MCP；
写盘；
Git；
外部系统写操作；
远程资源操作。
```

L5 高风险动作暂定全部强制用户 Gate（D-034）。

> 注：风险级别 L0-L5 与本文架构分层 Arch-L0~Arch-L8 为不同维度，互不冲突。

### 8.4 密钥脱敏（D-032）

允许识别：

```text
env 是否存在；
配置文件是否存在；
密钥文件是否存在。
```

不得泄露：

```text
Key；
Token；
Secret；
Password；
明文 env；
任何可还原密钥的日志或截图。
```
