## 0. 为什么容器化（结论）

适合，主因是 rebuild 的两项固有属性，而非追新：

1. **混合运行时**：后端 Python 3.12 + uv，集成层 shell 调用系统 `git`/`ssh`，OpenCode 走 Node CLI。同宿主机依赖易互相干扰。容器按模块隔离依赖。
2. **平台会执行代码**：Agent/OpenCode 生成的代码当前以宿主机 `subprocess` 运行，仅靠 deny-list 防护。将执行迁入**受限、网络隔离、非 root、资源受限**的一次性容器，是与执行风险分级 L4/L5 契合的安全升级，也是本规范的核心。

执行顺序硬约束：**先完成功能/安全返工（含 P0 连接池泄漏），再容器化**，不得把缺陷固化进镜像。

## 1. 部署拓扑（Phase C1：基础编排）

```
┌─────────────┐      ┌──────────────┐      ┌──────────────────┐
│ frontend     │/api │ backend       │ DB   │ sqlite(卷) / pg   │
│ nginx:80     ├────▶│ uvicorn:8000  ├─────▶│ (profile=pg)      │
│ SPA + 反代   │      │ FastAPI       │      └──────────────────┘
└─────────────┘      │  + git/ssh    │
                     │  ExecutionProvider
                     └──────┬───────┘
                            │ EXECUTION_MODE=container（C2）
                            ▼
                     ┌──────────────────────┐
                     │ execution-sandbox      │ 无网络/只读根/非root/限额
                     │ 一次性、disposable     │
                     └──────────────────────┘
```

- **frontend**：多阶段构建 → nginx 托管 `dist`，`/api` 反代至 `backend:8000`，SSE 关闭缓冲。
- **backend**：多阶段 uv 构建；运行层装 `git`+`openssh-client`；非 root（uid 10001）；`/api/health` healthcheck；数据卷 `/app/.data`（sqlite db、执行沙箱、仓库克隆）。
- **db**：默认 SQLite（卷），开箱即用；`--profile pg` 切 PostgreSQL（`DATABASE_URL` 覆盖）。
- **execution-sandbox**：Phase C2 隔离执行镜像，默认只构建（`--profile sandbox`）。

## 2. 镜像与编排基线（硬规则）

1. **密钥绝不入镜像**：`LLM_API_KEY`/各 Provider Key/Webhook/OAuth Secret 只经 `env_file`（`.env`，已 `.gitignore`）注入。镜像、`docker history`、构建日志均不得含明文（AGENTS §8/§12）。
2. **非 root 运行**：所有应用容器以非 root 用户运行。
3. **数据持久化用命名卷**：DB 与 `.data/` 必须落卷，容器重建不丢数据。
4. **可复现构建**：后端依赖锁定 `uv.lock`（`uv sync --frozen`），前端 `npm ci`。
5. **健康检查**：每个常驻服务定义 `HEALTHCHECK`。
6. **`.dockerignore` 卫生**：排除 `.venv/`、`.data/`、`node_modules/`、`dist/`、`.env`、`.git/`。
7. **LangGraph 主编排底座不变**（D-037）：容器化只改"在哪运行/如何隔离"，不改编排内核。

## 3. 执行隔离规范（Phase C2 — 安全核心）

### 3.1 ExecutionProvider 强制接口

平台内**一切代码执行**（Workspace、OpenCode 集成、未来 Run/Task 执行）**必须经 `ExecutionProvider`**（`backend/app/services/execution_provider.py`），不得在调用点直接 `subprocess`/直连 `opencode_adapter`：

| 模式（`EXECUTION_MODE`） | Provider | 说明 |
|--------------------------|----------|------|
| `local`（默认） | `LocalSubprocessExecutionProvider` | 当前行为：宿主机受控子进程 + deny-list，向后兼容 |
| `container`（预留） | `ContainerExecutionProvider` | 一次性、网络隔离、非 root、资源受限容器内执行；**未接线前返回显式 reserved 结果，绝不静默降级为宿主机执行** |

### 3.2 沙箱容器硬化基线（compose 已落地）

`read_only` 根文件系统、`network_mode: none`、`cap_drop: ALL`、`no-new-privileges`、`pids_limit`、`mem_limit`、`cpus`、`tmpfs` 工作目录、非 root。沙箱**不得**装 `git`/`ssh`/网络工具——不可外联代码托管/远程。

### 3.3 纵深防御（不可删除）

容器隔离是**第一层**；现有 `opencode_adapter` 的 deny-list / allowlist / timeout / stdout-stderr 截断 / env 脱敏作为**第二层**保留。

## 4. 对后续工作区（Workspace）及相关施工的约束（预留要求）

> 本节为对未来 R 阶段施工的**硬约束**，确保"工作区及相关部分"按容器化思路落地。

1. **R8+ Workspace/Run 执行施工**：项目内代码运行、测试、迁移脚本执行，**必须**走 `ExecutionProvider`，并优先支持 `container` 模式；新增执行入口不得绕过该 seam。
2. **每个项目工作区 = 一个隔离执行上下文**：以容器/命名空间为边界，工作区文件挂载为卷；不同项目工作区互不可见。
3. **远程/Git 操作**：保留在 backend 容器或专用 worker，凭据经卷/secret 挂载，不入镜像；沙箱本身无外联能力。
4. **信创交付（Phase C3）**：基础镜像替换为信创合规镜像（openEuler/UOS 系），产出离线镜像包，目标环境做端到端联调（D-074 同等标准）。
5. **变更控制**：部署/执行架构变更按 `04-变更控制规范` C2（编排）～C4（技术栈）提交；本规范 accepted 后作为该领域单一事实源。
